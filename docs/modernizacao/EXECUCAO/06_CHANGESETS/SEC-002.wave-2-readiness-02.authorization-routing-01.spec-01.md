# R222' — SEC-002 · Wave 2 Readiness · Authorization Routing (spec)

**Tipo:** especificação · governança pura  
**Alvo:** roteamento determinístico de mensagens externas GM/D-3 entre rejeição, reenvio, ledger futuro e abertura de rounds R213'/R214'.  
**Baseline:** R208', R209', R210', R211', R212', R213', R214', R215', R216', R217', R218', R219', R220', R221'.  
**Data:** 2026-07-12.

## 1. Objetivo

Fixar a árvore de decisão que impede mensagens genéricas, ambíguas ou incompletas de produzirem assinatura, deploy ou apply na Onda 2. Este spec **não** cria ledger, **não** assina, **não** cria `GO-SEC-002-helpers-02-deploy-01.md`, **não** preenche §5 de `D-3-SEC-002.md`, **não** faz deploy de `helpers-02` e **não** aplica `helpers-03`.

## 2. Entradas reconhecidas

O roteador só reconhece quatro famílias de entrada:

1. **Comando genérico de continuidade** — exemplo: `Seguir`, `MANTENHA O PADRÃO`, `ONDA ATUAL`, `PRÓXIMO PASSO`.
2. **Intake GM candidato** — bloco que declara alvo `helpers-02.deploy-01` e decisão `GO` ou `NO-GO`.
3. **Intake D-3 candidato** — bloco que declara alvo `helpers-03.apply-01` e opção `D-3a`, `D-3b` ou `D-3c`.
4. **Reenvio explícito** — bloco que declara estar substituindo intake rejeitado anterior conforme R220'.

Qualquer outra entrada permanece fora do escopo operacional e só pode gerar documentação de governança.

## 3. Árvore de roteamento

1. Se a entrada for comando genérico de continuidade, classificar como `SEM AUTORIZAÇÃO`; efeito: abrir apenas round documental, se necessário, preservando bloqueios.
2. Se a entrada for GM candidata, aplicar R218' §2:
   - se passar integralmente: registrar no ledger futuro conforme R221' como `ACEITO` e abrir round R213' materialize;
   - se falhar: mapear para R219' (`GM-N#`) e, se houver ledger já criado por round futuro, registrar como `REJEITADO`.
3. Se a entrada for D-3 candidata, aplicar R218' §3:
   - se passar integralmente: registrar no ledger futuro conforme R221' como `ACEITO` e abrir round R214' materialize;
   - se falhar: mapear para R219' (`D3-N#`) e, se houver ledger já criado por round futuro, registrar como `REJEITADO`.
4. Se a entrada for reenvio explícito, aplicar R220' antes de qualquer efeito material.
5. Se GM e D-3 válidos chegarem no mesmo ciclo, GM é roteado primeiro; D-3 fica em fila documental até o ciclo seguinte, preservando a dependência de `helpers-03` sobre deploy efetivo de `helpers-02`.

## 4. Efeitos proibidos

O roteador nunca pode, por si só:

- interpretar `Seguir` como `GO`, `NO-GO`, `D-3a`, `D-3b` ou `D-3c`;
- criar ou preencher documento de decisão;
- executar migration, SQL, edge function, workflow ou script;
- alterar `supabase/`, `src/`, `.github/sec002-evidence/INDEX.md`, verifier, apply-map, batches, `_lib/` ou banco;
- aceitar intake com segredo/chave/senha.

2. R213', R214', R216', R217', R218', R219', R220' e R221' preservados byte-a-byte.  
3. `SEC-002.wave-2-readiness-02.authorization-ledger.md` **não** criado neste ciclo.  
4. `GO-SEC-002-helpers-02-deploy-01.md` **não** criado; §5 de `03_DECISOES/D-3-SEC-002.md` permanece vazio.  
5. `SEC-002.inventory-02.csv` preservado (hash `8c18a694442e…d66a404ef`).  
6. `.github/sec002-evidence/INDEX.md` permanece com 45 linhas; `EXPECTED_INDEX_ROWS=45`.  
7. `Apply-map: v2026-07-12.4` preservado; `verify-wave-2-preconditions.mjs --json` continua verde em PC1..PC7 (PC8/PC9 SKIP).

## 6. Delegações abertas

- Aguardar intake GM ou D-3 completo conforme R218'/R220'.
- Se houver intake inválido formal, aplicar R219' e registrar apenas rejeição documental.
- Se houver intake válido formal, abrir round R213' ou R214' sem inverter dependências.
