# SEC-001.i.spec-01 — Remoção do password em plaintext no localStorage

**Onda:** 2 (bloqueada — D-1/D-2 · cutover em pipeline dedicado)
**Data:** 2026-07-12
**Escopo:** apoio à Onda 2 autorizado por D-9. Especifica a remoção de `password` em texto claro persistido em `localStorage.go_player` (audit-02 §3 e §7 — recomendação SEC-001.i). **Nenhum código de produção é alterado neste changeset.**

## 1. Estado atual

`src/contexts/AppContext.tsx` (linhas ~323-326) persiste o objeto `go_player` em `localStorage` incluindo `password` em texto claro. Motivação original: permitir `ensureSupabaseSession` reexecutar após reload do navegador, já que a sessão Cloud não sobrevive independente do PHP.

Riscos:
- XSS em qualquer rota exfiltra credencial permanente (não apenas token de sessão).
- Backups de perfil do navegador, extensões e devtools abertos expõem a senha.
- Viola premissa de zero-trust do cutover (`SEC-001.plan-h`).

## 2. Estado alvo

`localStorage.go_player` NUNCA contém `password`. Reidratação de sessão passa a depender exclusivamente do refresh token que o cliente Supabase já persiste em sua chave própria (`sb-<ref>-auth-token`), gerido pelo SDK.

Formato final de `go_player` (campos preservados):

```ts
{
  id, login, nome, email,
  is_gm, acessos,
  // password: REMOVIDO
}
```

## 3. Dependências obrigatórias (ordem)

`SEC-001.i` **só é seguro depois** de:

1. `SEC-001.g` — rota única `ensureCloudSession` + hidratação real via `signInWithPassword` no momento do login (spec-01 §3.1). Sem isso, reload perde a sessão Cloud porque só o PHP tem a credencial.
2. `SEC-001.mig-01` — sem duplicatas de `auth.users`, `refreshSession()` retorna o `user_id` correto.

## 4. Mudanças de código previstas

### 4.1 `src/contexts/AppContext.tsx`

- **Login (linha ~400)**: após `ensureCloudSession` (spec-01 §3.1), armazenar em `go_player` apenas os campos §2. Nunca `password`.
- **Reload (linha ~305-315)**: substituir o bloco atual por:
  ```ts
  const { data: { session } } = await supabase.auth.getSession();
  if (!session) {
    // sessão Cloud expirou — força novo login PHP (não tenta silencioso com senha)
    clearLocalPlayer();
    return;
  }
  // hidrata currentPlayer a partir de go_player + valida contra profiles/user_roles
  ```
- **Migração one-shot**: no primeiro boot pós-deploy, se `go_player.password` existir, remover a chave e forçar re-login:
  ```ts
  const raw = localStorage.getItem("go_player");
  if (raw && JSON.parse(raw).password) {
    localStorage.removeItem("go_player");
    localStorage.removeItem("go_token");
    await supabase.auth.signOut();
  }
  ```

### 4.2 `src/lib/auth/ensureCloudSession.ts`

Sem mudança de assinatura. Já recebe `password` como argumento por chamada (não persiste). Adicionar guard: se caller passar objeto com campo `password`, avisar em dev (`console.warn` em `import.meta.env.DEV`).

### 4.3 Nenhum outro consumidor

`rg -n "go_player" src` deve ser revisado no PR — hoje o objeto é lido em Login, hydrate e logout. Nenhum consumo direto de `password` fora do bloco `ensureSupabaseSession` (que já é removido em `SEC-001.g`).

## 5. Impacto UX

- Sessão Cloud expira em ~1h (default do SDK) mas o refresh token dura ~30d — reload dentro desse período é transparente.
- Após 30d ou revogação, usuário volta à tela de login (comportamento esperado).
- Sem "auto-login silencioso" após limpar cookies do navegador (correto — era exatamente o vetor).

## 6. Critérios de aceitação

- [ ] `rg -n "password" src/contexts/AppContext.tsx` sem matches em blocos de persistência.
- [ ] `JSON.parse(localStorage.getItem("go_player")).password === undefined` em todas as contas testadas.
- [ ] Reload após 5min mantém `currentPlayer` (refresh token válido).
- [ ] Reload após `supabase.auth.signOut()` cai em `/login`.
- [ ] Migração one-shot: usuário com `go_player.password` legado é redirecionado a `/login` no primeiro boot.

## 7. Rollout

Junto com `SEC-001.g` (R1 do release train em `SEC-001.g.spec-01 §5`), OU no release seguinte se preferir isolar risco. Não precisa migração SQL — é 100% cliente.

## 8. Fora de escopo

- Substituir `api.create("login")` por `signInWithPassword` como primary IdP → `SEC-001.j`.
- Rotação de senha forçada para usuários legados → decisão de produto, não segurança bloqueante.

## 9. Impacto em produção

**Nenhum.** Documento de especificação. Nenhum arquivo em `src/` ou `supabase/` foi alterado.
