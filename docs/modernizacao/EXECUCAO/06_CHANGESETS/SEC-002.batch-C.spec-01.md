## 4. Padrões de regra por classe

Quatro padrões apenas. Toda tabela do lote mapeia para exatamente um.

### 4.1 Padrão **OBRA-DIRECT**

```sql
create policy "<tabela>_select_obra"
  on public.<tabela>
  for select
  to authenticated
  using (public.user_in_obra(auth.uid(), obra_id));

create policy "<tabela>_write_obra"
  on public.<tabela>
  for all
  to authenticated
  using (public.user_in_obra(auth.uid(), obra_id))
  with check (public.user_in_obra(auth.uid(), obra_id));
```

`user_in_obra` já incorpora GM e fallback por empresa (`SEC-002.helpers-01` §4.2). Não precisa `or current_is_gm()` inline.

### 4.2 Padrão **EMPRESA-DIRECT**

Aplicado a `obras`:

```sql
create policy "obras_select_empresa"
  on public.obras
  for select
  to authenticated
  using (public.user_in_empresa(auth.uid(), empresa_id));

create policy "obras_write_empresa_role"
  on public.obras
  for all
  to authenticated
  using (
    public.current_is_gm()
    or (
      public.user_in_empresa(auth.uid(), empresa_id)
      and public.has_role(auth.uid(), 'obras')
    )
  )
  with check (
    public.current_is_gm()
    or (
      public.user_in_empresa(auth.uid(), empresa_id)
      and public.has_role(auth.uid(), 'obras')
    )
  );
```

Escrita exige `role = 'obras'` além do vínculo de empresa; leitura basta o vínculo.

### 4.3 Padrão **OBRA-VIA-PARENT**

Aplicado a `cronograma_item_baseline`, `cronograma_item_revisoes`, `itens_medicao`. Modelo (substituir `<parent_tbl>`, `<parent_fk>`):

```sql
create policy "<tabela>_select_obra_via_parent"
  on public.<tabela>
  for select
  to authenticated
  using (
    exists (
      select 1 from public.<parent_tbl> p
      where p.id = <tabela>.<parent_fk>
        and public.user_in_obra(auth.uid(), p.obra_id)
    )
  );

create policy "<tabela>_write_obra_via_parent"
  on public.<tabela>
  for all
  to authenticated
  using (
    exists (
      select 1 from public.<parent_tbl> p
      where p.id = <tabela>.<parent_fk>
        and public.user_in_obra(auth.uid(), p.obra_id)
    )
  )
  with check (
    exists (
      select 1 from public.<parent_tbl> p
      where p.id = <tabela>.<parent_fk>
        and public.user_in_obra(auth.uid(), p.obra_id)
    )
  );
```

Recursão RLS: `user_in_obra` é `security definer`, então o `exists` interno não reentra no RLS de `<parent_tbl>`. Sem ciclo.

### 4.4 Padrão **EMPRESA-VIA-OBRA**

Aplicado a `colaboradores`, `patrimonios`, `veiculos` (todos com `obra_atual_id`) e — indiretamente — a `responsabilidades_patrimonios`.

```sql
create policy "<tabela>_select_empresa_via_obra"
  on public.<tabela>
  for select
  to authenticated
  using (
    obra_atual_id is null and public.current_is_gm()
    or exists (
      select 1 from public.obras o
      where o.id = <tabela>.obra_atual_id
        and public.user_in_empresa(auth.uid(), o.empresa_id)
    )
  );

create policy "<tabela>_write_empresa_via_obra_role"
  on public.<tabela>
  for all
  to authenticated
  using (
    public.current_is_gm()
    or (
      exists (
        select 1 from public.obras o
        where o.id = <tabela>.obra_atual_id
          and public.user_in_empresa(auth.uid(), o.empresa_id)
      )
      and public.has_role(auth.uid(), '<role_dominio>')
    )
  )
  with check (<mesma expressão do using>);
```

Mapeamento de `<role_dominio>`:

| Tabela | `<role_dominio>` |
|--------|------------------|
| `colaboradores` | `'dp'` (secundário `'rh'` opcional — decisão de D-1) |
| `patrimonios` | `'patrimonio'` |
| `veiculos` | `'frota'` |

`obra_atual_id IS NULL` só é lido/escrito por GM (colaborador entre obras, patrimônio em depósito, etc.).

Para `responsabilidades_patrimonios` (que tem `patrimonio_id`, não `obra_atual_id`):

```sql
using (
  exists (
    select 1 from public.patrimonios pt
    join public.obras o on o.id = pt.obra_atual_id
    where pt.id = responsabilidades_patrimonios.patrimonio_id
      and public.user_in_empresa(auth.uid(), o.empresa_id)
  )
)
```

Escrita: `... and public.has_role(auth.uid(), 'patrimonio')` ou `current_is_gm()`.

## 5. Estrutura atômica da migração

Mesmo shape de `SEC-002.batch-B.spec-01` §4:

```sql
begin;
  -- por tabela:
  drop policy if exists "<policy_atual_1>" on public.<tabela>;
  drop policy if exists "<policy_atual_2>" on public.<tabela>;
  ...
  create policy "<tabela>_select_..." on public.<tabela> ...;
  create policy "<tabela>_write_..."  on public.<tabela> ...;

  alter table public.<tabela> enable row level security;
  revoke all on public.<tabela> from anon;
  grant select, insert, update, delete on public.<tabela> to authenticated;
  grant all on public.<tabela> to service_role;
commit;
```

**Transação única** para as 23 tabelas.

## 7. Exceções nominais

- **`obra_membros`.** Escrita restrita a **GM apenas** (não a `user_in_obra`), para evitar auto-promoção: `USING (public.current_is_gm()) WITH CHECK (public.current_is_gm())`. Leitura: `user_in_obra(auth.uid(), obra_id)`. Isso é compatível com a policy `role-scoped` que já existe em `obra_membros` hoje.
- **`licoes_aprendidas`.** Leitura ampliada para toda a **empresa** dona da obra:
  ```sql
  using (
    exists (
      select 1 from public.obras o
      where o.id = licoes_aprendidas.obra_id
        and public.user_in_empresa(auth.uid(), o.empresa_id)
    )
  )
  ```
  Escrita mantém `user_in_obra`.
- **`obras`.** `INSERT` exige `has_role('obras')` **e** `user_in_empresa(auth.uid(), empresa_id)` — usuário não pode criar obra em empresa que não pertence.

## 11. Riscos

- **R1: performance de policy `EXISTS` em telas de listagem** (`itens_medicao`, `cronograma_item_*`). Mitigação: `user_in_obra` é `stable security definer`; planner faz cache por statement. Índices sobre `cronograma_itens(obra_id)` e `medicoes(obra_id)` já existem (verificar no gate).
- **R2: `colaboradores` sem `empresa_id` direto.** Todo acesso vai por `obras`. Se `obra_atual_id IS NULL`, só GM lê/escreve — telas de "colaborador entre obras" devem ser exercidas por conta GM ou refatoradas para persistir uma empresa titular.
- **R3: `user_in_obra` cai no fallback empresa (`SEC-002.helpers-01` §4.2)** — leitura potencialmente mais ampla que o desejado enquanto `obra_membros` estiver incompleto. Mitigação: povoamento de `obra_membros` é pré-condição operacional do Lote C; sem ele o modelo degrada para "membros da empresa da obra".
- **R4: `responsabilidades_patrimonios` sem `obra_id` nem `empresa_id`** — depende de join duplo. Mitigação: policy escreve o join uma vez; `patrimonios(id, obra_atual_id)` PK já indexada.
- **R5: `mobilizacoes_veiculos` mescla escopo obra + frota**. Escrita: além de `user_in_obra`, exigir `has_role('frota')`:
  ```sql
  using (public.user_in_obra(auth.uid(), obra_id))
  with check (public.user_in_obra(auth.uid(), obra_id) and (public.current_is_gm() or public.has_role(auth.uid(),'frota')))
  ```
