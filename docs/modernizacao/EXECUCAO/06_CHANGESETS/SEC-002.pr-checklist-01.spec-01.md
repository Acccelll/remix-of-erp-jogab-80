# SEC-002.pr-checklist-01.spec-01 — Checklist obrigatório de PR para apply `SEC-002`

**Onda:** 2 (preparatória — bloqueada por fechamento de `SEC-001`)  
**Data:** 2026-07-12  
**Escopo:** especifica o checklist único e obrigatório para cada PR de apply em produção de `SEC-002` (`helpers-02`, `tests-02.suite`, `batch-B`, `batch-C`, `batch-D`, `batch-E`). Consolida os gates de `SEC-002.release-plan-01`, `SEC-002.observability-01.spec-01`, `SEC-002.freeze-policy-01.spec-01` e `SEC-002.staging-parity-01.spec-01` em um template versionado validado por CI. Nenhuma migração é aplicada; nenhum código de `src/` ou edge function muda.

## 1. Objetivos

1. Impedir PR de apply sem evidência explícita de backup, paridade staging, suíte RLS, freeze, observabilidade e rollback.
2. Padronizar o corpo dos PRs para que DRI, GM, DevOps e suporte auditem a decisão go/no-go sem depender de contexto oral.
3. Tornar o checklist validável por CI antes do merge.
4. Produzir trilha de auditoria reaproveitável no post-mortem e no handoff pós-`SEC-002`.

## 2. PRs cobertos

Todo PR que alterar qualquer um dos artefatos abaixo deve usar o template §4:

| Apply | Changeset | Tipo | Campo `sec002_apply_id` |
|-------|-----------|------|--------------------------|
| 1 | `SEC-002.helpers-02.migration` | migration | `helpers-02` |
| 2 | `SEC-002.tests-02.suite` | testes/CI | `tests-02-suite` |
| 3 | `SEC-002.batch-B.migration` | migration | `batch-B` |
| 4 | `SEC-002.batch-C.migration` | migration | `batch-C` |
| 5 | `SEC-002.batch-D.migration` | migration | `batch-D` |
| 6 | `SEC-002.batch-E.migration` | migration | `batch-E` |

PRs de documentação preparatória que não aplicam produção podem referenciar este checklist, mas não são bloqueados por ele.

## 3. Arquivo versionado

Template canônico:

```text
.github/pull_request_template/sec-002-apply.md
```

Regra operacional:

- PR de apply deve ser aberto usando esse template, sem remover seções.
- Campos com placeholder `<...>` devem ser preenchidos.
- Checklist marcado sem evidência/link correspondente é considerado inválido.
- Alterações no template durante o freeze seguem `SEC-002.freeze-policy-01.spec-01` §4 se mudarem gates de schema/policies.

## 4. Template obrigatório

Conteúdo esperado de `.github/pull_request_template/sec-002-apply.md`:

```md
# SEC-002 apply — <helpers-02|tests-02-suite|batch-B|batch-C|batch-D|batch-E>

## Identificação

- sec002_apply_id: <helpers-02|tests-02-suite|batch-B|batch-C|batch-D|batch-E>
- DRI: <nome>
- backup_dri: <nome>
- janela_planejada: <YYYY-MM-DD HH:mm UTC>
- release_plan_ref: docs/modernizacao/EXECUCAO/06_CHANGESETS/SEC-002.release-plan-01.md
- snapshot_id: <id do backup/snapshot>
- staging_snapshot_id: <id de SEC-002.staging-parity §8>

## Escopo

- [ ] Este PR altera somente o changeset indicado em `sec002_apply_id`.
- [ ] Não há alteração em `src/` acoplada ao apply.
- [ ] Não há alteração em schemas proibidos (`auth`, `storage`, `realtime`, `supabase_functions`, `vault`).
- [ ] `notify pgrst, 'reload schema';` está previsto quando houver mudança de policy/function/grant.

## Pré-condições globais

- [ ] `SEC-001` R1–R10 concluído e estável ≥ 48 h.
- [ ] Backup lógico de produção validado e restaurável.
- [ ] Freeze `SEC-002` ativo e sem exceção pendente.
- [ ] DRI e backup presentes na janela.
- [ ] Canal de comunicação preparado (`#anuncios`, `#incidentes`, suporte).

## Paridade staging

- [ ] `sec002-staging-refresh` verde há ≤ 24 h.
- [ ] `.github/sec002-staging-parity.json` aponta para este lote.
- [ ] `fixtures_ok=true`.
- [ ] `helpers_suite_pass=true`.
- [ ] Nenhum dado PII de produção foi copiado para staging.

## Testes RLS

- [ ] Suíte do lote verde em staging.
- [ ] Subconjunto `helpers/` verde.
- [ ] Assert count esperado confirmado: <H15|B39|C92|D75|E110|331>.
- [ ] Oráculos `gm`, `member`, `outsider` e `anonymous` cobertos quando aplicável.
- [ ] Evidência anexada: <link/log>

## Observabilidade

- [ ] Dashboard `SEC-002 — Release` aberto para a janela.
- [ ] Baseline de p95 congelada antes do apply.
- [ ] Alertas `42501`, policy drift e RLS disabled ativos.
- [ ] Job `sec002-tests-prod` agendado para T+15 min.
- [ ] Responsável por monitoramento T+0/T+1h/T+24h definido.

## Freeze / mudanças de schema

- [ ] Nenhuma operação proibida por `SEC-002.freeze-policy-01.spec-01`.
- [ ] Se houver exceção: `SEC-002.freeze.exception-<n>.md` aprovado por GM e tech lead.
- [ ] Grants existem para toda tabela pública nova ou alterada por policy.
- [ ] Policies antigas removidas e novas criadas na mesma transação quando aplicável.

## Rollback

- [ ] Companion rollback identificado: <arquivo/commit>.
- [ ] Rollback testado em staging.
- [ ] Critérios de disparo do release-plan §6 revisados com o operador.
- [ ] Flag de pausa de escrita por módulo disponível quando aplicável.

## Aprovações

- [ ] GM Cappucceno aprovou go/no-go.
- [ ] Tech lead backend aprovou a migration/suite.
- [ ] DevOps on-call aprovou janela e observabilidade.
- [ ] Product/support cientes da superfície impactada.

## Pós-apply obrigatório

- [ ] T+0 comunicado.
- [ ] T+15 min: suíte do lote executada em produção.
- [ ] T+1 h: status publicado.
- [ ] T+24 h: go/no-go documentado antes do próximo lote.
- [ ] Se rollback/errata ocorrer, incidente registrado em `docs/modernizacao/EXECUCAO/07_INCIDENTES/`.
```

## 5. Validação CI

Job obrigatório: `sec002-pr-checklist`.

O job reprova o PR se qualquer regra falhar:

1. Corpo do PR não contém `sec002_apply_id` válido.
2. `sec002_apply_id` não corresponde aos arquivos alterados.
3. Qualquer seção do template §4 foi removida.
4. Há checkbox obrigatório desmarcado no momento do merge.
5. Há placeholder `<...>` remanescente.
6. `staging_snapshot_id` diverge de `.github/sec002-staging-parity.json`.
7. `current_batch` em `.github/sec002-staging-parity.json` não corresponde ao `sec002_apply_id`.
8. `last_refresh_at` excede 24 h.
9. `SEC-002.freeze-policy` detecta operação proibida sem exceção aprovada.
10. Arquivos de lote anterior são modificados junto com lote atual.

Saída esperada:

```json
{
  "job": "sec002-pr-checklist",
  "sec002_apply_id": "batch-C",
  "template_ok": true,
  "staging_parity_ok": true,
  "freeze_ok": true,
  "tests_evidence_ok": true,
  "approvals_ok": true
}
```

## 6. Mapeamento de gates consolidados

| Gate | Fonte | Validação no checklist |
|------|-------|------------------------|
| Ordem canônica | `release-plan` §2 | `sec002_apply_id` + arquivos alterados |
| Janelas T+0/T+1h/T+24h | `release-plan` §3 | seção Pós-apply |
| Go/no-go | `release-plan` §4 | aprovações + testes + observabilidade |
| DRI | `release-plan` §5 | Identificação |
| Rollback | `release-plan` §6 | seção Rollback |
| Freeze | `freeze-policy` §2–§5 | seção Freeze + job guard |
| Paridade staging | `staging-parity` §7–§10 | seção Paridade staging |
| Métricas/alertas | `observability` §2–§6 | seção Observabilidade |

## 7. Convenções de nome

Branch:

```text
sec-002/apply/<sec002_apply_id>
```

Título do PR:

```text
[SEC-002][apply:<sec002_apply_id>] <descrição curta>
```

Commits de correção após CI vermelho devem manter o mesmo PR. Se houver mudança de policy após review aprovado, aprovações são invalidadas e refeitas.

## 8. Critérios de aceite deste changeset

- [ ] Template §4 cobre todos os gates dos documentos consolidados.
- [ ] CI §5 consegue bloquear PR incompleto sem interpretar linguagem livre.
- [ ] `sec002_apply_id` é campo único de roteamento para lote, staging parity e validação de arquivos.
- [ ] Checklist não autoriza nenhum apply sem backup, rollback e observabilidade.
- [ ] Nenhuma mudança real em produção é feita por este changeset.

## 9. Impacto em produção

**Nenhum neste changeset.** Documento de especificação do template e do job de validação. A criação real de `.github/pull_request_template/sec-002-apply.md` e do workflow `sec002-pr-checklist` deve ocorrer em PR de operação separado, consumindo esta spec como contrato.
