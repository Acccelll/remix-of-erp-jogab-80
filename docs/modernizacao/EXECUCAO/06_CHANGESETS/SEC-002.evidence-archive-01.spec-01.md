**Onda:** 2 (bloqueada — depende de fechamento de `SEC-001`)

**Materializa:** `.github/sec002-evidence/index.md` + `.github/sec002-evidence/<apply-id>/manifest.json` + `scripts/sec002/validate-evidence-archive.mjs`

## 1. Objetivo

Definir o contrato único de arquivamento, retenção e validação das evidências produzidas em `SEC-002`. O arquivo formal deve permitir auditoria posterior sem depender de contexto oral, mensagens soltas ou links não rastreáveis.

Este spec consolida:

1. taxonomia de evidências por apply;
2. estrutura de diretórios e manifests;
3. requisitos de integridade, retenção e imutabilidade;
4. evidências mínimas para go/no-go, incidentes, comunicação, acceptance e handoff;
5. validador determinístico para impedir encerramento com evidência ausente.

Sem arquivo de evidências válido, `SEC-002` não pode ser encerrado no handoff pós-RLS.

## 2. Fora de escopo

- Criar dashboards, pipelines ou testes novos.
- Alterar migrations, policies, helpers, código de produção ou funções edge.
- Armazenar segredos, tokens, PII ou dumps sensíveis.
- Substituir artefatos de decisão; este spec referencia e arquiva evidências desses artefatos.

## 3. Taxonomia de evidências

| Categoria | Prefixo | Exemplos | Obrigatória em |
|-----------|---------|----------|----------------|
| Checklist PR | `pr` | body do PR, run CI, changed-files report | todos os applies |
| Staging parity | `staging` | `.github/sec002-staging-parity.json`, refresh run | apply real |
| Go/no-go | `decision` | `.github/sec002-go-no-go/<id>.md`, assinaturas | apply real |
| Testes RLS | `tests` | artifacts da suíte, assert count, logs sanitizados | todos os applies |
| Observabilidade | `obs` | screenshots, URLs, alertas armados | apply real |
| Comunicação | `comms` | `.github/sec002-comms/<id>.md`, refs de mensagens | apply real |
| Incidentes | `incident` | registros, pós-mortems, rollback/hotfix refs | quando aplicável |
| Acceptance | `acceptance` | `.github/sec002-acceptance/<id>.md` | pós-apply |
| Handoff | `handoff` | `.github/sec002-handoff/post-rls.md` | encerramento |
| Rollback | `rollback` | script/ref, hash, dry-run, verificação | apply real |

## 6. Manifest pós-RLS

Arquivo: `.github/sec002-evidence/post-rls/manifest.json`.

Deve consolidar:

1. refs para todos os manifests por apply;
2. ref do handoff pós-RLS;
3. suite RLS final em produção;
4. índice de incidentes e pós-mortems;
5. riscos residuais aceitos;
6. backlog pós-RLS triado;
7. comprovação de desativação do freeze, quando ocorrer.

Campos obrigatórios adicionais:

```json
{
  "handoff_ref": ".github/sec002-handoff/post-rls.md",
  "all_applies_accepted": true,

  "freeze_deactivated": false,

    "expected_asserts": 331,
    "observed_asserts": 331,
    "failures": 0,
    "errors": 0,

  }

```

## 7. Requisitos de integridade

| id | Requisito | Regra |
|----|-----------|-------|
| I1 | Hash obrigatório | todo artifact local exige `sha256` válido |
| I2 | Sem placeholders | nenhum campo pode conter `<...>` |
| I3 | Sem segredos | `contains_secret` deve ser `false` |
| I4 | Sem PII | `contains_pii` deve ser `false` |
| I5 | Retenção mínima | `retain_until >= created_at + 5 anos` |
| I6 | Imutabilidade lógica | correção cria novo artifact, não sobrescreve o anterior |
| I7 | Referências estáveis | refs não podem apontar para ambiente efêmero sem export |

Falha em `I3` ou `I4` bloqueia merge e exige remoção imediata do artefato.

## 10. Validador `scripts/sec002/validate-evidence-archive.mjs` (materialização futura)

Assinatura:

```bash
node scripts/sec002/validate-evidence-archive.mjs --apply-id <id|post-rls> --manifest .github/sec002-evidence/<id>/manifest.json
```

Verificações determinísticas:

1. manifest existe e JSON é válido;
2. `sec002_apply_id` bate com `--apply-id`, exceto `post-rls`;
3. campos obrigatórios presentes;
4. `retain_until >= created_at + 5 anos`;
5. todo artifact local existe;
6. `sha256` calculado bate com manifest;
7. `sanitized=true`, `contains_pii=false`, `contains_secret=false`;
8. evidências mínimas do apply presentes;
9. assert count bate com mapa declarativo (`helpers=15`, `tests=331`, `B=39`, `C=92`, `D=75`, `E=110`);
10. `failures=0` e `errors=0` quando `acceptance=ACCEPTED`;
11. refs de go/no-go, comms e acceptance existem quando aplicável;
12. nenhum campo contém placeholder `<...>`.

Exit codes: `0` válido; `1` inválido com mensagem determinística no stderr.

## 11. Integração com handoff

O handoff pós-RLS só pode entrar em `READY` quando:

1. todos os manifests por apply validarem;
2. `index.md` listar todos os applies;
3. manifest `post-rls` consolidar suite final 331/331;
4. incidentes SEV1/SEV2 estiverem encerrados e referenciados;
5. riscos residuais do handoff tiverem evidência e aceite GM.
