# SEC-001.plan-h — Plano de conciliação `@planifik.local` ↔ `@obraflow.local`

**Onda:** 2 (bloqueada — D-1/D-2 · cutover em pipeline dedicado)
**Data:** 2026-07-12
**Escopo:** apoio à Onda 2 autorizado por D-9. Detalha a recomendação **SEC-001.h** (audit-02 §7): unificar em um único domínio canônico antes do cutover de auth, sem alterar código de produção nesta iteração.

## 1. Problema

Do `SEC-001.audit-02` §2 e §7:

- Rota A (`provision-auth-user`) grava `auth.users.email` = `player.email` real ou `${login}@obraflow.local`.
- Rota B (`sync-player-auth`) grava `${login}@planifik.local`.
- O mesmo `login` PHP pode existir com **dois `auth.users` distintos** — quebra `has_role(auth.uid(), ...)`, quebra RLS, quebra logout unificado.

Cutover (D-1/D-2) exige **1 login PHP ⇔ 1 `auth.users.id`**.

## 2. Domínio canônico

**Decisão proposta:** `@obraflow.local` como domínio de fallback (quando `player.email` real é ausente/ inválido).

Racional:
- Alinha com o nome atual do produto (memória de projeto: "GestãObra"/ObraFlow).
- Rota A já usa `@obraflow.local` — menor superfície de mudança.
- `@planifik.local` é resíduo histórico (produto anterior "Planifik") — só existe em `sync-player-auth`.

**Regra final pós-SEC-001.g (colapso das rotas):**

```
email_canonico(player) =
  player.email                              se player.email é válido e não termina em @obraflow.local
  ${lower(login)}@obraflow.local            caso contrário
```

## 3. Estado esperado no banco (pré-migração)

Query de inventário (a rodar em `SEC-001.mig-01`, **não agora**):

```sql
-- Duplicados por login
select
  split_part(email, '@', 1)                  as login,
  array_agg(email order by created_at)       as emails,
  array_agg(id    order by created_at)       as auth_ids,
  count(*)                                    as n
from auth.users
where email like '%@planifik.local'
   or email like '%@obraflow.local'
group by 1
having count(*) > 1;
```

Três classes de linha esperadas:

| Classe | Condição | Ação na migração |
|--------|----------|------------------|
| **C1 — só `@obraflow.local`** | 1 linha, domínio canônico | nada a fazer |
| **C2 — só `@planifik.local`** | 1 linha, domínio legado | `update auth.users set email = replace(email,'@planifik.local','@obraflow.local')` — preservar `id` |
| **C3 — ambos** | 2 linhas para o mesmo `login` | **merge**: manter o `id` mais antigo (linkado a `profiles`/`user_roles`), migrar FKs do outro, apagar o remanescente |

## 4. Estratégia de merge (C3)

Pré-condições:
- lock exclusivo em `profiles` e `user_roles` do login afetado;
- backup lógico do par (`pg_dump --table auth.users --where ...`) em `SEC-001.mig-01`.

Passos (por login duplicado):

1. `keep_id`  := `min(auth.users.id)` filtrado por `created_at` mais antiga.
2. `drop_id`  := o outro.
3. Reatribuir FKs no schema `public` que apontem para `drop_id`:
   - `profiles.id` → **merge manual** (dois profiles → um) preservando `nome`, `is_gm`, `acessos` com regra "OR" para `is_gm` e união para `acessos`.
   - `user_roles.user_id` → `update ... set user_id = keep_id where user_id = drop_id` seguido de `on conflict do nothing` via unique `(user_id, role)`.
   - qualquer outra tabela com FK para `auth.users.id` (levantar via `pg_catalog` no `SEC-001.mig-01`).
4. `delete from auth.users where id = drop_id`.
5. `update auth.users set email = ${login}@obraflow.local where id = keep_id`.

## 5. Ordem obrigatória vs. SEC-001.g

O merge SÓ é seguro depois que **SEC-001.g** (colapso das duas edge functions em uma) estiver em produção — caso contrário, novas duplicatas surgem entre o merge e o cutover.

Sequência final:

```
SEC-001.g   →  unifica rota cliente + edge function (1 domínio, 1 payload)
SEC-001.h   →  este plano — migração idempotente de conciliação
SEC-001.i   →  remove plaintext password em localStorage.go_player
SEC-001.j   →  substitui api.create("login") por supabase.auth.signInWithPassword
```

## 6. Reversibilidade

- Backup lógico obrigatório antes da migração (`SEC-001.mig-01`).
- Migração deve ser **idempotente**: rodar duas vezes produz o mesmo estado.
- Rollback: restore do dump + revert do deploy que carrega SEC-001.g.

## 7. Fora de escopo desta nota

- Emissão da migração SQL propriamente dita → `SEC-001.mig-01` (próximo audit-changeset).
- Alteração das edge functions → `SEC-001.g` (Onda 2 GO).
- Remoção do `@planifik.local` no cliente → `SEC-001.g`.

## 8. Impacto em produção

**Nenhum.** Apenas documentação. Nenhum arquivo em `src/` ou `supabase/` foi tocado.
