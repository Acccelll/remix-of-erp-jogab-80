# SEC-002.staging-parity-01.spec-01 — Paridade staging↔produção para `SEC-002`

**Onda:** 2 (preparatória — bloqueada por fechamento de `SEC-001`)  
**Data:** 2026-07-12  
**Escopo:** especifica o procedimento formal para garantir que **staging reflete produção** (schema + dados sanitizados + fixtures da suíte) antes do apply de cada lote de `SEC-002`. Sem paridade, a suíte `SEC-002.tests-02.suite` executada em staging não é oráculo confiável para o go/no-go do release-plan §4. Nenhuma migração é aplicada; nenhum código de `src/` ou edge function muda.

## 1. Objetivos

1. Garantir que a suíte `tests-02.suite` executada em staging exercite o **mesmo schema, mesmas policies e mesma volumetria representativa** de produção.
2. Bloquear apply em produção enquanto paridade estiver quebrada.
3. Preservar privacidade: staging **nunca** contém PII de produção sem sanitização.
4. Fornecer artefato reprodutível: qualquer engenheiro deve conseguir recriar o staging usado em um apply passado.

## 2. Definição de "paridade"

Staging é considerado em paridade com produção quando **todos** verdadeiros:

1. **Schema idêntico** — `pg_dump --schema-only` de staging e produção diferem apenas em: nomes de owner, timestamps, e migrations planejadas ainda não aplicadas em produção. Nenhum diff em `CREATE TABLE`, `CREATE POLICY`, `CREATE FUNCTION`, `GRANT`, `INDEX` fora dessa lista.
2. **Volumetria representativa** — para cada tabela do lote a ser testado, `count(*)` em staging ≥ 10 % de produção **e** ≥ 100 linhas (o que for maior), até um teto de 100 k linhas por tabela (para caber na janela de restore).
3. **Fixtures sobrepostas** — as UUIDs canônicas definidas em `SEC-002.tests-02.suite.spec-01` (`E1`, `E2`, `O1`, `O2`, `B1`, `B2`, `C1`, `U1`, `U2`, `UGM`) existem em staging com os vínculos esperados em `user_roles`, `user_empresas`, `obra_membros`, `board_membros`, `card_membros`.
4. **PII sanitizada** — nenhuma coluna listada em §5 contém valor de produção original.
5. **Freshness** — snapshot base ≤ 24 h antes do apply em produção.

## 3. Pipeline de refresh

Job `sec002-staging-refresh`, executado sob demanda pelo DRI:

```text
1. lock: adquire mutex 'sec002-staging' (impede reruns concorrentes)
2. snapshot: pg_dump lógico de produção (schema + data) → objeto no bucket 'observability-sec-002/snapshots/<ts>.dump'
3. restore: pg_restore em staging efêmera (drop + create do schema public)
4. sanitize: executa SQL de §5 (idempotente)
5. seed_fixtures: executa SQL de §6 (idempotente)
6. verify: executa checks de §7; falha ⇒ job vermelho
7. tag: grava metadados em '.github/sec002-staging-parity.json' (§8)
8. release lock
```

Duração-alvo: ≤ 45 min. Se ultrapassar, revisar volumetria §2.2.

## 4. Restrições de dados transferidos

Antes do `pg_dump`:

- **Tabelas excluídas do dump de dados** (schema copiado, dados **não**):
  - `dp_holerite`, `historico_salarial`, `decimo_terceiro`, `fopag_entries`, `provisoes` — dados de folha/remuneração jamais deixam produção.
  - `audit_logs` — não recriado em staging.
- **Colunas mascaradas no dump** (via `--exclude-table-data` combinado com re-seed sintético): não aplicável — mascaramento é feito na etapa de sanitização §5.
- `storage` schema e `auth.users` completos **não** são copiados; §6 recria usuários mínimos.

## 5. Sanitização obrigatória

Após o `pg_restore`, executar em transação única:

```sql
begin;

-- 5.1 profiles: substituir login/nome por valores sintéticos determinísticos
update public.profiles
set login = 'user_' || substr(md5(id::text), 1, 8),
    nome  = 'Staging User ' || substr(md5(id::text), 1, 6);

-- 5.2 colaboradores: mascarar CPF, e-mail, telefone e nome pessoal
update public.colaboradores
set cpf       = lpad((abs(hashtext(id::text)) % 100000000000)::text, 11, '0'),
    email     = 'colab_' || substr(md5(id::text), 1, 8) || '@staging.local',
    telefone  = '+55' || lpad((abs(hashtext(id::text)) % 10000000000)::text, 11, '0'),
    nome      = 'Colab ' || substr(md5(id::text), 1, 6);

-- 5.3 clientes: mascarar CNPJ/razão social
update public.clientes
set cnpj          = lpad((abs(hashtext(id::text)) % 100000000000000)::text, 14, '0'),
    razao_social  = 'Cliente Staging ' || substr(md5(id::text), 1, 6),
    email         = 'cliente_' || substr(md5(id::text), 1, 8) || '@staging.local';

-- 5.4 notas_fiscais: mascarar chave/número
update public.notas_fiscais
set chave_acesso = md5(id::text),
    numero       = substr(md5(id::text), 1, 9);

-- 5.5 solicitacoes_financeiras: manter apenas domínio funcional, mascarar autoria textual
update public.solicitacoes_financeiras
set solicitante = 'user_' || substr(md5(coalesce(solicitante, id::text)), 1, 8),
    criado_por  = 'user_' || substr(md5(coalesce(criado_por,  id::text)), 1, 8),
    aprovado_por = case when aprovado_por is null then null
                        else 'user_' || substr(md5(aprovado_por), 1, 8) end;

-- 5.6 card_comentarios / card_atividades: mascarar texto livre longo
update public.card_comentarios set conteudo = '[staging]';
update public.card_atividades  set detalhe  = '{"staging":true}'::jsonb
  where detalhe is not null;

commit;
```

Nenhum `update` acima é opcional. Cada release do refresh recomputa determinísticamente pelos `id`s — reruns geram mesmos valores, facilitando reprodução.

## 6. Fixtures obrigatórias

Após sanitização, aplicar `supabase/tests/sec-002/_lib/fixtures.sql` (referenciado em `SEC-002.tests-02.suite.spec-01`). Criações mínimas:

- Usuários auth: `U1`, `U2`, `UGM` (via `auth.admin.create_user` em job runner com `service_role`).
- Empresas: `E1`, `E2` em `public.empresas`.
- Obras: `O1` (empresa `E1`), `O2` (empresa `E2`).
- Boards: `B1` (obra `O1`), `B2` (obra `O2`).
- Cards: `C1` no board `B1`.
- Vínculos: `user_empresas(U1,E1)`, `user_empresas(U2,E2)`, `user_roles(UGM,'gm')`, `obra_membros(U1,O1)`, `board_membros(U1,B1)`, `card_membros(U1,C1)`.

Todas idempotentes (`insert ... on conflict do nothing`). Nenhuma fixture usa UUIDs que colidam com dados restaurados (namespace `00000000-0000-0000-0000-0000000000xx`).

## 7. Checklist de verificação (bloqueio automático)

Job `sec002-staging-parity` reprova se qualquer:

- [ ] Diff de schema fora do permitido (§2.1) — usa `migra` ou `pg_dump --schema-only | diff`.
- [ ] Alguma tabela do lote alvo com `count(*)` abaixo do mínimo §2.2.
- [ ] Alguma coluna sanitizada §5 contendo valor original (checagem heurística: nenhum `login` sem prefixo `user_`, nenhum CPF fora do padrão determinístico, etc.).
- [ ] Alguma fixture §6 ausente.
- [ ] Snapshot mais antigo que 24 h (§2.5).
- [ ] Suíte `SEC-002.tests-02.suite/helpers/*` **vermelha** em staging pós-refresh (sanity: se helpers falham, staging não serve para o lote).

Saída do job: `sec002-staging-parity-<ts>.log` + atualização de §8.

## 8. Metadado versionado

`.github/sec002-staging-parity.json`:

```json
{
  "last_refresh_at": "<iso8601>",
  "snapshot_id": "<uuid do dump>",
  "schema_diff_hash": "<sha256>",
  "row_counts": { "<tabela>": <n>, ... },
  "fixtures_ok": true,
  "helpers_suite_pass": true,
  "current_batch": "B" | "C" | "D" | "E" | "none"
}
```

CI do PR de apply em produção lê este arquivo e reprova se:

- `last_refresh_at` > 24 h antes do apply.
- `fixtures_ok=false` ou `helpers_suite_pass=false`.
- `current_batch` não corresponde ao lote sendo aplicado.

## 9. Interação com o freeze

`sec002-staging-refresh` é **permitido durante o freeze** — não altera schema de produção; apenas espelha em staging. Mudanças no próprio script de refresh seguem freeze §2 se envolverem SQL de `public` — na prática, edições ficam confinadas a `supabase/tests/sec-002/**` e ao job CI, ambos fora do freeze.

## 10. Rotina por lote

Antes de abrir o PR de apply de cada lote:

1. DRI dispara `sec002-staging-refresh`.
2. DRI dispara `sec002-tests-suite` contra staging pós-refresh (subconjunto: `helpers/` + lote alvo).
3. Se ambos verdes, abre PR de apply em produção citando `snapshot_id` de §8 no corpo.
4. CI do PR revalida §8 (freshness + fixtures_ok).
5. Após apply em produção, DRI dispara **novo refresh** para começar a janela de 24 h com staging já alinhado ao novo estado.

## 11. Invariantes do documento

- [ ] Nenhum dado de PII de produção em staging (§5 exaustiva).
- [ ] Tabelas §4 nunca têm dados copiados.
- [ ] Suíte `helpers/` sempre verde em staging antes do primeiro apply do lote.
- [ ] `snapshot_id` reproduzível (dump preservado ≥ 30 dias no bucket).
- [ ] Nenhuma alteração em `public` neste changeset.
- [ ] Refresh não altera produção — direção é sempre prod → staging.

## 12. Impacto em produção

**Nenhum neste changeset.** Documento de especificação de procedimento. A instrumentação real (job CI, script de sanitização, bucket) é entregue por PR de operação separado, consumindo esta spec como contrato.
