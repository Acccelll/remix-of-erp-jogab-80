# SEC-002.batch-B.migration.spec-01 — Migração executável do Lote B

**Onda:** 2 (preparatória — bloqueada por fechamento de `SEC-001` e por `SEC-002.helpers-02.migration`)
**Data:** 2026-07-12
**Escopo:** especifica o **arquivo SQL executável** `supabase/migrations/<ts>_sec_002_batch_b.sql` que materializa as políticas-alvo descritas em `SEC-002.batch-B.spec-01` para as **13 tabelas registry/transversal**. Este changeset é **apenas especificação do arquivo de migração** — nada é aplicado ao banco, nada em `src/` ou edge functions muda. É o **segundo artefato executável** de `SEC-002` (o primeiro é `SEC-002.helpers-02.migration`).

## 2. Pré-requisitos duros (gate do PR)

Aplica só se todos verdadeiros:

1. `SEC-001` release train R1–R10 concluído.
2. `SEC-002.helpers-02.migration` **aplicada** — as 4 funções `user_in_*` existem (não são consumidas por este lote, mas o release train impõe ordem).
3. `SEC-002.tests-02.suite/helpers/*` **verde** em staging.
4. `SEC-002.tests-02.suite/batch-B/*` **verde** em staging contra este mesmo arquivo (39/39 asserts PASS).
5. Snapshot lógico do banco criado ≤ 1 h antes do apply (runbook `SEC-001.backup-01`, reutilizado).
6. Nenhuma policy de `batch-C/D/E` em produção — ordem canônica B → C → D → E.

Se qualquer item falhar, PR fechado sem merge.

## 3. Estrutura do arquivo

Uma transação. Ordem estrita por tabela, com todas as 13 tabelas no mesmo `begin/commit`:

```text
begin;
  -- para cada tabela (§6 do batch-B.spec-01):
  --   1. drop policy if exists <policy_atual_n> on public.<tabela>;  (todas as atuais)
  --   2. create policy "<tabela>_select_..."  on public.<tabela> ... ;
  --   3. create policy "<tabela>_write_..."   on public.<tabela> ... ;
  --   4. alter  table  public.<tabela> enable row level security;
  --   5. revoke all on public.<tabela> from anon;
  --   6. grant  select, insert, update, delete on public.<tabela> to authenticated;
  --   7. grant  all on public.<tabela> to service_role;
commit;
```

Transação única (§5 de `batch-B.spec-01`). Sem `commit` intermediário — falha em qualquer tabela reverte o lote inteiro.

## 4. Fonte canônica do SQL de policies

Cópia literal dos padrões §3 e do mapeamento §6 de `SEC-002.batch-B.spec-01`. Qualquer divergência de nome de policy, `USING`, `WITH CHECK`, `to authenticated`, `for all/select`, ou par de grants é bug do arquivo e reprova no gate.

## 5. Enumeração das policies atuais para `drop policy if exists`

O PR de execução obriga, **antes de escrever o SQL**, uma extração literal da lista de policies vigente por tabela via:

```sql
select tablename, policyname
from   pg_policies
where  schemaname = 'public'
  and  tablename in (<13 tabelas>)
order  by tablename, policyname;
```

O resultado alimenta o bloco `drop policy if exists "<policyname>" on public.<tabela>;` para cada linha. `if exists` mantém idempotência.

## 6. Grants finais (repetição obrigatória por tabela)

Bloco padrão de `batch-B.spec-01` §8 aplicado às **13** tabelas:

```sql
revoke all      on public.<tabela> from anon;
grant  select,insert,update,delete on public.<tabela> to authenticated;
grant  all      on public.<tabela> to service_role;
```

Exceções nominais (validadas contra §7 de `batch-B.spec-01`):

- `public.notificacoes`: mantém 3 policies (não 4) porque `DELETE` é bloqueado por padrão (`for all` cobre insert/update; select separado; delete ausente).
- `public.user_roles`: mantém 1 policy única (`select` via `has_role` / `current_is_gm`); `INSERT/UPDATE/DELETE` **somente `service_role`**, sem grant a `authenticated`. Ajuste do grant:

  ```sql
  revoke all on public.user_roles from anon;
  grant  select on public.user_roles to authenticated;
  grant  all   on public.user_roles to service_role;
  ```

Nenhum `grant` a `anon` em qualquer tabela do lote.

## 7. Verificações pós-migração (obrigatórias no gate)

Após `commit`, executar em janela read-only:

```sql
-- 7.1 RLS habilitado nas 13 tabelas
select relname, relrowsecurity
from   pg_class
where  relnamespace = 'public'::regnamespace
  and  relname in (<13 tabelas>);
-- oráculo: relrowsecurity = true em todas

-- 7.2 Contagem de policies bate com §6 do batch-B.spec-01
select tablename, count(*) as n_policies
from   pg_policies
where  schemaname='public' and tablename in (<13 tabelas>)
group  by tablename
order  by tablename;
-- oráculo: bate com a coluna "N policies" do §6

-- 7.3 anon sem privilégio de DML em nenhuma das 13
select table_name, privilege_type
from   information_schema.role_table_grants
where  table_schema='public'
  and  grantee='anon'
  and  table_name in (<13 tabelas>);
-- oráculo: 0 linhas

-- 7.4 authenticated tem os 4 privilégios (exceto user_roles: só SELECT)
select table_name, string_agg(privilege_type, ',' order by privilege_type)
from   information_schema.role_table_grants
where  table_schema='public'
  and  grantee='authenticated'
  and  table_name in (<13 tabelas>)
group  by table_name;
-- oráculo: 'DELETE,INSERT,SELECT,UPDATE' em 12 tabelas; 'SELECT' em user_roles
```

Qualquer discrepância aborta o release e dispara o rollback §8.

## 8. Rollback

Companion `SEC-002.batch-B.rollback.sql`, executável em transação única:

```sql
begin;
  -- para cada tabela do lote:
  drop policy if exists "<tabela>_select_..." on public.<tabela>;
  drop policy if exists "<tabela>_write_..."  on public.<tabela>;

  -- recria a policy legada permissiva (baseline do inventário-02):
  create policy "<tabela>_authenticated_all"
    on public.<tabela>
    for all
    to authenticated
    using (true)
    with check (true);
commit;
```

Grants **não** são revertidos — permanecem coerentes com o esquema atual. Rollback só é seguro se `batch-C/D/E` ainda não tiverem sido aplicados.

## 10. Riscos

- **R1: policy legada com nome desconhecido não é dropada.** Mitigação: extração §5 é obrigatória no PR; a ausência de matches no `drop` seria caught pelo teste `outsider` (linhas antigas ainda visíveis).
- **R2: `user_roles` sem grant `INSERT` quebra fluxo de bootstrap de novo usuário.** Mitigação: bootstrap ocorre via `handle_new_user` trigger (`security definer`) que roda como `postgres`; não depende de grant a `authenticated`. Confirmar no gate.
- **R3: `notificacoes` mantém 3 policies e a suíte espera 4.** Mitigação: `_lib/test_ids.txt` documenta contagem esperada por tabela; assert §7.2 usa mapa nominal, não valor único.
- **R4: PostgREST cacheia policies antigas.** Mitigação: `notify pgrst, 'reload schema';` no final da migração.
