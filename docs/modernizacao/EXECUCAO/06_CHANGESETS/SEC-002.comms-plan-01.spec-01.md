# SEC-002.comms-plan-01.spec-01 — Plano formal de comunicação

**Onda:** 2 (bloqueada — depende de fechamento de `SEC-001`)  
**Data:** 2026-07-12  
**Tipo:** especificação (contrato) — **nenhum código de produção alterado**  
**Depende de:** `SEC-002.release-plan-01`, `SEC-002.observability-01.spec-01`, `SEC-002.freeze-policy-01.spec-01`, `SEC-002.staging-parity-01.spec-01`, `SEC-002.pr-checklist-01.spec-01`, `SEC-002.apply-template-01.spec-01`, `SEC-002.go-no-go-01.spec-01`, `SEC-002.incident-runbook-01.spec-01`  
**Materializa:** `docs/runbooks/sec-002-comms.md` + `.github/sec002-comms/<apply-id>.md` + `scripts/sec002/validate-comms-log.mjs`

## 1. Objetivo

Definir, de forma determinística, como comunicar cada apply `SEC-002` (`helpers-02`, `tests-02-suite`, `batch-B/C/D/E`) antes, durante e depois da janela de execução. O plano consolida:

1. audiências obrigatórias e canais oficiais;
2. cadência mínima `T-24h`, `T-1h`, `T+0`, `T+1h`, `T+24h`;
3. templates por estado (`GO`, `HOLD`, `ROLLBACK`, `ERRATA`, `INCIDENT`);
4. matriz RACI de comunicação;
5. registro auditável em `.github/sec002-comms/<apply-id>.md`;
6. validação CI para impedir apply sem comunicação mínima.

Sem registro de comunicação válido, o PR de apply `SEC-002` **não** pode ser mergeado.

## 2. Fora de escopo

- Alterar políticas RLS, migrações, código de produção, funções edge ou dashboards.
- Definir canal corporativo fora do escopo `SEC-002`.
- Substituir o runbook de incidente; este plano apenas define comunicação e escalonamento.

## 3. Audiências obrigatórias

| Audiência | Objetivo da comunicação | Canal oficial | Obrigatório em |
|-----------|--------------------------|---------------|----------------|
| GM (Cappucceno) | aprovação, risco residual, decisão final | `#sec-002-exec` + registro no PR | `GO`, `HOLD`, `ROLLBACK`, `INCIDENT` |
| Ops / Plataforma | execução técnica, freeze, rollback, staging parity | `#sec-002-ops` | todos os estados |
| DRI testes | suíte RLS, asserts esperados, evidências | `#sec-002-tests` | `GO`, `HOLD`, `ROLLBACK`, `INCIDENT` |
| DRI observabilidade | dashboards, alertas, anomalias pós-apply | `#sec-002-ops` | `GO`, `INCIDENT` |
| Usuários impactados | aviso operacional sem detalhes técnicos sensíveis | canal interno operacional | `GO`, `ROLLBACK`, `INCIDENT` |

Regra: nenhuma mensagem para usuários impactados pode expor nomes de tabelas sensíveis, PII, chaves, URLs internas ou detalhes de RLS falso-permissivo.

## 4. Cadência mínima

| Marco | Quando | Conteúdo mínimo | Responsável | Evidência |
|-------|--------|-----------------|-------------|-----------|
| `T-24h` | 24 h antes da janela | lote, janela, risco, plano de rollback, freeze ativo | Comms | link mensagem |
| `T-1h` | 1 h antes | confirmação go/no-go, staging parity, suíte staging, contatos de plantão | Comms + DRI técnico | link mensagem |
| `T+0` | início do apply | início efetivo, apply-id, executor, status do freeze | IC/Comms | link mensagem |
| `T+1h` | 1 h após apply | resultado, métricas iniciais, suíte prod, pendências | Comms + observabilidade | link mensagem + dashboard |
| `T+24h` | 24 h após apply | encerramento da janela, incidentes, decisão de avançar/hold | Comms + GM | link mensagem + decisão |

Se `decision=HOLD`, `ROLLBACK`, `ERRATA` ou `INCIDENT`, comunicar imediatamente no canal executivo e registrar a causa em até 15 min.

## 5. Templates canônicos

Todos os templates devem preservar `apply_id`, `decision`, `window`, `owner` e `next_update_at`.

### 5.1 `GO`

```text
[SEC-002][GO][<apply_id>]
Janela: <inicio> → <fim>
Escopo: <helpers-02|tests-02-suite|batch-B|batch-C|batch-D|batch-E>
Evidências: staging parity <ref>, suíte RLS <ref>, go/no-go <ref>
Rollback: <ref>
Freeze: ativo
Próxima atualização: <ISO8601>
Owner: <github-login>
```

### 5.2 `HOLD`

```text
[SEC-002][HOLD][<apply_id>]
Motivo: <critério G*/H*/T*/B*/C*/D*/E* ausente ou falho>
Impacto: apply bloqueado, sem alteração produtiva
Ação corretiva: <descrição curta>
Próxima reavaliação: <ISO8601>
Owner: <github-login>
```

### 5.3 `ROLLBACK`

```text
[SEC-002][ROLLBACK][<apply_id>]
Motivo: <referência ao incidente ou falha>
Rollback SQL: <ref>
Verificação: suíte prod <ref>, pg_policies baseline <ref>
Status: <em execução|mitigado|encerrado>
Próxima atualização: <ISO8601>
Owner: <github-login>
```

### 5.4 `ERRATA`

```text
[SEC-002][ERRATA][<apply_id>]
Tipo: docs-only
Motivo: <correção textual/contratual>
Sem migração: confirmado
Validador: changed-files docs-only <ref>
Owner: <github-login>
```

### 5.5 `INCIDENT`

```text
[SEC-002][INCIDENT][<incident_id>][<SEV1|SEV2|SEV3>]
Apply: <apply_id>
Gatilho: <trigger-key>
Decisão inicial: <ROLLBACK|HOTFIX|OBSERVE>
IC: <github-login>
Próxima atualização: <ISO8601, máximo +15 min para SEV1/SEV2>
Runbook: <incident ref>
```

## 6. Registro auditável

Arquivo: `.github/sec002-comms/<apply-id>.md`.

Formato obrigatório:

```yaml
---
sec002_apply_id: <helpers-02|tests-02-suite|batch-B|batch-C|batch-D|batch-E>
decision_ref: .github/sec002-go-no-go/<apply-id>.md
comms_owner: <github-login>
window:
  starts_at: <ISO8601 UTC>
  ends_at: <ISO8601 UTC>
channels:
  exec: <url>
  ops: <url>
  tests: <url|null>
  users: <url|null>
events:
  T-24h: { sent_at: <ISO8601>, channel: <exec|ops|users>, ref: <url>, template: GO|HOLD|ROLLBACK|ERRATA|INCIDENT }
  T-1h: { sent_at: <ISO8601>, channel: <exec|ops>, ref: <url>, template: GO|HOLD|ROLLBACK|ERRATA|INCIDENT }
  T+0: { sent_at: <ISO8601>, channel: <ops>, ref: <url>, template: GO|HOLD|ROLLBACK|ERRATA|INCIDENT }
  T+1h: { sent_at: <ISO8601>, channel: <exec|ops>, ref: <url>, template: GO|HOLD|ROLLBACK|ERRATA|INCIDENT }
  T+24h: { sent_at: <ISO8601>, channel: <exec|ops|users>, ref: <url>, template: GO|HOLD|ROLLBACK|ERRATA|INCIDENT }
exceptions: []
approved_by:
  dri_technical: <github-login>
  gm: <github-login>
---
```

Regras:

1. `T-24h`, `T-1h`, `T+0`, `T+1h`, `T+24h` são obrigatórios para `decision=GO`.
2. `HOLD` antes do apply exige ao menos `T-24h` ou `T-1h` com motivo explícito.
3. `ROLLBACK` e `INCIDENT` exigem evento adicional em `exceptions[]` com `incident_id`.
4. `approved_by.gm` obrigatório para mensagens que liberam avanço de lote.
5. O arquivo é append-only: correções entram em `exceptions[]`, não removem eventos passados.

## 7. Matriz RACI

| Atividade | R | A | C | I |
|-----------|---|---|---|---|
| Redigir mensagens `GO`/`HOLD` | Comms | DRI técnico | Ops, testes | GM |
| Comunicar usuários impactados | Comms | GM | DRI técnico | Ops |
| Comunicar início/fim de apply | IC | DRI técnico | Ops | GM |
| Comunicar incidente | IC + Comms | GM | Ops, observabilidade | usuários impactados |
| Registrar `.github/sec002-comms` | Comms | DRI técnico | CI | GM |
| Encerrar janela T+24h | Comms | GM | DRI observabilidade | todos |

R = Responsible, A = Accountable, C = Consulted, I = Informed.

## 8. Validador `scripts/sec002/validate-comms-log.mjs` (materialização futura)

Assinatura:

```bash
node scripts/sec002/validate-comms-log.mjs --apply-id <id> --file .github/sec002-comms/<id>.md
```

Verificações determinísticas:

1. arquivo existe e frontmatter YAML é válido;
2. `sec002_apply_id` = argumento `--apply-id`;
3. `decision_ref` existe e aponta para o mesmo `apply-id`;
4. eventos obrigatórios existem conforme decisão;
5. `sent_at` respeita ordem temporal (`T-24h ≤ T-1h ≤ T+0 ≤ T+1h ≤ T+24h` quando aplicável);
6. cada evento possui `ref` não vazio;
7. `template ∈ {GO,HOLD,ROLLBACK,ERRATA,INCIDENT}`;
8. `approved_by.gm` presente quando `decision=GO`;
9. `ROLLBACK`/`INCIDENT` exigem `exceptions[].incident_id`;
10. nenhum campo contém placeholder `<...>`.

Exit codes: `0` válido; `1` inválido com mensagem determinística no stderr.

## 9. Integração com CI

`sec002-pr-checklist` ganha step após `validate-go-no-go`:

```yaml
- name: Validate communications log
  run: node scripts/sec002/validate-comms-log.mjs --apply-id "${{ steps.parse.outputs.apply_id }}" --file ".github/sec002-comms/${{ steps.parse.outputs.apply_id }}.md"
```

Ordem final dos gates:

1. `validate-pr-checklist`
2. `validate-changed-files`
3. `validate-staging-parity`
4. `validate-go-no-go`
5. `validate-comms-log`
6. `sec002-freeze-guard`
7. `sec-002-tests`

Falha em comunicação mínima → merge bloqueado.

## 10. Exceções controladas

Exceções são permitidas apenas quando:

1. janela emergencial aprovada por GM;
2. incidente SEV1 exige rollback/hotfix imediato;
3. canal oficial indisponível.

Toda exceção deve registrar:

```yaml
exceptions:
  - at: <ISO8601>
    type: <emergency|incident|channel_unavailable>
    approved_by: <github-login>
    reason: <texto>
    replacement_channel: <url|null>
```
