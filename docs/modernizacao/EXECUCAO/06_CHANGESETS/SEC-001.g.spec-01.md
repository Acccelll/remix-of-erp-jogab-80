# SEC-001.g.spec-01 — Especificação do colapso das rotas de auth

**Onda:** 2 (bloqueada — D-1/D-2 · cutover em pipeline dedicado)
**Data:** 2026-07-12
**Escopo:** apoio à Onda 2 autorizado por D-9. Especifica a implementação futura de **SEC-001.g** (audit-02 §7): uma única rota cliente + uma única edge function para sincronização PHP↔Cloud. **Nenhum código de produção é alterado neste changeset.**

## 1. Estado atual (recap de `SEC-001.audit-02`)

| Rota | Cliente | Edge function | Email | Payload |
|------|---------|---------------|-------|---------|
| A | `ensureCloudSession` (`src/lib/auth/ensureCloudSession.ts`) | `provision-auth-user` | real ou `@obraflow.local` | `{login,email,password,is_gm,acessos}` |
| B | `ensureSupabaseSession` (inline em `AppContext.tsx:353-376`) | `sync-player-auth` | `@planifik.local` | `{login,senha}` |

Consequência: duplicatas em `auth.users`, RBAC inconsistente, RLS quebrada silenciosamente.

## 2. Estado alvo

**Uma única rota:** `ensureCloudSession(player, password)` → edge function `provision-auth-user`.

- Domínio canônico: `@obraflow.local` (ver `SEC-001.plan-h §2`).
- Payload único: `{login, email, password, is_gm, acessos, nome}`.
- Retorno único: `{ok: true, user_id}` ou `{ok:false, code, message}`.
- Rate-limit e allowlist centralizados na edge function (audit-01 §5).

## 3. Mudanças de código previstas

### 3.1 `src/lib/auth/ensureCloudSession.ts`

- Assinatura passa a exigir `password` (hoje já exige; manter).
- Após provisionamento OK, chamar `supabase.auth.signInWithPassword({email, password})` para hidratar sessão. Hoje só provisiona — quem loga é o caller.
- Retornar `{userId, session}` para o caller decidir se persiste.

### 3.2 `src/contexts/AppContext.tsx`

Remover integralmente:

- `ensureSupabaseSession` (linhas ~353-376);
- chamada em `login` (linha ~405);
- chamada em hydrate de reload (linha ~311).

Substituir por chamada única a `ensureCloudSession` recebendo `player` + `password` do fluxo PHP.

### 3.3 `src/contexts/EmpresaContext.tsx`

Nenhuma mudança de API — continua chamando `ensureCloudSession(currentPlayer)`. Como a sessão já está hidratada pelo `AppContext`, o helper deve virar **no-op quando `supabase.auth.getSession()` retornar sessão válida** (evita chamada redundante à edge function).

### 3.4 `supabase/functions/sync-player-auth/`

**Deprecar e remover** após 1 release de convivência com log de "chamada residual" (para pegar clientes cacheados). Cronograma:

- Release N: edge function retorna `410 Gone` com header `X-Deprecated: use provision-auth-user`; incrementa métrica.
- Release N+1: `supabase--delete_edge_functions` da função.

### 3.5 `supabase/functions/provision-auth-user/`

Aplicar recomendações pendentes de `SEC-001.audit-01`:

- SEC-001.a — email real do cliente sempre que válido;
- SEC-001.b — gravar `is_gm`/`acessos` no `raw_user_meta_data` para o trigger `handle_new_user`;
- SEC-001.c — unificar CORS via `../_shared/cors.ts`;
- SEC-001.d — exigir prova de login PHP (token opaco de 60s emitido pelo PHP) além de senha;
- SEC-001.e — rate-limit por IP+login (10/min);
- SEC-001.f — paginar `listUsers` ou usar `getUserByEmail`.

## 4. Invariantes que devem se manter

1. `player.isGM === has_role(auth.uid(), 'gm')` para todo `currentPlayer` hidratado.
2. `currentPlayer` só é definido após `supabase.auth.getSession()` retornar sessão não-nula (elimina fire-and-forget do audit-02 §3).
3. Um `login` PHP ⇒ no máximo um `auth.users.id` (garantido por §3.4 + `SEC-001.mig-01`).
4. Nenhuma referência textual a `@planifik.local` em `src/`, `supabase/functions/` ou `docs/` (fora do histórico dos audits).
