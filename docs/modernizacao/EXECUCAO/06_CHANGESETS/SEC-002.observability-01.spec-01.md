# SEC-002.observability-01.spec-01 — Observabilidade obrigatória de `SEC-002`

**Onda:** 2 (preparatória — bloqueada por fechamento de `SEC-001`)  
**Data:** 2026-07-12  
**Escopo:** especifica os **dashboards, métricas, alertas e execuções periódicas** que instrumentam as janelas T+0 / T+1 h / T+24 h definidas em `SEC-002.release-plan-01` §3. Nenhuma migração é aplicada; nenhum código de `src/` ou edge function muda. Este documento é pré-requisito para abrir o PR de `SEC-002.helpers-02.migration`.

## 1. Objetivos

1. Detectar regressão RLS (erro `42501` em rota legítima) em ≤ 5 min.
2. Detectar degradação de latência de queries listadas em §11.R1 dos specs de cada lote em ≤ 10 min.
3. Fornecer evidência quantitativa para o go/no-go de 24 h (§4 do release-plan-01).
4. Rodar a suíte `SEC-002.tests-02.suite` contra produção em janela dedicada, sem afetar usuários.

## 2. Fontes de dados

| Sinal | Fonte | Retenção mínima |
|-------|-------|-----------------|
| Erros PostgREST por rota | `edge_function_logs` + logs do PostgREST no projeto Cloud | 30 dias |
| Latência de query | `pg_stat_statements` (habilitado no projeto) | rolling 7 dias |
| Contagem de policies e RLS habilitada | `pg_policies`, `pg_class.relrowsecurity` — coletado por job periódico | snapshot diário, 90 dias |
| Contagem de cards órfãos | query §5.3 abaixo | snapshot horário, 30 dias |
| Resultado da suíte em produção | artefato do job CI `sec-002-tests-prod` | 90 dias |

Nenhuma dessas coletas exige nova tabela em `public`. Snapshots são gravados em bucket dedicado `observability-sec-002` (schema `storage`, criado apenas se necessário e fora deste changeset).

## 3. Métricas obrigatórias

### 3.1 `sec002_rls_denied_total`

- **Definição:** contagem de respostas PostgREST com `code=42501` por (`rota`, `role`, `lote_ativo`).
- **Labels:** `route` (path REST), `role` (`anon` | `authenticated`), `batch` (`B` | `C` | `D` | `E` | `none`).
- **Fonte:** parser dos logs do PostgREST.
- **Alerta:** `> 5` eventos com `role='authenticated'` em janela de 10 min ⇒ **crítico** (dispara rollback §6 do release-plan).

### 3.2 `sec002_query_p95_ms`

- **Definição:** p95 de `mean_exec_time` de `pg_stat_statements` para o conjunto de queries listado por lote em §5.2.
- **Labels:** `query_id`, `batch`.
- **Alerta:** `p95 > 1.3× baseline` por 15 min ⇒ **warning**; `> 3× baseline` por 5 min ⇒ **crítico**.

### 3.3 `sec002_policy_drift`

- **Definição:** diff entre a contagem esperada de policies por tabela (§8.2 dos specs de cada batch) e a contagem observada em `pg_policies`.
- **Alerta:** qualquer valor `≠ 0` ⇒ **crítico** (indica ALTER manual ou rollback parcial).

### 3.4 `sec002_rls_disabled_total`

- **Definição:** número de tabelas em `public` com `relrowsecurity = false` que deveriam estar em `true` conforme o lote ativo.
- **Alerta:** `> 0` ⇒ **crítico**.

### 3.5 `sec002_orphan_cards_total`

- **Definição:** cards sem `card_board_posicao` e sem `card_membros`. Cobre risco R2 de `batch-E`.
- **Alerta:** crescimento `> 5%` em 24 h ⇒ **warning**.

### 3.6 `sec002_suite_pass_ratio`

- **Definição:** asserts PASS / asserts totais do último run da suíte contra produção.
- **Alerta:** `< 1.0` ⇒ **crítico**.

## 5. Queries de referência

### 5.1 Erros RLS por rota (últimos 10 min)

```sql
select route, count(*) as n
from   observability.postgrest_errors
where  code = '42501'
  and  role_name = 'authenticated'
  and  occurred_at > now() - interval '10 minutes'
group  by route
order  by n desc;
```

### 5.2 p95 por lote

Cada batch declara em errata deste documento (`SEC-002.observability-01.baseline-<batch>.md`) as `queryid` de `pg_stat_statements` a monitorar. Conjunto mínimo obrigatório:

| Lote | Queries mínimas |
|------|-----------------|
| B | `select ... from public.profiles`, `select ... from public.user_roles`, `select ... from public.empresas` |
| C | `select ... from public.obras`, `select ... from public.cronograma_itens`, `select ... from public.medicoes` |
| D | `select ... from public.financeiro_lancamentos`, `select ... from public.notas_fiscais`, `select ... from public.solicitacoes_financeiras` |
| E | `select ... from public.cards`, `select ... from public.card_board_posicao`, `select ... from public.card_membros` |

### 5.3 Cards órfãos

```sql
select count(*) as orfaos
from   public.cards c
where  not exists (select 1 from public.card_board_posicao p where p.card_id = c.id)
  and  not exists (select 1 from public.card_membros m where m.card_id = c.id);
```

### 5.4 Drift de policies

```sql
with esperado(tablename, n) as (
  values
    ('profiles', 2), ('user_roles', 1),
    -- ... (populado pelo job com base no lote ativo)
    ('cards', 4)
),
observado as (
  select tablename, count(*)::int as n
  from   pg_policies
  where  schemaname = 'public'
  group  by tablename
)
select e.tablename, e.n as esperado, coalesce(o.n, 0) as observado
from   esperado e
left   join observado o using (tablename)
where  coalesce(o.n, 0) <> e.n;
```

## 6. Execução periódica da suíte em produção

Job CI dedicado `sec002-tests-prod`, agendado:

- **T+15 min após qualquer apply** de lote (disparo manual pelo DRI).
- **A cada 6 h** durante a janela de 24 h do lote.
- **Diariamente às 03:00 UTC** enquanto `SEC-002` estiver ativa.

Configuração:

- Conecta com `service_role` em janela isolada, timeout 5 min.
- Executa apenas o subconjunto `helpers/` + lotes já aplicados (nunca lotes futuros).
- Artefato de saída: `sec002-tests-prod-<ts>.log` com contagem `-- OK:` por assert.
- Falha ⇒ alerta crítico e bloqueio automático de novos deploys em produção via feature flag `sec002_freeze`.

## 7. Alertas — matriz de destino

| Severidade | Canal | Ação esperada |
|------------|-------|---------------|
| **crítico** | `#incidentes` (menciona DRI de plantão) | seguir runbook §6 do release-plan-01 |
| **warning** | `#observability-sec002` | investigação em ≤ 1 h; decisão de manter, criar errata ou promover a crítico |
| **info** | `#observability-sec002` (silencioso fora de janela de apply) | contexto para o post-mortem |

Nenhum alerta é enviado a canais públicos de usuários.

## 8. Congelamento pós-apply

Enquanto `sec002_rls_denied_total` com `role='authenticated'` for `> 0` na última hora após um apply:

- Novo deploy de `src/` bloqueado (feature flag `sec002_freeze = true`).
- Novo apply de lote seguinte bloqueado, independentemente do timer de 24 h.

O flag só é liberado por decisão explícita do DRI (§5 do release-plan) com registro no canal `#incidentes`.

## 9. Handoff pós-`SEC-002`

Após `batch-E` estável por 24 h com todos os alertas verdes:

1. Dashboard **SEC-002 — Release** é arquivado como `SEC-002 — Release (histórico)`.
2. Métricas `sec002_rls_denied_total` e `sec002_policy_drift` migram para o dashboard permanente `RLS — Produção`, mantidas indefinidamente.
3. `sec002_query_p95_ms` mantém as queries do §5.2 no dashboard permanente de performance; baseline atualizada para pós-migração.
4. `sec002_orphan_cards_total` continua monitorado até resolução formal em `SEC-003`.
5. Job `sec002-tests-prod` reduz frequência para semanal e é renomeado `rls-tests-prod`.
