# SEC-002.tests-02.suite.spec-01 — Spec da suíte executável de testes RLS

**Onda:** 2 (preparatória — bloqueada por fechamento de `SEC-001`)
**Data:** 2026-07-12
**Escopo:** especifica o **layout, runner, fixtures e oráculos** do artefato executável `SEC-002.tests-02.suite/`, que operacionaliza os 15 asserts de helpers (`SEC-002.helpers-01` §6) e os 331 asserts globais por lote (B=39, C=92, D=75, E=110, H=15) enumerados em `SEC-002.tests-01` e reconciliados em `SEC-002.batch-D.spec-01` §9. **Nada é executado aqui**, nada em `src/` ou `supabase/` muda; este documento define o **contrato do diretório de testes** que os PRs subsequentes materializarão.

## 1. Localização e layout do diretório

```text
supabase/tests/sec-002/
├── README.md                       # aponta para este spec
├── _lib/
│   ├── fixtures.sql                # seeds determinísticos §5 (UUIDs canônicos)
│   ├── jwt.sql                     # helpers set local role/claims (§1.2 tests-01)
│   ├── assert.sql                  # macros assert_rows / assert_denied / assert_bool
│   └── teardown.sql                # rollback explícito + limpeza de user_roles
├── helpers/
│   ├── user_in_empresa.sql         # 3 casos
│   ├── user_in_obra.sql            # 3 casos
│   ├── user_in_board.sql           # 4 casos
│   └── user_in_card.sql            # 5 casos
├── batch-B/                        # 13 tabelas × 3 casos = 39 asserts
│   └── <tabela>.sql                # um arquivo por tabela
├── batch-C/                        # 23 tabelas × 4 casos = 92 asserts
│   └── <tabela>.sql
├── batch-D/                        # 15 tabelas × 5 casos = 75 asserts
│   └── <tabela>.sql
└── batch-E/                        # 22 tabelas × 5 casos = 110 asserts
    └── <tabela>.sql
```

Total: **5 + 4 + 73 = 82 arquivos** de teste + runner.

## 2. Runner

- Ferramenta: `psql -v ON_ERROR_STOP=1` executando arquivos em ordem alfabética por subpasta, orquestrado por `scripts/db/run-sec-002-tests.sh` (novo, escopo do PR de execução; contrato definido aqui).
- Alvo: banco de **staging** ou preview do PR — **nunca** produção.
- Precondições verificadas pelo runner antes do primeiro assert:
  1. `SEC-002.helpers-02.migration` aplicada (verifica `pg_proc` §7.1 de `helpers-02.spec-01`).
  2. Migração do lote sob teste aplicada (verifica presença de policy-alvo por `pg_policies`).
  3. Extensão `pgcrypto` disponível (para `gen_random_uuid` em fixtures dinâmicas, quando necessário).
- Saída: código 0 se **todos** os asserts passam; ≠0 no primeiro `raise exception`.
- Log: cada arquivo imprime `-- OK: <test_id>` por assert bem-sucedido; falha aborta a suíte inteira.

Nenhuma extensão externa (pgTAP, plpgsql_check) é exigida — o padrão de assert é `do $$ begin if not (<cond>) then raise exception '<test_id> failed: <detalhe>'; end if; end $$;`, herdado de `SEC-002.tests-01` §1.3.

## 3. Ordem de execução

Estrita, imposta pelo runner:

```text
1. helpers/*                        # pré-condição semântica dos lotes
2. batch-B/*                        # registry (menor blast radius)
3. batch-C/*                        # obras/operação
4. batch-D/*                        # dp/financeiro
5. batch-E/*                        # boards/cards (maior superfície)
```

Se `helpers/` falha, os lotes não rodam. Se um lote falha, os posteriores não rodam.

## 4. Estrutura padrão de arquivo de teste

Herdada de `SEC-002.tests-01` §1.3, formalizada aqui:

```sql
-- test_id: SEC-002.T-<lote>-<slug>-<caso>
begin;
  \i _lib/fixtures.sql              -- seeds canônicos §5
  \i _lib/jwt.sql

  -- ATO
  select set_jwt_user('<uuid_do_papel>');   -- ou set_jwt_anon()

  -- ORÁCULO
  do $$
  declare v_count int;
  begin
    select count(*) into v_count
    from public.<tabela>
    where <predicado_do_caso>;
    if v_count <> <esperado> then
      raise exception 'SEC-002.T-<lote>-<slug>-<caso> failed: got % expected %',
        v_count, <esperado>;
    end if;
  end $$;
  raise notice '-- OK: SEC-002.T-<lote>-<slug>-<caso>';
rollback;
```

Cada arquivo agrupa **todos os casos da mesma tabela** em blocos `begin/rollback` independentes — falha de um caso não contamina os outros da mesma tabela, mas aborta a suíte no runner.

## 5. Fixtures (`_lib/fixtures.sql`)

Fonte única de UUIDs canônicos (§1.4 de `tests-01`) e seeds mínimos:

- Empresas: `E1`, `E2`.
- Usuários (via `auth.users` já existentes no ambiente de teste, referenciados por UUID; a suíte **não** cria em `auth.users`, apenas em `public.profiles` e `public.user_empresas`/`user_roles`).
- Obras: `O1` em `E1`; `O2` em `E2`.
- Boards: `B1` em `O1` com `owner_id=U1`; `B2` sem obra.
- Cards: `C1` posicionado em `B1` com `responsavel_id=U1`.
- Vínculos: `user_empresas(U1,E1)`, `obra_membros(U1,O1)`, `board_membros(B1,U1)`, `card_membros(C1,U1)`.
- GM: `user_roles(UGM,'gm')`.
- Outsider: `U2` **sem nenhum vínculo**.

Fixtures são **idempotentes** (`insert ... on conflict do nothing`) para permitir reexecução no mesmo transaction wrapper de CI.

## 6. Helpers de JWT (`_lib/jwt.sql`)

Duas funções `plpgsql` locais à sessão (definidas por `create or replace function pg_temp.set_jwt_user(...)` ou como scripts `\set`), para evitar poluir o schema `public`:

```sql
create or replace function pg_temp.set_jwt_user(_uid uuid)
returns void language plpgsql as $$
begin
  perform set_config('role', 'authenticated', true);
  perform set_config('request.jwt.claims',
    json_build_object('sub', _uid, 'role','authenticated','aud','authenticated')::text,
    true);
end $$;

create or replace function pg_temp.set_jwt_anon()
returns void language plpgsql as $$
begin
  perform set_config('role', 'anon', true);
  perform set_config('request.jwt.claims', '{"role":"anon"}', true);
end $$;
```

## 7. Oráculos por caso mínimo

Cada `<caso>` mapeia para exatamente um dos padrões abaixo:

| Caso | Ato | Oráculo |
|------|-----|---------|
| `gm` | `set_jwt_user(UGM)` | `SELECT` retorna todas as linhas da tabela / `INSERT` aceito |
| `member` | `set_jwt_user(U1)` | `SELECT` retorna apenas linhas do escopo de `U1` |
| `outsider` | `set_jwt_user(U2)` | `SELECT` retorna 0 linhas; `INSERT/UPDATE/DELETE` bloqueado |
| `anon` | `set_jwt_anon()` | qualquer comando retorna 0 linhas ou erro `permission denied` |
| `ownership` | `set_jwt_user(U1)` | `UPDATE/DELETE` em linha alheia afeta 0 linhas (RLS filtra) |
| `segregation` (D) | `set_jwt_user(U1)` como solicitante | `UPDATE` de aprovação em própria solicitação afeta 0 linhas |

## 10. Riscos e mitigação

- **R1: fixtures colidem entre lotes.** Mitigação: cada arquivo abre/fecha transação; UUIDs canônicos são compartilhados mas rollback isola escritas.
- **R2: policies dependem de `auth.uid()` — `set_config('role','authenticated', true)` sozinho não popula.** Mitigação: `_lib/jwt.sql` também seta `request.jwt.claims` com `sub`, que é o que `auth.uid()` do PostgREST lê.
- **R3: `user_roles` deixa `gm` residual entre arquivos.** Mitigação: `teardown.sql` roda ao fim de cada arquivo removendo `user_roles(_,‘gm’)` inseridos por fixture (idempotente por UUIDs canônicos).
- **R4: staging sem dados reais mascara regressão de performance.** Fora do escopo desta suíte — cobrir em `SEC-002.perf-01` (futuro).
- **R5: divergência entre `test_id` no spec e no runner.** Mitigação: runner extrai `test_id` do comentário `-- test_id:` e valida contra lista canônica em `_lib/test_ids.txt` (gerado a partir de `SEC-002.tests-01`).
