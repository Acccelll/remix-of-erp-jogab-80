# SEC-002.freeze-guard-01.evidence-validator-bump-01.spec-01 — Extensão do `sec002-freeze-guard` para proteger validador de evidências e `INDEX.md`

**Onda:** 2 (bloqueada — depende de `SEC-001` fechar e da Onda 2 ser formalmente aberta)
**Data:** 2026-07-12
**Depende de:**
- `SEC-002.freeze-guard-01.spec-01` — contrato original do freeze-guard (F1–F8);
- `SEC-002.freeze-guard-01.parser-bump-01.materialize-01` (R55) — guard data-driven com F9–F11;
- `SEC-002.evidence-index-01.materialize-01` (R59) — `INDEX.md` canônico;
- `SEC-002.validate-evidence-index-01.materialize-01` (R61) — validador canônico;
- `SEC-002.apply-map-01.evidence-validator-bump-01.spec-01` (R62) — contrato do bump `v2026-07-12.4`;
- `SEC-002.apply-map-01.evidence-validator-bump-01.materialize-01` (R63) — materialização do bump e dos novos `protected_paths[]`.

**Escopo:** especificar a extensão do CI guard `sec002-freeze-guard` para consumir a lista `protected_paths[]` do apply-map `v2026-07-12.4` — em particular os três caminhos novos (`scripts/sec002/validate-evidence-index.mjs`, `.github/sec002-evidence/validate-evidence-index-01/**` e `.github/sec002-evidence/INDEX.md`) — e bloquear PRs que os alterem fora de um apply autorizado. **Nenhum arquivo de produção é alterado nesta spec.** Materialização ocorre em `SEC-002.freeze-guard-01.evidence-validator-bump-01.materialize-01` (R65).

## 1. Racional

R63 registrou três novos caminhos em `protected_paths[]`. Como R55 já tornou o guard data-driven, a extensão aqui se limita a: (a) adicionar mapeamento canônico `caminho → apply autorizado`, (b) reservar códigos de erro específicos F12–F14 para diagnóstico, e (c) proteger o `INDEX.md` — que é evidência transversal e não pertence a um único apply.

Sem esta extensão, qualquer PR poderia editar `validate-evidence-index.mjs` ou reescrever `INDEX.md` sem sinal de CI, quebrando a cadeia R58–R63.

## 2. Fonte da verdade

- **Única fonte** de `protected_paths[]`: `.github/sec002-apply-map.json` via `loadApplyMap()`. O guard **não** mantém lista própria.
- **Única fonte** de `APPLY_ID`: `scripts/sec002/parse-apply-id.mjs`. Sem reimplementação.
- Casamento de caminho: mesma semântica de R55 (prefixo literal + `**` no fim de segmentos de diretório).

## 3. Novas invariantes (F12–F14)

- **F12.** `scripts/sec002/validate-evidence-index.mjs` só pode ser alterado sob o apply `validate-evidence-index-01`. Qualquer outro `APPLY_ID` que toque esse arquivo é violação com código `E_FREEZE_F12`.
- **F13.** `.github/sec002-evidence/validate-evidence-index-01/**` só aceita adições/updates dentro do apply `validate-evidence-index-01`; qualquer outro apply tocando esse prefixo é violação com código `E_FREEZE_F13`.
- **F14.** `.github/sec002-evidence/INDEX.md` só pode ser alterado sob os applies autorizados `evidence-index-01` ou `validate-evidence-index-01` (o índice é evidência compartilhada da subsuíte de evidências). Qualquer outro `APPLY_ID` é violação com código `E_FREEZE_F14`.

F1–F11 permanecem inalteradas. F9 continua sendo o gate genérico "todo `protected_paths[]` é verificado" — F12–F14 são refinamentos com códigos dedicados para diagnóstico.

## 4. Delta funcional do guard

- Nenhuma mudança estrutural: o guard já é data-driven desde R55.
- Adicionar tabela canônica interna de mapeamento `path_pattern → allowed_apply_ids[]` **apenas** para os três caminhos novos, de modo a emitir códigos F12/F13/F14 em vez do F9 genérico:

```js
const EVIDENCE_VALIDATOR_MAP = [
  { pattern: "scripts/sec002/validate-evidence-index.mjs",              allowed: ["validate-evidence-index-01"], code: "E_FREEZE_F12" },
  { pattern: ".github/sec002-evidence/validate-evidence-index-01/**",   allowed: ["validate-evidence-index-01"], code: "E_FREEZE_F13" },
  { pattern: ".github/sec002-evidence/INDEX.md",                        allowed: ["evidence-index-01", "validate-evidence-index-01"], code: "E_FREEZE_F14" }
];
```

- A tabela é redundância verificável: cada `pattern` **deve** estar em `map.protected_paths[]` (assertiva de startup do guard) — se não estiver, o guard falha com `E_FREEZE_F9` referenciando divergência apply-map ↔ guard.
- Algoritmo por arquivo alterado permanece: `git diff --name-only origin/main...HEAD` → casar com `map.protected_paths[]` → exigir `APPLY_ID` cujo `allowed_paths[]` cobre o arquivo. A tabela acima só troca o código emitido em caso de violação.

## 5. Interação com outros guards

| Guard | Efeito |
|---|---|
| `sec002-consumers-guard` | independente; roda sempre |
| `sec002-pr-checklist` | freeze-guard continua paralelo, sem depender dos 11 gates |
| `parse-apply-id.mjs` | reutilizado para extrair `APPLY_ID`; sem reimplementação local |
| `validate-evidence-index.mjs` | consumidor do apply-map (R63), rodado pelo checklist; freeze-guard apenas protege o arquivo |

## 6. Rejeição

Rejeitar a materialização (R65) se:

- guard mantiver qualquer lista hard-coded fora da tabela restrita de §4 ou perder o assert de consistência com `map.protected_paths[]`;
- F12, F13 ou F14 não estiverem cobertas por checagens executáveis;
- guard permitir alterar `INDEX.md` sob `APPLY_ID` diferente de `evidence-index-01` ou `validate-evidence-index-01`;
- guard reimplementar parsing de `APPLY_ID` em vez de invocar `parse-apply-id.mjs`;
- workflow do freeze-guard for renomeado ou perder `concurrency`/`timeout-minutes`;
- qualquer alteração em `src/**`, `supabase/functions/**` ou `supabase/migrations/**`.

## 7. Fora de escopo

- Materializar o script e o workflow atualizados (será R65);
- Alterar semântica dos 11 gates do checklist;
- Introduzir novos `protected_paths[]` além dos fixados por R63;
- Alterar o apply-map ou seus consumidores.
