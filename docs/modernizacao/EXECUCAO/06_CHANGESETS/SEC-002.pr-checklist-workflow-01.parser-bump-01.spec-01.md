# SEC-002.pr-checklist-workflow-01.parser-bump-01.spec-01 — Atualização do workflow `sec002-pr-checklist` para o apply-map `v2026-07-12.3`

**Onda:** 2 (bloqueada — depende de `SEC-001` fechar e da Onda 2 ser formalmente aberta)
**Data:** 2026-07-12
**Depende de:**
- `SEC-002.pr-checklist-workflow-01.materialize-01` (R50) — workflow final com 11 gates;
- `SEC-002.parse-apply-id-01.materialize-01` (R51) — parser oficial;
- `SEC-002.apply-map-01.parser-bump-01.materialize-01` (R53) — apply-map `v2026-07-12.3`;
- `SEC-002.freeze-guard-01.parser-bump-01.materialize-01` (R55) — freeze-guard data-driven.

**Escopo:** especificar a atualização do workflow `sec002-pr-checklist.yml` para consumir o apply-map `v2026-07-12.3` (via loader/validador com M14–M16) e reconhecer explicitamente o pré-gate `parse-apply-id` como consumidor auditado (categoria `parser`). **Sem alterar a ordem, a contagem ou a semântica dos 11 gates.** Nenhum arquivo de produção é alterado nesta spec.

## 1. Racional

R53 bumpou o apply-map, mas o workflow congelado por R50 ainda foi escrito para `v2026-07-12.2`. Sem esta atualização controlada:

- `validate-apply-map` continuaria aceitando um schema desatualizado se o validador local for chamado sem M14–M16;
- o pré-gate `parse-apply-id` estaria auditável no guard `sec002-consumers-guard`, mas o próprio workflow não afirmaria essa dependência de forma explícita;
- futuras auditorias não teriam como amarrar o workflow ao bump correto.

## 2. Delta canônico do workflow

Aplicar exclusivamente estes deltas sobre R50 §3:

### 2.1 Anotação de versão

Adicionar comentário de topo (linhas 1–3 do arquivo):

```yaml
# sec002-pr-checklist
# apply-map: v2026-07-12.3
# consumers: parse-apply-id (parser) + 11 gates
```

### 2.2 Passo `parse-apply-id`

Manter o passo já existente. Nenhuma mudança de shell. Apenas anotar `name`:

```yaml
- name: parse-apply-id  # consumer id="parse-apply-id" category="parser"
```

### 2.3 Passo `validate-apply-map`

Continua sendo o gate 1 lógico do pipeline; garantir que a chamada seja exatamente:

```yaml
- name: validate-apply-map
  run: node scripts/sec002/validate-apply-map.mjs
```

O binário local é o de R53 (com M14–M16). Nenhuma flag nova.

### 2.4 Ordem dos 11 gates

**Não muda.** A ordem canônica de R50 §3 (linhas 40–110) é preservada literalmente. Este bump é apenas de versão e anotação.

## 3. Novas invariantes (W12–W14)

- **W12.** O comentário de topo declara `apply-map: v2026-07-12.3`; qualquer divergência com `SCHEMA_VERSION` do loader é violação.
- **W13.** O passo `parse-apply-id` é o **único** passo antes de `validate-apply-map` e continua sendo o único emissor de `APPLY_ID` em `$GITHUB_ENV`.
- **W14.** O workflow não introduz passos, jobs ou matrizes novas além dos já definidos por R50; contagem final permanece `1 pré-gate + 11 gates`.

W1–W11 permanecem inalteradas.

- Qualquer passo novo, removido ou reordenado dentro dos 11 gates;
- `parse-apply-id` movido para fora da posição de pré-gate único;
- Introdução de `secrets`, `permissions: write-*` ou chamadas de rede externas;
- Alteração em `src/**`, `supabase/functions/**` ou `supabase/migrations/**`.
