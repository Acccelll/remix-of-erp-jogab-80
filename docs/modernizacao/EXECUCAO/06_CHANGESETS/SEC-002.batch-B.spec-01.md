# SEC-002.batch-B.spec-01 — Políticas-alvo do Lote B (registry & transversal)

**Onda:** 2 (preparatória — bloqueada por fechamento de `SEC-001`)
**Data:** 2026-07-12
**Escopo:** especifica o **conjunto atômico de políticas** que substituirá as políticas atuais das **13 tabelas do Lote B** definidas em `SEC-002.inventory-02` §3. É a primeira migração real do plano `SEC-002`. **Nenhuma migração é aplicada neste changeset; este arquivo é a spec que a migração `SEC-002.batch-B.migration` executará**, sob gate, quando o release train `SEC-001` fechar. Nenhum código de produção é alterado.

## 1. Escopo

Tabelas cobertas (13):

```text
audit_logs           formas_pagamento     profiles
centros_custo_totvs  funcoes              user_empresas
clientes             notificacoes         user_roles
documento_tipos      plano_contas
empresas             players
```

Fora do escopo deste lote: qualquer tabela dos lotes C, D, E (irão em seus próprios `batch-*.spec-01`).

## 2. Pré-requisitos duros

A migração `SEC-002.batch-B.migration` só entra depois de:

1. **R7 de `SEC-001`** (delete `sync-player-auth`) — não bloqueante para o SQL, mas exigido pela política de "sem sistema dual" antes de mexer em RLS.
2. **R9 de `SEC-001`** (RBAC server-sourced consolidado) — garante que `public.current_is_gm()` e `public.has_role(...)` são a **única** fonte de autoridade.
3. **`SEC-002.helpers-01` publicado** (este pacote não usa `user_in_*`, mas mantém a ordem).
4. **Suíte `SEC-002.tests-02.suite` verde para o Lote B** — 39/39 PASS.

Se qualquer um falhar no gate, a migração não roda.

## 3. Padrões de regra por classe

Três padrões apenas — cada tabela do lote é mapeada em §5 para um deles.

### 3.1 Padrão **REGISTRY-OPEN-READ** (leitura ampla, escrita GM/admin)

Aplicável a tabelas de referência transversal que qualquer `authenticated` precisa ler:

```sql
create policy "<tabela>_select_authenticated"
  on public.<tabela>
  for select
  to authenticated
  using (true);

create policy "<tabela>_write_gm_admin"
  on public.<tabela>
  for all
  to authenticated
  using (public.current_is_gm() or public.has_role(auth.uid(), 'admin'))
  with check (public.current_is_gm() or public.has_role(auth.uid(), 'admin'));
```

`for all` cobre `INSERT/UPDATE/DELETE` no mesmo par `USING/WITH CHECK`. `SELECT` fica na policy separada porque tem regra distinta.

### 3.2 Padrão **OWNER-SELF** (dono lê/escreve sua própria linha)

Aplicável a tabelas cujo domínio é o próprio usuário:

```sql
create policy "<tabela>_select_owner_or_gm"
  on public.<tabela>
  for select
  to authenticated
  using (
    public.current_is_gm()
    or <coluna_owner> = auth.uid()
  );

create policy "<tabela>_write_owner_or_gm"
  on public.<tabela>
  for all
  to authenticated
  using (
    public.current_is_gm()
    or <coluna_owner> = auth.uid()
  )
  with check (
    public.current_is_gm()
    or <coluna_owner> = auth.uid()
  );
```

### 3.3 Padrão **ROLES-READ-VIA-DEFINER** (leitura pela função `has_role`, escrita só GM)

Exclusivo de `public.user_roles` — nunca lida diretamente pelo cliente; toda leitura acontece via `public.has_role(...)` `security definer`.

```sql
-- SELECT: negado a authenticated (usa has_role)
create policy "user_roles_select_gm_only"
  on public.user_roles
  for select
  to authenticated
  using (public.current_is_gm());

create policy "user_roles_write_gm"
  on public.user_roles
  for all
  to authenticated
  using (public.current_is_gm())
  with check (public.current_is_gm());
```

`service_role` continua livre por `GRANT`, não por policy.

## 4. Estrutura atômica da migração

Para cada tabela, o bloco é sempre o mesmo shape:

```sql
-- 1. drop das políticas atuais (nomes vindos de pg_policies)
drop policy if exists "<policy_atual_1>" on public.<tabela>;
drop policy if exists "<policy_atual_2>" on public.<tabela>;
...

-- 2. create das políticas-alvo (§3.1/§3.2/§3.3)
create policy "..." on public.<tabela> ...;
create policy "..." on public.<tabela> ...;

-- 3. reafirmar RLS e revogar anon (idempotente)
alter table public.<tabela> enable row level security;
revoke all on public.<tabela> from anon;
grant select, insert, update, delete on public.<tabela> to authenticated;
grant all on public.<tabela> to service_role;
```

A migração inteira roda em **uma transação**: ou todas as 13 tabelas migram, ou nenhuma. Sem `commit` intermediário. Sem `set local` mágico.

## 5. Mapeamento tabela ⇒ padrão

| Tabela | Padrão | Justificativa | Casos §2 de `tests-01` |
|--------|--------|---------------|------------------------|
| `audit_logs` | REGISTRY-OPEN-READ (mas leitura restrita a GM/admin) — **variante:** `SELECT` também exige `current_is_gm() or has_role(...,'admin')` | log sensível; nunca `USING(true)` | `gm`, `member`(nega), `anon`(nega) |
| `centros_custo_totvs` | REGISTRY-OPEN-READ | catálogo transversal | `gm`, `member`, `anon` |
| `clientes` | REGISTRY-OPEN-READ | usado por obras/financeiro | `gm`, `member`, `anon` |
| `documento_tipos` | REGISTRY-OPEN-READ | referência de DP | `gm`, `member`, `anon` |
| `empresas` | REGISTRY-OPEN-READ | catálogo lido em toda tela | `gm`, `member`, `anon` |
| `formas_pagamento` | REGISTRY-OPEN-READ (escrita = GM ∪ `has_role('financeiro')`) | catálogo financeiro | `gm`, `member`, `anon` |
| `funcoes` | REGISTRY-OPEN-READ | catálogo com NRs | `gm`, `member`, `anon` |
| `notificacoes` | OWNER-SELF (`destinatario_id`) | 1:1 com usuário; escrita externa via `service_role` | `gm`, `member` (só as suas), `anon` |
| `plano_contas` | REGISTRY-OPEN-READ (escrita = GM ∪ `has_role('financeiro')`) | plano contábil | `gm`, `member`, `anon` |
| `players` | OWNER-SELF (`id`) + REGISTRY-OPEN-READ para `SELECT` | leitura em toda tela; escrita apenas do próprio ou GM | `gm`, `member`, `anon` |
| `profiles` | OWNER-SELF (`id`) + REGISTRY-OPEN-READ para `SELECT` | idem players | `gm`, `member`, `anon` |
| `user_empresas` | OWNER-SELF (`user_id`) | usuário lê os próprios vínculos; escrita = GM | `gm`, `member`, `anon` |
| `user_roles` | ROLES-READ-VIA-DEFINER | não pode vazar role list | `gm`, `member`(nega SELECT direto), `anon` |

## 6. Exceções nominais (variantes do padrão)

Registradas explicitamente para o gate:

- **`audit_logs`.** `SELECT` **não é aberto** a `authenticated`. Regra:
  ```sql
  using (public.current_is_gm() or public.has_role(auth.uid(),'admin'))
  ```
- **`formas_pagamento`, `plano_contas`.** Escrita: `current_is_gm() or has_role(auth.uid(),'financeiro') or has_role(auth.uid(),'admin')`.
- **`players`, `profiles`.** Duas policies de `SELECT` empilhadas: (a) `USING(true)` para `authenticated` **apenas** se o campo em jogo for público, ou (b) `owner-or-gm`. Como hoje o app já lê tudo, adotamos leitura aberta a `authenticated` e escrita `owner-or-gm`. `INSERT` continua sendo feito por `handle_new_user()` (trigger `SECURITY DEFINER`) — não afetado.
- **`notificacoes`.** `INSERT` restrito a `service_role` **ou** GM (front nunca cria notificação diretamente).
- **`user_roles`.** Nenhuma escrita por `authenticated` fora de GM. Nunca conceder `grant` a `anon`.

## 7. Grants finais (reafirmados)

Aplicados em bloco no final da migração para toda tabela do lote:

```sql
revoke all on public.<tabela> from anon;
grant select, insert, update, delete on public.<tabela> to authenticated;
grant all on public.<tabela> to service_role;
```

Exceção: `public.user_roles` recebe **apenas** `grant select on public.user_roles to authenticated` (compat com `has_role` chamada via `security definer`; escrita fica em `service_role` + GM via policy).

## 9. Reversão

A migração escreve `SEC-002.batch-B.rollback.sql` (companion), contendo `DROP POLICY` de cada nova policy e `CREATE POLICY` das antigas com `USING(true)` (baseline do inventário-02). O rollback é destinado exclusivamente a incidentes de produção; execução exige aprovação de D-9.

## 10. Riscos

- **R1: quebra de leitura em telas que assumiam `USING(true)`.** Mitigação: padrão REGISTRY-OPEN-READ preserva leitura ampla em 10/13 tabelas. As 3 restantes (`audit_logs`, `user_roles`, `notificacoes`) já são acessadas via `security definer` ou owner.
- **R2: `service_role` acidentalmente restrito.** Mitigação: §7 reafirma `grant all` para `service_role` em todas as 13 tabelas.
- **R3: `handle_new_user()` falha ao inserir em `profiles` com nova policy.** Mitigação: trigger é `SECURITY DEFINER owner=postgres`; não passa por RLS. Ainda assim, `profiles_write_owner_or_gm` cobre o `id = auth.uid()` do próprio usuário.
- **R4: leitura de `user_roles` pelo cliente quebra código legado.** Mitigação: `SEC-001.k` já obrigou uso de `has_role`; qualquer `select` direto restante é bug a corrigir no mesmo release.

## 11. Impacto em produção

**Nenhum neste changeset.** Documento de especificação. A migração real (`SEC-002.batch-B.migration`) e sua suíte de testes (`SEC-002.tests-02.suite/batch-B`) são changesets seguintes, cada um sujeito a gate próprio.
