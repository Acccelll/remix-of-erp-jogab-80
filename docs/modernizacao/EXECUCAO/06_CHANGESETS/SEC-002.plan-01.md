# SEC-002.plan-01 — Plano de migração RLS por lotes

**Onda:** 2 — Reforma de Segurança  
**Achado:** `SEC-002` — RLS permissivo: políticas `USING(true)`/`WITH CHECK(true)` em tabelas de negócio  
**Achado absorvido:** `DB-002` — Modelo de acesso RLS em dois regimes  
**Prioridade:** P0 · **Complexidade:** Alta · **Criticidade:** C0 · **Estratégia:** MIGRAÇÃO  
**Data:** 2026-07-12  
**Escopo:** plano técnico e inventário inicial para a execução futura de `SEC-002`. **Nenhuma política, grant, migration ou código de produção é alterado neste changeset.**

## 1. Premissas formais

`SEC-002` só pode entrar em execução efetiva depois de:

1. `SEC-001` concluído no release train definido em `SEC-001.README`;
2. identidade backend confiável e hidratada no cliente;
3. `current_is_gm()`/`has_role()` validados como autoridade final;
4. decisões D-1 e D-2 registradas no Contrato de Execução;
5. baseline de testes de acesso por papel disponível.

D-2 fixou o regime-alvo:

```text
RLS estrita por empresa + role, com GM bypass explícito.
Base: has_role + current_empresas/current_is_gm.
```

## 2. Baseline observado em 2026-07-12

Consultas de inventário executadas contra o backend atual indicam que o cenário já diverge parcialmente da auditoria original:

| Métrica | Valor atual | Leitura |
|---------|-------------|---------|
| Políticas públicas em `public` | 286 | universo atual de RLS |
| Políticas `anon` com `true` | 0 | exposição anônima direta já não aparece no baseline atual |
| Tabelas com política `anon` permissiva | 0 | critério crítico parcialmente atendido no estado atual |
| Políticas `authenticated` com `true` | 184 | ainda há regime amplo para usuário autenticado |
| Tabelas com política `authenticated` permissiva | 47 | núcleo restante de `DB-002`/`SEC-002` |
| Avisos do linter: `RLS Policy Always True` | 163 | foco principal dos lotes |

Interpretação: `SEC-002` deixa de ser apenas fechamento de `anon`; passa a ser consolidação do regime para usuários autenticados, substituindo `true` por regras explícitas de empresa, papel, obra, autoria ou exceção pública mínima.

## 3. Invariantes de segurança

1. Tabelas de negócio não podem ter leitura/escrita anônima sem justificativa explícita.
2. `authenticated` não é permissão suficiente por si só para dados sensíveis.
3. Todo bypass GM deve usar `public.current_is_gm()` ou função equivalente server-side.
4. Acesso por empresa deve usar `public.current_empresas()` ou vínculo derivado.
5. Acesso por obra deve usar `public.user_em_obra()`/`public.user_pode_editar_obra()` ou helper `_require_*` existente.
6. Service role continua fora da RLS operacional e deve ser usado apenas por funções/rotinas administrativas.
7. QR público e fluxos realmente públicos são exceções documentadas, nunca `USING(true)` genérico.

## 4. Estratégia por lotes

### Lote A — Inventário e classificação (`SEC-002.a`)

Objetivo: produzir uma matriz por tabela antes de alterar políticas.

Campos mínimos:

| Campo | Descrição |
|-------|-----------|
| tabela | nome em `public` |
| módulo | financeiro, DP, planejamento, obras, cards, suprimentos, etc. |
| sensibilidade | baixa, média, alta, crítica |
| leitura alvo | GM, setor, empresa, obra, autoria, público mínimo |
| escrita alvo | GM, setor, gestor de obra, autor, função backend |
| política atual | permissiva, parcial, estrita, exceção pública |
| função/helper recomendado | `current_is_gm`, `current_has_setor`, `user_em_obra`, etc. |
| teste obrigatório | anon, usuário comum, setor, GM |

Saída esperada: `SEC-002.inventory-01.md`.

### Lote B — Tabelas transversais e cadastros (`SEC-002.b`)

Escopo provável:

- `clientes`;
- `funcoes`;
- `formas_pagamento`;
- `documento_tipos`;
- `centros_custo_totvs`;
- demais cadastros read-heavy.

Regra alvo:

- leitura: usuário autenticado com empresa/escopo compatível, ou GM;
- escrita: GM ou setor responsável;
- sem `WITH CHECK(true)`.

### Lote C — Obras, planejamento e cronograma (`SEC-002.c`)

Escopo provável:

- `obras` e dados derivados;
- `cronograma_*`;
- `pacotes_trabalho`, `restricoes`, `licoes_aprendidas`, `compromissos_semanais`;
- vínculos por obra.

Regra alvo:

- leitura: membro da obra, setor autorizado ou GM;
- escrita: gestor/editor da obra, setor autorizado ou GM;
- exceções documentadas para dados necessários em seletores globais.

### Lote D — Financeiro e DP (`SEC-002.d`)

Escopo provável:

- `financeiro_*`;
- `controle_despesas`;
- `solicitacoes_financeiras`;
- `dp_holerite`, `fopag_entries`, `historico_salarial`, `provisoes`, `horas_extras`, `decimo_terceiro`, `custo_colaborador_competencia`.

Regra alvo:

- leitura/escrita restrita a GM, setor financeiro/DP e escopo empresarial;
- dados pessoais e folha nunca ficam abertos para todo usuário autenticado;
- testes negativos obrigatórios para usuário comum.

### Lote E — Cards, inspeções e fluxos públicos controlados (`SEC-002.e`)

Escopo provável:

- `cards` e tabelas auxiliares;
- `inspecao_*`;
- alvos QR/públicos, se aplicável.

Regra alvo:

- cards por setor, obra, membro ou GM;
- QR público com política mínima, coluna/ação mínima e registro de justificativa;
- nenhuma política pública genérica sobre tabela de negócio inteira.

### Lote F — Gate e documentação final (`SEC-002.f`)

Entregas:

- script/gate de verificação de políticas permissivas;
- consulta de regressão para leitura anônima vazia;
- documentação do regime por tabela;
- checklist de exceções públicas aprovadas.

## 5. Forma das migrations futuras

Cada lote deve seguir o padrão:

1. `DROP POLICY IF EXISTS` apenas das políticas substituídas;
2. criação de políticas específicas por comando (`SELECT`, `INSERT`, `UPDATE`, `DELETE`), evitando `FOR ALL` quando a regra divergir;
3. `GRANT` revisado para remover privilégios `anon` de tabelas não públicas;
4. helpers server-side reaproveitados antes de criar funções novas;
5. comentários SQL quando houver exceção pública deliberada.

Exemplo conceitual — não aplicar diretamente:

```sql
CREATE POLICY "<tabela> select por obra ou gm"
ON public.<tabela>
FOR SELECT
TO authenticated
USING (
  public.current_is_gm()
  OR public.user_em_obra(obra_id)
);
```

## 6. Consultas de verificação

### 6.1 Políticas permissivas remanescentes

```sql
SELECT tablename, policyname, roles, cmd, qual, with_check
FROM pg_policies
WHERE schemaname = 'public'
  AND (
    (roles::text LIKE '%anon%' AND (qual = 'true' OR with_check = 'true'))
    OR
    (roles::text LIKE '%authenticated%' AND cmd <> 'SELECT' AND (qual = 'true' OR with_check = 'true'))
  )
ORDER BY tablename, policyname;
```

### 6.2 Grants anônimos remanescentes

```sql
SELECT table_name, privilege_type
FROM information_schema.table_privileges
WHERE table_schema = 'public'
  AND grantee = 'anon'
ORDER BY table_name, privilege_type;
```

### 6.3 Baseline agregado

```sql
SELECT
  count(*) FILTER (WHERE roles::text LIKE '%anon%' AND (qual = 'true' OR with_check = 'true')) AS anon_true_policies,
  count(*) FILTER (WHERE roles::text LIKE '%authenticated%' AND (qual = 'true' OR with_check = 'true')) AS authenticated_true_policies,
  count(DISTINCT tablename) FILTER (WHERE roles::text LIKE '%authenticated%' AND (qual = 'true' OR with_check = 'true')) AS authenticated_true_tables
FROM pg_policies
WHERE schemaname = 'public';
```

## 7. Critérios de aceite de `SEC-002`

- [ ] 0 política `TO anon ... USING(true)`/`WITH CHECK(true)` sem justificativa documentada.
- [ ] 0 grant `anon` em tabela de negócio não pública.
- [ ] Políticas `authenticated` com `true` substituídas por regra explícita ou justificadas como leitura pública interna não sensível.
- [ ] Leitura anônima de tabelas de negócio retorna vazio.
- [ ] Usuário comum não acessa financeiro, DP ou dados de obra fora de escopo.
- [ ] GM mantém acesso total por `current_is_gm()`/RLS.
- [ ] QR público e edge functions preservados por políticas mínimas específicas.
- [ ] Linter sem novos avisos relacionados às policies alteradas no lote.
- [ ] Regime por tabela documentado.

## 8. Riscos e bloqueios

| Risco | Mitigação |
|-------|-----------|
| Fechar política antes de mapear telas consumidoras | inventário por módulo antes de cada migration |
| Quebrar dropdowns globais de cadastro | separar leitura mínima de escrita restrita |
| Reintroduzir `authenticated true` em migrations futuras | gate `SEC-002.f` |
| Confundir dado público com dado operacional interno | exceção pública precisa de justificativa e teste |
| Executar antes do fim de `SEC-001` | manter este changeset como plano até o GO |
