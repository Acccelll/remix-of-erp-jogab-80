# SEC-001.k.spec-01 — RBAC server-sourced e remoção de `currentPlayer.isGM` como fonte de verdade

**Onda:** 2 (bloqueada — D-1/D-2 · cutover em pipeline dedicado)  
**Data:** 2026-07-12  
**Escopo:** apoio à Onda 2 autorizado por D-9. Especifica a consolidação do RBAC no backend, removendo a dependência de `currentPlayer.isGM` como fonte de verdade para autorização. **Nenhum código de produção é alterado neste changeset.**

## 1. Estado atual

`SEC-001.audit-02 §5` identificou **37 arquivos** referenciando `isGM`/`currentPlayer.isGM`.

Categorias afetadas:

- contextos e helpers (`AppContext`, `EmpresaContext`, mappers, `usePlayersState`);
- hooks de permissão (`useObraMembership`, `useObrasEditaveis`, `useCardPermissions`);
- páginas com bypass GM;
- diálogos e fluxos de importação.

Hoje, `isGM` chega ao cliente a partir do login PHP/local e pode ser persistido em `go_player`. Mesmo que `SEC-001.j` passe a hidratar o valor via backend, qualquer decisão de autorização baseada diretamente no objeto local continua frágil.

## 2. Estado alvo

Autorização sempre derivada do backend:

1. Papéis ficam em `public.user_roles`.
2. Checagem GM usa `public.current_is_gm()` para o usuário autenticado.
3. Políticas RLS continuam usando `public.has_role(auth.uid(), 'gm')` ou equivalentes.
4. `currentPlayer.isGM` permanece apenas como **campo de compatibilidade visual/transicional**, alimentado por backend, sem decidir acesso sensível.
5. Nenhum bypass de página, hook ou ação destrutiva consulta `localStorage.go_player.isGM` ou `currentPlayer.isGM` diretamente.

Invariante final:

```text
Permissão efetiva = f(auth.uid(), user_roles, user_empresas, políticas RLS)
currentPlayer.isGM = espelho derivado, nunca autoridade
```

## 3. Mudanças de código previstas

### 3.1 Criar camada única de autorização cliente

Novo hook/serviço previsto:

```ts
type AuthzSnapshot = {
  userId: string;
  isGM: boolean;
  roles: string[];
  empresas: string[];
};

useAuthz(): {
  data: AuthzSnapshot | null;
  isLoading: boolean;
  can: (capability: string, scope?: unknown) => boolean;
}
```

Fonte dos dados:

- `supabase.auth.getSession()` para `auth.uid()` efetivo;
- `supabase.rpc("current_is_gm")` para GM;
- `user_roles`/`user_empresas` para papéis e escopo empresarial;
- cache curto por `session.user.id`, invalidado em logout e troca de sessão.

### 3.2 Migrar hooks de permissão primeiro

Prioridade de migração:

1. `useObraMembership`;
2. `useObrasEditaveis`;
3. `useCardPermissions`;
4. qualquer hook que hoje trate GM como bypass local.

Regra: hooks recebem `authz` ou consomem `useAuthz`; não recebem booleano GM do `currentPlayer`.

### 3.3 Migrar páginas e diálogos

Páginas/diálogos deixam de fazer:

```ts
if (currentPlayer?.isGM) { ... }
```

E passam a usar:

```ts
const { can } = useAuthz();
if (can("obra:editar", { obraId })) { ... }
```

O mapa `capability → regra` deve ficar centralizado para evitar lógica duplicada em componentes.

### 3.4 `AppContext.tsx`

Após `SEC-001.j`, `AppContext` pode manter `currentPlayer.isGM` para compatibilidade de UI, mas deve:

- preencher `isGM` somente a partir de `current_is_gm()`/backend;
- nunca derivar `isGM` de payload PHP ou `localStorage`;
- expor aviso de depreciação em comentário interno: `currentPlayer.isGM is display-only; use useAuthz() for authorization`.

### 3.5 `usePlayersState`

Operações administrativas sobre players não devem confiar no GM local. Devem exigir:

- sessão backend válida;
- `current_is_gm() = true` ou política equivalente;
- erro explícito quando a checagem de autorização não puder ser confirmada.

## 4. Ordem obrigatória

`SEC-001.k` só é seguro depois de:

1. `SEC-001.g` — rota única e sessão Cloud hidratada;
2. `SEC-001.mig-01` — identidade única por login;
3. `SEC-001.i` — sem senha em `go_player`;
4. `SEC-001.j` — login primário via Cloud Auth, com `isGM` já server-sourced;
5. `SEC-001.j flag OFF` — fallback PHP desativado ou métrica residual justificada.

## 5. Compatibilidade transicional

Durante a migração:

- `Player.isGM` permanece no tipo para evitar quebra ampla;
- componentes visuais podem ler `currentPlayer.isGM` apenas para rótulos/estado visual não sensível;
- qualquer ação de leitura restrita, escrita, aprovação, exclusão ou bypass operacional deve passar por `useAuthz`/RLS;
- se `useAuthz` estiver carregando, ações sensíveis ficam bloqueadas, não liberadas por fallback local.

## 6. Critérios de aceitação

- [ ] `rg -n 'currentPlayer\??\.isGM|currentPlayer\.isGM' src` sem matches em decisões de autorização.
- [ ] Hooks de permissão consomem `useAuthz` ou RPC server-sourced, não booleano local.
- [ ] `currentPlayer.isGM` é preenchido apenas por backend após sessão válida.
- [ ] `localStorage.go_player` não contém nem decide `isGM` para autorização.
- [ ] Usuário GM mantém acesso total via `current_is_gm()`/RLS.
- [ ] Usuário não-GM não consegue obter bypass alterando `localStorage` no navegador.
- [ ] Logout invalida cache de `useAuthz` e remove dados locais derivados.

## 7. Testes previstos

1. Smoke GM: login → `current_is_gm() = true` → páginas restritas acessíveis.
2. Smoke não-GM: login → `current_is_gm() = false` → páginas restritas bloqueadas.
3. Manipulação local: alterar `go_player.isGM = true` no devtools não altera permissões.
4. Troca de sessão: logout/login com outro usuário não reaproveita cache de RBAC.
5. RLS: query restrita falha quando `user_roles` não autoriza, mesmo que UI tente liberar.

## 8. Fora de escopo

- Redesenhar todas as permissões funcionais do produto.
- Criar novos papéis além dos já existentes.
- Aplicar migrações ou políticas novas sem GO da Onda 2/D-2.
- Remover o campo `isGM` do tipo `Player` nesta etapa; isso pode ser `SEC-001.m`.

## 9. Impacto em produção

**Nenhum.** Documento de especificação. Nenhum arquivo em `src/`, `supabase/functions/` ou `supabase/migrations/` foi alterado.
