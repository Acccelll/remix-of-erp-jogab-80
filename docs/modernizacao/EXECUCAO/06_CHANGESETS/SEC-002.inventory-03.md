# SEC-002.inventory-03 — Reclassificação de `other` e alocação de `test_id`

**Onda:** 2 (preparatória — bloqueada por fechamento de `SEC-001`)  
**Data:** 2026-07-12  
**Escopo:** fecha os dois débitos de `SEC-002.inventory-02`: (a) reclassificar as 25 políticas caídas em `other` e (b) atribuir `test_id` a toda linha da matriz. **Nenhuma migração, nenhuma alteração de código.**

## 1. Diagnóstico das 25 políticas `other`

Consulta de verificação:

```sql
select tablename, cmd, policyname, roles, qual, with_check
from pg_policies
where schemaname='public' and qual is null and with_check is not null and with_check <> 'true';
```

Resultado: **25 linhas, todas `cmd = INSERT`** — políticas de escrita não têm `USING` (por definição do Postgres), apenas `WITH CHECK`. A classificação inicial em `SEC-002.inventory-02` só olhou `qual`, portanto marcou-as como `other`. São, na verdade:

| Subclasse | Contagem | Tabelas | Regra encontrada |
|-----------|----------|---------|------------------|
| `auth-only-write` | 24 | `boards`, `board_campos`, `board_listas`, `board_membros`, `cards`, `card_anexos`, `card_atividades`, `card_board_posicao`, `card_campos_valores`, `card_checklist_itens`, `card_comentarios`, `card_custom_field_valores`, `card_grupos_negociacao`, `card_label_links`, `card_labels`, `card_local`, `card_membros`, `card_membros_externos`, `card_recursos`, `card_secoes_visiveis`, `card_setores`, `card_views_salvas`, `empresas`, `user_empresas` | `WITH CHECK (auth.uid() IS NOT NULL)` |
| `role-scoped-write` | 1 | `obra_membros` | `WITH CHECK (current_is_gm())` |

## 2. Regra de classificação corrigida (para futuras varreduras)

Adicionar ao classificador de `SEC-002.inventory-01` §5:

> Para políticas com `cmd IN ('INSERT','UPDATE','ALL')`, aplicar as mesmas heurísticas de expressão sobre `COALESCE(qual, with_check)`, não apenas `qual`.

Com essa correção, as 25 políticas migram para `auth-only` (24) e `role-scoped` (1). A distribuição consolidada passa a ser:

| Classificação | Antes | Depois |
|---------------|-------|--------|
| permissive-authenticated | 184 | 184 |
| auth-only | 72 | **96** |
| role-scoped | 3 | **4** |
| owner-or-scoped | 2 | 2 |
| other | 25 | **0** |
| **Total** | 286 | 286 |

Zero políticas ficam sem classificação determinística. O CSV `SEC-002.inventory-02.csv` **não é reescrito**; as contagens agregadas por tabela em `permissive_auth` / `auth_only` / `role_scoped` continuam válidas porque somam `total` corretamente (INSERTs `auth-only-write` já estão contados na coluna `auth_only` do agregado por tabela, exceto onde apareciam como `permissive_auth` — ver §3).

## 3. Ajuste por tabela

As tabelas afetadas pela reclassificação são exatamente aquelas listadas em §1. Para elas, uma unidade **muda de coluna** no CSV agregado:

- Tabelas `boards`, `board_*`, `cards`, `card_*` (22): já tinham `auth_only = 3` (SELECT/UPDATE/DELETE) e `permissive_auth = 0`; o INSERT antes caía em `other` e agora entra em `auth_only`, elevando para `auth_only = 4`. **Sem impacto no lote (E)**.
- `empresas`, `user_empresas` (2): `auth_only` sobe de 3 para 4. **Sem impacto no lote (B)**.
- `obra_membros` (1): `role_scoped` sobe de 3 para 4. **Sem impacto no lote (C)**; confirma que a tabela já está integralmente `role-scoped` (base para `user_in_obra`).

Correção formal do CSV fica para `SEC-002.inventory-04` junto com a coluna `test_id`; o presente changeset registra a diferença sem reescrever o artefato para preservar hash de auditoria.

## 4. Convenção de `test_id`

Formato: `SEC-002.T-<lote>-<slug>-<caso>`.

- `<lote>` ∈ {B,C,D,E}
- `<slug>` = nome da tabela em snake_case
- `<caso>` ∈ {`gm`, `member`, `outsider`, `anon`, `segregation`, `owner`}

Casos mínimos obrigatórios por classe-alvo:

| Regra-alvo do lote | Casos mínimos |
|--------------------|---------------|
| Registry autenticado (B) | `gm`, `member` (authenticated qualquer), `anon` (negado) |
| Escopo empresa (C base) | `gm`, `member` (mesma empresa), `outsider` (outra empresa), `anon` |
| Escopo obra (C operação) | `gm`, `member` (membro da obra), `outsider` (não-membro), `anon` |
| DP/Financeiro (D) | `gm`, `member` (com `has_role` correspondente), `outsider` (sem role), `anon`, `segregation` (solicitante ≠ aprovador) |
| Boards/Cards (E) | `gm`, `owner`, `member`, `outsider`, `anon` |

Toda linha da matriz recebe o **conjunto mínimo** do seu lote — não é necessário duplicar `test_id` por comando (SELECT/INSERT/UPDATE/DELETE); o caso de teste exercita os quatro comandos em sequência.

## 5. Anexo do `test_id` à matriz

Para as 73 tabelas de `SEC-002.inventory-02.csv`, o `test_id` derivado é determinístico e não precisa ser rearmazenado linha a linha; a regra é:

```text
test_ids(table, batch) = { SEC-002.T-<batch>-<table>-<caso> | caso ∈ casos_minimos(batch) }
```

Onde `casos_minimos(batch)` segue §4. O ficheiro executável (`SEC-002.tests-01.md`) — próximo changeset — vai enumerar cada `test_id` com fixture, oráculo e comando de execução (pgTAP ou seed + `set request.jwt.claims`).
