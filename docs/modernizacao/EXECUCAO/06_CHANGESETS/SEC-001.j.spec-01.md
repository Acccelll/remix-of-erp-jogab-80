# SEC-001.j.spec-01 — Supabase como IdP primário, PHP como fallback

**Onda:** 2 (bloqueada — D-1/D-2 · cutover em pipeline dedicado)
**Data:** 2026-07-12
**Escopo:** apoio à Onda 2 autorizado por D-9. Especifica a inversão de autoridade: `supabase.auth.signInWithPassword` passa a ser o IdP primário; PHP legado vira **fallback condicionado** durante a janela de convivência e é desligado no cutover final. **Nenhum código de produção é alterado neste changeset.**

## 1. Estado atual (recap)

`AppContext.login` (audit-02 §3):

```
1. api.create("login")            // PHP — fonte da verdade hoje
2. ensureSupabaseSession()        // fire-and-forget → sync-player-auth
3. setCurrentPlayer(...)
```

`supabase.auth` é apenas consequência do PHP. RLS depende de self-heal ex post.

## 2. Estado alvo (pós-SEC-001.j)

`AppContext.login` (fluxo canônico):

```
1. email = resolveEmailFromLogin(login)      // @obraflow.local
2. { data, error } = supabase.auth.signInWithPassword({email, password})
3a. sucesso → hidrata currentPlayer via profiles + user_roles + user_empresas
3b. erro "Invalid login credentials" E flag PHP_FALLBACK_ENABLED
    → chama PHP api.create("login")
    → se PHP OK, chama edge function provision-auth-user (self-heal)
    → repete passo 2
4. qualquer outro erro → mostra erro ao usuário, não tenta fallback
```

## 3. Resolução `login → email`

`resolveEmailFromLogin(login: string)` retorna `${lower(login)}@obraflow.local`.

Racional: após `SEC-001.mig-01`, `auth.users.email` é determinístico. Não precisa consulta ao PHP para descobrir email — a convenção de domínio basta.

Usuários com email real (raro, mas suportado pela Rota A hoje) mantêm o email real gravado em `auth.users`; para esses, `signInWithPassword` com `@obraflow.local` falha e cai no fallback PHP, que na resposta traz o `email` real e refaz o `signInWithPassword`. Custo aceitável (poucos casos, apenas primeira migração).

## 4. Feature flag `PHP_FALLBACK_ENABLED`

Fonte: constante em `src/config/authFlags.ts` (a criar em SEC-001.j implementação). Valores:

| Fase | Flag | Comportamento |
|------|------|---------------|
| Cutover D+0..D+30 | `true` | Fallback PHP ativo (rede de segurança) |
| D+30..D+60 | `true` + banner "IdP primário Supabase" para GM | Métrica de uso do fallback deve tender a 0 |
| D+60 (aprovação D-1/D-2) | `false` | PHP não é mais chamado; se `signInWithPassword` falha, é falha real |
| D+90 | remoção do código de fallback | `SEC-001.k` (delete `sync-player-auth` já feito em SEC-001.g R7) |

Flag pode ser em compile-time (`import.meta.env.VITE_PHP_FALLBACK`) para evitar dependência de tabela remota no login.

## 5. Mudanças de código previstas

### 5.1 `src/contexts/AppContext.tsx`

- Substituir `api.create("login")` inicial por `supabase.auth.signInWithPassword`.
- Bloco fallback isolado em função `tryPhpFallback(login, password): Promise<Player|null>` — retorna `null` quando `PHP_FALLBACK_ENABLED = false`.
- Após sucesso Supabase, hidratação:
  ```ts
  const { data: profile } = await supabase.from("profiles").select("*").eq("id", session.user.id).single();
  const isGm = await supabase.rpc("has_role", { _user_id: session.user.id, _role: "gm" });
  ```
  `currentPlayer.isGM` passa a ser **server-sourced** (audit-02 §7 recomendação SEC-001.l).

### 5.2 `src/lib/auth/ensureCloudSession.ts`

Passa a ser chamado APENAS no fallback (§2 passo 3b). Fora do fallback, o `signInWithPassword` já cria a sessão sem precisar da edge function.

### 5.3 `src/lib/api.ts`

`api.create("login", ...)` continua exportado (usado por outros fluxos legados fora do escopo), mas ganha `@deprecated: use supabase.auth.signInWithPassword`.

## 6. Invariantes preservadas

- `currentPlayer.isGM ⇔ has_role(auth.uid(),'gm')` — agora **por construção**, não por convergência.
- Logout limpa `supabase.auth.signOut()` + `localStorage.removeItem("go_player")` + `localStorage.removeItem("go_token")` (audit-02 §7, fecha o buraco do logout fire-and-forget).
- Nenhum novo `auth.users` é criado no fluxo primário — só no fallback (que emite via `provision-auth-user`).

## 7. Riscos e mitigação

| Risco | Mitigação |
|-------|-----------|
| PHP muda regra de senha (hash, expiração) durante convivência | Fallback dispara `provision-auth-user` que reseta hash Supabase; próximas tentativas usam Supabase direto |
| Usuário PHP-only nunca aparece no Supabase | Fallback provisiona no primeiro login pós-deploy |
| Race entre 2 logins simultâneos do mesmo user | `signInWithPassword` é idempotente; `provision-auth-user` já tem upsert (audit-01 §7) |
| Métrica de fallback não cai | Bloqueia D+60 (flag continua `true`); investiga pool de contas travadas |

## 8. Critérios de aceitação (para GO da Onda 2 final)

- [ ] `rg -n 'api.create\\("login"' src` apenas dentro de `tryPhpFallback`.
- [ ] Login novo em conta limpa passa por `signInWithPassword` sem tocar PHP (log da edge PHP mostra 0 chamadas em ambiente de teste).
- [ ] `currentPlayer.isGM` vem de `has_role`, não de `player.is_gm` recebido do PHP.
- [ ] Métrica `auth.fallback.hits / auth.login.total` < 1% após 30d de convivência.
- [ ] Desativar flag em staging não quebra nenhum login existente.
