# TST-001.a — E2E de caracterização (M1/M5/M7/M8)

**Onda:** 0 · **Categoria:** Testes · **Prioridade:** P1 · **Criticidade:** C0
**Relacionado:** OPS-001.a (CI), TST-004 (cobertura), Contrato §1 item 2 (cirurgia de regressão Muito Alta exige caracterização E2E prévia)

## Problema

Nenhuma suíte E2E cobria as jornadas críticas do produto. Qualquer cirurgia estrutural (Ondas 3–6) violaria o Contrato §1.2.

## Ação

1. Adicionado `@playwright/test@1.48.2` como devDependency.
2. `playwright.config.ts` com um projeto `setup` (login) + quatro projetos de jornada (`M1`, `M5`, `M7`, `M8`). Sessão gerenciada do Lovable Cloud reusada via `storageState`.
3. Estrutura `e2e/`:
   - `auth.setup.ts` — login via UI usando `E2E_USER`/`E2E_PASSWORD`.
   - `journeys/M1-mobilizacao.spec.ts` — quadro de mobilização.
   - `journeys/M5-inspecao.spec.ts` — agenda de inspeções.
   - `journeys/M7-suprimentos.spec.ts` — requisições de suprimentos.
   - `journeys/M8-financeiro.spec.ts` — lançamentos financeiros.
   - `README.md` — regra de ouro da caracterização.
4. `.env.e2e.example` publicado; `.env.e2e`, `e2e/.auth/`, `playwright-report/`, `test-results/` adicionados ao `.gitignore` (D-01: aplicar no repo espelho — sandbox Lovable trata `.gitignore` como somente-leitura).
5. Script `bun run test:e2e` em `package.json`.
6. Job opcional `e2e` no CI (`.github/workflows/ci.yml`) — roda somente com secrets `E2E_USER`/`E2E_PASSWORD` presentes; caso contrário, `skipped` (não bloqueia PRs externos).

## Escopo consciente (baseline permissivo)

Cada spec faz o mínimo para caracterizar: **rota carrega autenticada, não caiu em `/login`, não é 404**. Passos ricos (drag-and-drop de mobilização, criação de OC, etc.) são adicionados incrementalmente **junto** com o Achado que os exigir, mantendo o custo de manutenção baixo enquanto o produto ainda muda muito.

## Critérios de aceite

- (a) `@playwright/test` em devDependencies ✅
- (b) Config com projeto `setup` + 4 jornadas ✅
- (c) Specs esqueleto por marco (M1/M5/M7/M8) ✅
- (d) Sessão reusada via `storageState` (sem repetir login) ✅
- (e) Documentação da regra de caracterização ✅
- (f) Job de CI opcional condicionado a secrets ✅
- (g) Primeira execução verde contra a instância — ⏳ **pendente**: exige criação do usuário de teste dedicado e provisão dos secrets `E2E_USER`/`E2E_PASSWORD` no repositório (fora da sandbox).

## Discoveries

- **D-18:** os specs assumem seletores por label (`E-mail`, `Senha`) e texto de botão `Entrar`. Se o formulário de login mudar (Achados de UX na Onda 7), atualizar `auth.setup.ts` no mesmo PR.
- **D-19:** para cobrir OAuth Google no futuro, será necessário provisionar conta de teste dedicada ou stub — fora do escopo da caracterização baseline.
- **D-20:** o job de CI usa `bunx playwright install --with-deps chromium`; se migrar para container próprio, remover `--with-deps`.
