# OPS-003.slice-02 — Sinks + propagação de correlationId no cliente

**Onda:** 7 · **Achado:** OPS-003 · **Tipo:** STD/REF · **Escopo:** LOTE (Plataforma)

## Problema

O `structured-logger` do `slice-01` existe mas ninguém está plugado
como sink, e o cliente HTTP (`apiFetch`) ainda não emite eventos
estruturados nem envia `X-Correlation-Id` — ou seja, a fronteira
cliente→backend continua irrastreável.

## Alterações

`src/lib/observability/bootstrap.ts` (novo, `@module-kind io`):
- `installObservabilitySinks()` idempotente.
- **Dev:** sink de console (`console.debug("[evt]", JSON)`) — grep-friendly.
- **Prod (Sentry ativo):** sink que empurra cada evento como
  `Sentry.addBreadcrumb` preservando `severity → level`, `event → message`,
  `correlationId` + `fields` como `data`.
- Sem sink duplicado, sem I/O adicional além do já existente.

`src/main.tsx`:
- Chama `installObservabilitySinks()` logo após `initSentry()`.

`src/lib/api.ts` (instrumentação):
- `doFetch(url, init, correlationId)` passa a exigir o id e o envia
  como header **`X-Correlation-Id`**.
- Cada `apiFetch` gera um id via `newCorrelationId("api")`.
- Emite eventos estruturados:
  - `planifik.api.ok` (debug) — `route`, `method`, `status`, `durationMs`.
  - `planifik.api.http_error` (warn) — `route`, `method`, `status`.
  - `planifik.api.fail` (error) — `route`, `method`, `error`, `replayed?`.
- Log livre pré-existente (`logger.warn` em `noteFailure`) preservado.

## Não escopo

- Não altera o backend PHP (a leitura do header e propagação para
  Supabase/edge é outro slice — depende de acesso ao backend).
- Não instrumenta os edge functions ainda (`slice-03`).
- Não substitui `logger.*`; mensagens livres seguem permitidas.
- Não altera schema/RLS.

## Validação

- `bunx tsgo --noEmit` limpo.
- `bunx vitest run src/lib/observability` → 8/8 verde
  (regra pura do `slice-01` intacta).
- Header `X-Correlation-Id` inspecionável no DevTools > Network em
  qualquer chamada via `apiFetch`.
