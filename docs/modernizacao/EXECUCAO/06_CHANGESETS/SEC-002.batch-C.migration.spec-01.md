# SEC-002.batch-C.migration.spec-01 — Migração executável do Lote C

**Onda:** 2 (preparatória — bloqueada por fechamento de `SEC-001`, `SEC-002.helpers-02.migration` e `SEC-002.batch-B.migration`)  
**Data:** 2026-07-12  
**Escopo:** especifica o **arquivo SQL executável** `supabase/migrations/<ts>_sec_002_batch_c.sql` que materializa as políticas-alvo descritas em `SEC-002.batch-C.spec-01` para as **23 tabelas de obras/operação**. Este changeset é **apenas especificação do arquivo de migração** — nada é aplicado ao banco, nada em `src/` ou edge functions muda. É o terceiro artefato executável de `SEC-002`, depois de `helpers-02` e `batch-B`.

## 2. Pré-requisitos duros (gate do PR)

Aplica só se todos verdadeiros:

1. `SEC-001` release train R1–R10 concluído.
2. `SEC-002.helpers-02.migration` **aplicada** — `user_in_empresa`, `user_in_obra`, `user_in_board`, `user_in_card` existem, têm `grant execute` para `authenticated` e não têm `grant execute` para `anon`.
3. `SEC-002.batch-B.migration` **em produção há ≥ 24 h sem regressão RLS**.
4. `SEC-002.tests-02.suite/helpers/*` **verde** em staging (15/15 asserts PASS).
5. `SEC-002.tests-02.suite/batch-C/*` **verde** em staging contra este mesmo arquivo (92/92 asserts PASS).
6. Snapshot lógico do banco criado ≤ 1 h antes do apply (runbook `SEC-001.backup-01`, reutilizado).
7. Nenhuma policy de `batch-D/E` em produção — ordem canônica B → C → D → E.

Se qualquer item falhar, PR fechado sem merge.

## 3. Estrutura do arquivo

Uma transação. Ordem estrita por tabela, com todas as 23 tabelas no mesmo `begin/commit`:

```text
begin;
  -- para cada tabela (§6 do batch-C.spec-01):
  --   1. drop policy if exists <policy_atual_n> on public.<tabela>;  (todas as atuais)
  --   2. create policy "<tabela>_select_..." on public.<tabela> ... ;
  --   3. create policy "<tabela>_write_..."  on public.<tabela> ... ;
  --   4. alter table public.<tabela> enable row level security;
  --   5. revoke all on public.<tabela> from anon;
  --   6. grant select, insert, update, delete on public.<tabela> to authenticated;
  --   7. grant all on public.<tabela> to service_role;
  notify pgrst, 'reload schema';
commit;
```

Transação única. Sem `commit` intermediário — falha em qualquer tabela reverte o lote inteiro.

## 5. Enumeração das policies atuais para `drop policy if exists`

O PR de execução obriga, **antes de escrever o SQL**, uma extração literal da lista de policies vigente por tabela via:

```sql
select tablename, policyname
from   pg_policies
where  schemaname = 'public'
  and  tablename in (<23 tabelas>)
order  by tablename, policyname;
```

O resultado alimenta o bloco `drop policy if exists "<policyname>" on public.<tabela>;` para cada linha. `if exists` mantém idempotência e evita assumir nomes legados.

## 6. Materialização por classe

Cada tabela deve terminar com exatamente **2 policies**: uma de leitura e uma de escrita. As expressões abaixo são o contrato mínimo; nomes devem seguir `SEC-002.batch-C.spec-01`.

### 6.1 OBRA-DIRECT

Aplicado a:

```text
aditivos_contrato, bms_previstas, bms_redistribuicao, cronograma_baselines,
cronograma_dependencias, cronograma_itens, cronograma_marcos,
cronograma_revisoes, medicoes, mobilizacoes_periodos, ocorrencias, riscos
```

Contrato:

```sql
using (public.user_in_obra(auth.uid(), obra_id))
with check (public.user_in_obra(auth.uid(), obra_id))
```

### 6.2 OBRA-VIA-PARENT

Aplicado a:

| Tabela | Parent | FK |
|--------|--------|----|
| `cronograma_item_baseline` | `cronograma_itens` | `cronograma_item_id` |
| `cronograma_item_revisoes` | `cronograma_itens` | `cronograma_item_id` |
| `itens_medicao` | `medicoes` | `medicao_id` |

Contrato:

```sql
exists (
  select 1
  from public.<parent_tbl> p
  where p.id = <tabela>.<parent_fk>
    and public.user_in_obra(auth.uid(), p.obra_id)
)
```

Mesma expressão no `USING` e no `WITH CHECK`.

### 6.3 EMPRESA-VIA-OBRA

Aplicado a:

| Tabela | Role de escrita |
|--------|-----------------|
| `colaboradores` | `dp` |
| `patrimonios` | `patrimonio` |
| `veiculos` | `frota` |

Leitura:

```sql
(
  (obra_atual_id is null and public.current_is_gm())
  or exists (
    select 1
    from public.obras o
    where o.id = <tabela>.obra_atual_id
      and public.user_in_empresa(auth.uid(), o.empresa_id)
  )
)
```

Escrita:

```sql
(
  public.current_is_gm()
  or (
    exists (
      select 1
      from public.obras o
      where o.id = <tabela>.obra_atual_id
        and public.user_in_empresa(auth.uid(), o.empresa_id)
    )
    and public.has_role(auth.uid(), '<role_dominio>')
  )
)
```

`colaboradores` usa apenas `dp` neste arquivo. Inclusão de `rh` depende de decisão D-1 e exige errata explícita antes da execução.

### 6.4 Exceções nominais obrigatórias

- **`licoes_aprendidas`:** `SELECT` por empresa da obra; `WRITE` por `user_in_obra(auth.uid(), obra_id)`.
- **`obra_membros`:** `SELECT` por `user_in_obra(auth.uid(), obra_id)`; `WRITE` **GM-only** com `public.current_is_gm()` no `USING` e no `WITH CHECK`.
- **`obras`:** `SELECT` por `user_in_empresa(auth.uid(), empresa_id)`; `WRITE` exige `current_is_gm()` ou `user_in_empresa(auth.uid(), empresa_id) and has_role(auth.uid(), 'obras')`.
- **`responsabilidades_patrimonios`:** escopo por `patrimonio_id → patrimonios.obra_atual_id → obras.empresa_id`; `WRITE` exige `current_is_gm()` ou escopo + `has_role(auth.uid(), 'patrimonio')`.
- **`mobilizacoes_veiculos`:** `SELECT` por `user_in_obra(auth.uid(), obra_id)`; `WRITE` exige `user_in_obra(auth.uid(), obra_id)` **e** `current_is_gm() or has_role(auth.uid(), 'frota')`. Esta regra resolve formalmente o R5 de `SEC-002.batch-C.spec-01` §11.

## 7. Grants finais (repetição obrigatória por tabela)

Bloco padrão aplicado às **23** tabelas:

```sql
revoke all on public.<tabela> from anon;
grant select, insert, update, delete on public.<tabela> to authenticated;
grant all on public.<tabela> to service_role;
```

Nenhum `grant` a `anon` em qualquer tabela do lote.

## 8. Verificações pós-migração (obrigatórias no gate)

Após `commit`, executar em janela read-only:

```sql
-- 8.1 RLS habilitado nas 23 tabelas
select relname, relrowsecurity
from   pg_class
where  relnamespace = 'public'::regnamespace
  and  relname in (<23 tabelas>);
-- oráculo: relrowsecurity = true em todas

-- 8.2 Contagem de policies: exatamente 2 por tabela
select tablename, count(*) as n_policies
from   pg_policies
where  schemaname='public'
  and  tablename in (<23 tabelas>)
group  by tablename
order  by tablename;
-- oráculo: 23 linhas, n_policies = 2 em todas

-- 8.3 anon sem privilégio de DML em nenhuma das 23
select table_name, privilege_type
from   information_schema.role_table_grants
where  table_schema='public'
  and  grantee='anon'
  and  table_name in (<23 tabelas>);
-- oráculo: 0 linhas

-- 8.4 authenticated tem os 4 privilégios nas 23
select table_name, string_agg(privilege_type, ',' order by privilege_type)
from   information_schema.role_table_grants
where  table_schema='public'
  and  grantee='authenticated'
  and  table_name in (<23 tabelas>)
group  by table_name;
-- oráculo: 'DELETE,INSERT,SELECT,UPDATE' em todas

-- 8.5 policies dependem dos helpers esperados
select tablename, policyname, qual, with_check
from   pg_policies
where  schemaname='public'
  and  tablename in (<23 tabelas>)
order  by tablename, policyname;
-- oráculo: sem USING(true), sem auth.uid() is not null permissivo,
--          e referências a user_in_obra/user_in_empresa/current_is_gm/has_role conforme §6
```

Qualquer discrepância aborta o release e dispara o rollback §9.

## 9. Rollback

Companion `SEC-002.batch-C.rollback.sql`, executável em transação única:

```sql
begin;
  -- para cada tabela do lote:
  drop policy if exists "<tabela>_select_..." on public.<tabela>;
  drop policy if exists "<tabela>_write_..."  on public.<tabela>;

  -- recria a policy legada permissiva conforme baseline do inventário-02:
  create policy "<tabela>_authenticated_all"
    on public.<tabela>
    for all
    to authenticated
    using (true)
    with check (true);
commit;
```

Grants **não** são revertidos — permanecem coerentes com o esquema atual. Rollback só é seguro se `batch-D/E` ainda não tiverem sido aplicados.

## 10. Invariantes do PR (checklist)

- [ ] Um único `begin;` … `commit;`.
- [ ] 23 blocos de tabela na ordem alfabética de §4.
- [ ] Cada bloco: `drop policy if exists` × N atuais, `create policy` × 2 (select + write), `alter table ... enable rls`, 3 grants.
- [ ] `licoes_aprendidas`, `obra_membros`, `obras`, `responsabilidades_patrimonios` e `mobilizacoes_veiculos` seguem §6.4.
- [ ] Zero `grant ... to anon`.
- [ ] Zero policy com `USING (true)` ou `auth.uid() is not null` permissivo.
- [ ] Zero alteração fora de `supabase/migrations/` no PR de execução.
- [ ] Suíte `batch-C` verde no CI antes do merge (92/92 asserts).
- [ ] Snapshot lógico anexado ao PR.

## 11. Riscos

- **R1: join em policies degrada listagens grandes.** Mitigação: validar planos para `cronograma_item_*`, `itens_medicao` e `responsabilidades_patrimonios`; helpers são `stable security definer` e os FKs/PKs usados já devem estar indexados no gate.
- **R2: `obra_atual_id IS NULL` some para usuários não-GM.** Mitigação: comportamento intencional; telas operacionais devem tratar itens sem obra como fila administrativa GM.
- **R3: `obra_membros` GM-only bloqueia gestão por coordenadores.** Mitigação: deliberado para evitar auto-promoção; delegação futura exige role própria e nova policy.
- **R4: `colaboradores` usa `dp` e não `rh`.** Mitigação: D-1 decide se `rh` entra; sem decisão, `dp` é o domínio canônico.
- **R5: PostgREST cacheia policies antigas.** Mitigação: `notify pgrst, 'reload schema';` no final da migração.

## 12. Impacto em produção

**Nenhum neste changeset.** Documento de especificação do arquivo. A execução real (`SEC-002.batch-C.migration`) é changeset seguinte, com seu próprio gate.
