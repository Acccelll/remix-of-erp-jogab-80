# SEC-002.apply-map-01 — Contrato canônico do mapa de applies

**Onda:** 2 (bloqueada — depende de `SEC-001` fechar)  
**Data:** 2026-07-12  
**Tipo:** especificação (contrato) — **nenhum código de produção alterado**  
**Depende de:** `SEC-002.apply-template-01.spec-01`, `SEC-002.go-no-go-01.spec-01`, `SEC-002.evidence-archive-01.spec-01`, `SEC-002.errata-policy-01.spec-01`  
**Materializa:** `.github/sec002-apply-map.json` + `scripts/sec002/load-apply-map.mjs` + adaptação dos validadores `validate-*` para consumir o mapa canônico

## 1. Objetivo

Definir um **mapa canônico único** para todos os applies de `SEC-002`, eliminando divergência entre specs e validadores que hoje referenciam caminhos distintos (`scripts/sec002/sec002-apply-map.json` vs `.github/sec002-apply-map.json`).

O mapa deve ser a fonte de verdade para:

1. ordem de execução dos applies;
2. quantidade esperada de asserts por apply;
3. batch de staging esperado;
4. paths permitidos por PR;
5. critérios específicos de go/no-go;
6. evidências mínimas de archive;
7. regras de errata por target.

Sem esse contrato, validadores independentes podem aprovar PRs com interpretações diferentes do mesmo apply.

## 2. Decisão canônica

O arquivo oficial é:

```text
.github/sec002-apply-map.json
```

Regras:

1. `scripts/sec002/sec002-apply-map.json` fica **proibido** como fonte primária.
2. Validadores devem carregar o mapa por `scripts/sec002/load-apply-map.mjs`.
3. Qualquer spec anterior que mencione `scripts/sec002/sec002-apply-map.json` deve ser tratada como referência histórica e substituída na materialização.
4. O mapa é versionado, revisado por PR e lido somente em CI; não entra no bundle da aplicação.

## 4. Invariantes

| id | Regra | Oráculo |
|----|-------|---------|
| M1 | `schema_version` obrigatório | string ISO-like versionada |
| M2 | `sec002_status` não pode ser `OPEN` enquanto `SEC-001` estiver em NO-GO | `BLOCKED_BY_SEC001` |
| M3 | `order` é sequencial e único | `1..6` sem lacunas |
| M4 | `expected_asserts` bate com specs de lote | 15, 331, 39, 92, 75, 110 |
| M5 | `staging_batch` é `none` para `helpers-02`/`tests-02-suite` | sem refresh obrigatório |
| M6 | `staging_batch` é `B/C/D/E` para lotes reais | paridade obrigatória |
| M7 | `allowed_paths` nunca inclui `src/**` | apply RLS não altera frontend |
| M8 | `allowed_paths` nunca inclui schemas proibidos | `auth`, `storage`, `realtime`, `supabase_functions`, `vault` |
| M9 | `required_evidence_categories` contém `acceptance` para todo apply | handoff depende disso |
| M10 | todo critério específico existe em `SEC-002.go-no-go-01.spec-01` | sem critério órfão |

Falha em qualquer invariante ⇒ CI vermelho.

## 5. Consumidores obrigatórios

Os seguintes scripts/validadores devem carregar o mapa canônico:

| Consumidor | Uso do mapa |
|------------|-------------|
| `validate-pr-checklist.mjs` | ids válidos, assert count esperado, seções obrigatórias |
| `validate-changed-files.mjs` | `allowed_paths`, bloqueio de lotes cruzados, proibição de `src/**` |
| `validate-staging-parity.mjs` | `staging_batch`, `requires_staging_parity` |
| `validate-go-no-go.mjs` | critérios específicos por apply, validade de decisão |
| `validate-acceptance-gates.mjs` | assert count, gates específicos, liberação entre lotes |
| `validate-evidence-archive.mjs` | evidências mínimas, asserts, categorias obrigatórias |
| `validate-errata.mjs` | `target_apply_id` válido e categoria permitida |
| `sec002-freeze-guard` | exceções permitidas por apply/errata |

Nenhum consumidor deve manter cópia local do mapa.

## 6. Loader compartilhado

Materialização futura cria `scripts/sec002/load-apply-map.mjs` com contrato:

```js
import { loadApplyMap, getApply, listApplies } from './load-apply-map.mjs';

const map = loadApplyMap();
const apply = getApply('batch-C');
const applies = listApplies();
```

Regras do loader:

1. resolve sempre a partir da raiz do repositório;
2. lê `.github/sec002-apply-map.json`;
3. valida `schema_version` e invariantes mínimas antes de retornar;
4. não faz rede;
5. não lê secrets;
6. em erro, imprime mensagem determinística e retorna `exit 1` quando chamado por CLI.

## 7. Validador do mapa

Materialização futura cria `scripts/sec002/validate-apply-map.mjs`.

Assinatura:

```bash
node scripts/sec002/validate-apply-map.mjs --file .github/sec002-apply-map.json
```

Verificações determinísticas:

1. JSON válido;
2. todos os applies obrigatórios existem;
3. nenhum apply extra sem spec correspondente;
4. `order` sequencial;
5. assert counts iguais aos specs;
6. `allowed_paths` não contém `src/**` nem paths fora do escopo `SEC-002`;
7. `specific_criteria` existem no mapa de critérios do `go-no-go`;
8. `requires_staging_parity=true` para `batch-*`;
9. categorias de evidência pertencem à taxonomia do `evidence-archive`;
10. nenhum placeholder (`TODO`, `<...>`, `TBD`).

Saída de falha:

```text
SEC002_APPLY_MAP_FAILED
- invalid_order: batch-D expected 5 got 6
- forbidden_path: src/App.tsx
- missing_evidence_category: batch-C acceptance
```

## 8. Integração com CI

O workflow `sec002-pr-checklist` ganha primeiro step lógico:

```yaml
- name: Validate SEC-002 apply map
  run: node scripts/sec002/validate-apply-map.mjs --file .github/sec002-apply-map.json
```

Ordem recomendada:

```text
1. validate-apply-map
2. validate-pr-checklist
3. validate-changed-files
4. validate-staging-parity
5. validate-go-no-go
6. validate-acceptance/evidence quando aplicável
```

Se o mapa falhar, todos os gates dependentes devem ser considerados inválidos.

## 9. Interação com errata

Erratas não adicionam novos applies ao mapa.

Regras:

1. `target_apply_id` da errata deve existir em `.github/sec002-apply-map.json`.
2. Errata pode alterar o conteúdo de um apply existente, mas não pode mudar `order` nem `expected_asserts` retroativamente.
3. Se uma errata exigir novo assert permanente, isso deve virar novo changeset fora do apply original, com atualização explícita do mapa em PR operacional próprio.
4. Errata `severity ∈ {high, critical}` pode referenciar o mapa para justificar `freeze.exception-<n>`.

## 10. Interação com handoff e evidence

O handoff pós-RLS só pode entrar em `READY` se:

1. todos os applies listados no mapa tiverem acceptance válida;
2. todos os manifests de evidence existirem para os applies do mapa;
3. a suíte final consolidada bater com `expected_asserts=331` do `tests-02-suite`;
4. não houver apply no mapa com `requires_acceptance=true` sem artefato `.github/sec002-acceptance/<apply-id>.md`.

O evidence archive deve registrar o `schema_version` do mapa usado em cada manifest.
