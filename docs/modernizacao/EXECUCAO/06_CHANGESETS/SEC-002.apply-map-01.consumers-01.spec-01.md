# SEC-002.apply-map-01.consumers-01.spec-01 — Refatoração dos consumidores para fonte única

**Onda:** 2 (bloqueada — depende de `SEC-001` fechar e da abertura formal da Onda 2)  
**Data:** 2026-07-12  
**Depende de:** `SEC-002.apply-map-01.spec-01` (R40), `SEC-002.apply-map-01.materialize-01` (R41)  
**Escopo:** especificar formalmente como cada validador e workflow SEC-002 deve consumir exclusivamente `scripts/sec002/load-apply-map.mjs`, eliminando toda lista, contagem ou path duplicado. **Nenhum arquivo de produção alterado.** Materialização em changesets posteriores por consumidor.

## 1. Racional

R40 e R41 estabeleceram fonte única (`.github/sec002-apply-map.json` + loader). Sem esta refatoração normativa, cada validador poderia reintroduzir sua própria cópia (assert count, allowed_paths, apply order), reproduzindo o problema que R40 resolveu. Este documento congela o **contrato de consumo**: o que cada consumidor lê do map, o que jamais deve hardcodear, e como falha se o map estiver ausente.

## 2. Regra geral de consumo (C1–C7)

- **C1 Import único.** Todo consumidor Node importa apenas de `./load-apply-map.mjs` (ou path relativo equivalente). Proibido `readFileSync('.github/sec002-apply-map.json')` fora do loader.
- **C2 Zero hardcode.** Proibidos, no código do consumidor, literais: `apply_id` (`"helpers-02"`, `"batch-B"`, …), `expected_asserts` (`15`, `39`, `92`, `75`, `110`, `331`, `462`), `staging_batch` (`"B"`..`"E"`), `specific_criteria` (`"B1"`, `"C3"`, …), `required_evidence_categories`, `allowed_paths` de apply.
- **C3 Fail-closed.** Se `loadApplyMap()` lançar (arquivo ausente, schema_version divergente, JSON inválido), o consumidor sai com código `1` e mensagem `[sec002/<consumer>] apply-map indisponível: <erro>`. Nunca degrada silenciosamente.
- **C4 Sem cache paralelo.** Consumidores não replicam o `_cache` do loader; chamam `loadApplyMap()`/`getApply()`/`listApplies()` diretamente.
- **C5 Erro de `apply_id` desconhecido é fatal.** `getApply(id)` já lança; consumidores não capturam essa exceção — propagam.
- **C6 Ordem canônica.** Iterações que exijam ordem usam `listApplies()` (já ordenado por `order`); proibido `sort()` local.
- **C7 Workflows YAML.** Workflows GitHub Actions consomem o map indiretamente via scripts Node; não lêem o JSON com `jq` diretamente (evita segunda implementação de validação).

## 3. Contrato por consumidor

| Consumidor | Lê do map | Não pode hardcodear |
|---|---|---|
| `validate-pr-checklist.mjs` | `getApply(applyId)` → `expected_asserts`, `specific_criteria`, `required_evidence_categories`, `requires_staging_parity`, `requires_comms`, `requires_acceptance` | contagem de asserts, IDs de critérios, categorias de evidência |
| `validate-changed-files.mjs` | `getApply(applyId).allowed_paths` | qualquer glob por apply |
| `validate-staging-parity.mjs` | `getApply(applyId).requires_staging_parity`, `.staging_batch` | mapa apply→batch |
| `validate-go-no-go.mjs` | `getApply(applyId).specific_criteria`, `.kind` | lista `B1..E6` |
| `validate-acceptance-gates.mjs` | `getApply(applyId).requires_acceptance`, `.kind`, `.closes_sec002` | quais applies exigem aceite |
| `validate-evidence-archive.mjs` | `getApply(applyId).required_evidence_categories`, `.expected_asserts` | mínimos de evidência por apply |
| `validate-errata.mjs` | `listApplies().map(a=>a.apply_id)` para validar `target_apply_id` | lista de apply_ids válidos |
| `validate-post-rls-handoff.mjs` | `listApplies()`, `totals.final_rls_suite_asserts`, `closes_sec002` | 331, lista final de applies |
| `sec002-freeze-guard` (workflow) | via script Node que chama `listApplies()` para determinar contexto de exceção | apply_ids em YAML |
| `sec002-pr-checklist` (workflow) | via `validate-pr-checklist.mjs` (não lê o JSON diretamente) | qualquer campo do map |

## 4. Padrão de erro unificado

Todo consumidor emite falhas no formato:

```
[sec002/<consumer>] FAIL
 - <invariante ou campo> em <apply_id|contexto>: <detalhe>
```

E sucesso:

```
[sec002/<consumer>] OK
```

Códigos de saída: `0` sucesso, `1` falha de invariante, `2` erro operacional (I/O, JSON). Nenhum outro código.

## 5. Invariantes de refatoração (R1–R6) — verificáveis por grep

Executáveis em CI (ex.: `sec002-consumers-guard`):

- **R1** `rg -n "sec002-apply-map\.json" scripts/sec002` retorna **apenas** `scripts/sec002/load-apply-map.mjs`.
- **R2** `rg -n "readFileSync\(.*sec002-apply-map" scripts/sec002` retorna **apenas** `load-apply-map.mjs`.
- **R3** `rg -nw "(helpers-02|tests-02-suite|batch-B|batch-C|batch-D|batch-E)" scripts/sec002` só aparece em strings de mensagem/log, nunca em estruturas de controle (`switch`/`if`) — validado por regra AST no changeset de materialização.
- **R4** `rg -nw "(15|39|92|75|110|331|462)" scripts/sec002` não aparece em `validate-*.mjs` (apenas em `load-apply-map.mjs` como parte de testes, se houver).
- **R5** `rg -n "jq .*sec002-apply-map" .github/workflows` sem matches.
- **R6** Cada `validate-*.mjs` importa `load-apply-map.mjs` (grep obrigatório).

## 6. Ordem de materialização

Cada consumidor recebe um changeset próprio `SEC-002.<consumer>.materialize-01.md` que:

1. Reescreve o script para consumir o loader conforme §3.
2. Prova §5 (R1–R6) na sua parcela.
3. Registra evidência categoria `decision` com hash do arquivo resultante.

Ordem recomendada: `validate-changed-files` → `validate-pr-checklist` → `validate-staging-parity` → `validate-go-no-go` → `validate-acceptance-gates` → `validate-evidence-archive` → `validate-errata` → `validate-post-rls-handoff` → workflows.

## 7. Impacto em produção

**Nenhum.** Especificação normativa. Não altera `src/`, `supabase/functions/` ou `supabase/migrations/`, nem grava arquivos em `.github/` ou `scripts/sec002/`.
