# SEC-002.batch-E.spec-01 — Políticas-alvo do Lote E (boards & cards)

**Onda:** 2 (preparatória — bloqueada por fechamento de `SEC-001` e migrations B/C/D)  
**Data:** 2026-07-12  
**Escopo:** especifica o **conjunto atômico de políticas** que substituirá as políticas atuais das **22 tabelas do Lote E** conforme `SEC-002.inventory-02` §3. Nenhuma migração é aplicada; **este é o contrato SQL** que a migração `SEC-002.batch-E.migration` executará, sob gate, depois dos lotes B/C/D e dos helpers `user_in_board`/`user_in_card` (`SEC-002.helpers-01`). Nenhum código de produção é alterado.

## 1. Escopo

Tabelas cobertas (22):

```text
board_campos              card_custom_field_valores  card_membros_externos
board_listas              card_grupos_negociacao     card_recursos
board_membros             card_label_links           card_secoes_visiveis
boards                    card_labels                card_setores
card_anexos               card_local                 card_views_salvas
card_atividades           card_membros               cards
card_board_posicao
card_campos_valores
card_checklist_itens
card_comentarios
```

Fora do escopo: qualquer tabela dos lotes B/C/D, telemetria/QR público (avaliada em `SEC-002.f`) e alterações estruturais de colunas. Este changeset só define RLS alvo.

## 2. Pré-requisitos duros

A migração `SEC-002.batch-E.migration` só entra depois de, em ordem:

1. `SEC-002.batch-B.migration` **em produção há ≥ 24 h sem regressão RLS**.
2. `SEC-002.batch-C.migration` **em produção há ≥ 24 h sem regressão RLS**.
3. `SEC-002.batch-D.migration` **em produção há ≥ 24 h sem regressão RLS**.
4. `SEC-002.helpers-02.migration` **aplicada** — inclui `public.user_in_board` e `public.user_in_card` (`SEC-002.helpers-01`).
5. `SEC-001.k` concluído — RBAC server-sourced; `currentPlayer.isGM` não é autoridade.
6. Suíte `SEC-002.tests-02.suite/batch-E/*` **verde** (110 asserts; ver §9).

Se qualquer passo falhar, a migração aborta.

## 4. Padrões de regra por classe

Cinco padrões apenas. Toda tabela do lote mapeia para exatamente um em §6.

### 4.1 Padrão **BOARD-SCOPE**

Aplicável a estruturas de board (listas, campos, seções, labels e posições). Leitura/escrita por membros do board; GM bypass.

```sql
create policy "<tabela>_select_board"
  on public.<tabela>
  for select
  to authenticated
  using (
    public.current_is_gm()
    or public.user_in_board(auth.uid(), board_id)
  );

create policy "<tabela>_write_board"
  on public.<tabela>
  for all
  to authenticated
  using (
    public.current_is_gm()
    or public.user_in_board(auth.uid(), board_id)
  )
  with check (
    public.current_is_gm()
    or public.user_in_board(auth.uid(), board_id)
  );
```

### 4.2 Padrão **CARD-SCOPE**

Aplicável a filhos diretos de `cards` com `card_id uuid`. Membros do card leem/escrevem; GM bypass.

```sql
create policy "<tabela>_select_card"
  on public.<tabela>
  for select
  to authenticated
  using (
    public.current_is_gm()
    or public.user_in_card(auth.uid(), card_id)
  );

create policy "<tabela>_write_card"
  on public.<tabela>
  for all
  to authenticated
  using (
    public.current_is_gm()
    or public.user_in_card(auth.uid(), card_id)
  )
  with check (
    public.current_is_gm()
    or public.user_in_card(auth.uid(), card_id)
  );
```

### 4.3 Padrão **CARDS-ROOT**

Aplicável apenas a `public.cards`. Escopo canônico é o próprio card: membros diretos (`card_membros`) e membros do board onde o card está posicionado (`card_board_posicao` → `boards`).

```sql
create policy "cards_select_scoped"
  on public.cards
  for select
  to authenticated
  using (
    public.current_is_gm()
    or responsavel_id = auth.uid()
    or public.user_in_card(auth.uid(), id)
    or exists (
      select 1
      from public.card_board_posicao p
      where p.card_id = cards.id
        and public.user_in_board(auth.uid(), p.board_id)
    )
    or (obra_id is not null and public.user_in_obra(auth.uid(), obra_id))
  );

create policy "cards_insert_member"
  on public.cards
  for insert
  to authenticated
  with check (
    public.current_is_gm()
    or (obra_id is null or public.user_in_obra(auth.uid(), obra_id))
  );

create policy "cards_update_member"
  on public.cards
  for update
  to authenticated
  using (
    public.current_is_gm()
    or responsavel_id = auth.uid()
    or public.user_in_card(auth.uid(), id)
  )
  with check (
    public.current_is_gm()
    or responsavel_id = auth.uid()
    or public.user_in_card(auth.uid(), id)
  );

create policy "cards_delete_owner"
  on public.cards
  for delete
  to authenticated
  using (
    public.current_is_gm()
    or responsavel_id = auth.uid()
  );
```

### 4.4 Padrão **BOARDS-ROOT**

Aplicável apenas a `public.boards`. Escopo: owner, membros do board, escopo de obra (quando `obra_id` presente), GM.

```sql
create policy "boards_select_scoped"
  on public.boards
  for select
  to authenticated
  using (
    public.current_is_gm()
    or owner_id = auth.uid()
    or public.user_in_board(auth.uid(), id)
    or (obra_id is not null and public.user_in_obra(auth.uid(), obra_id))
  );

create policy "boards_insert_authenticated"
  on public.boards
  for insert
  to authenticated
  with check (
    public.current_is_gm()
    or (owner_id = auth.uid()
        and (obra_id is null or public.user_in_obra(auth.uid(), obra_id)))
  );

create policy "boards_update_owner"
  on public.boards
  for update
  to authenticated
  using (public.current_is_gm() or owner_id = auth.uid())
  with check (public.current_is_gm() or owner_id = auth.uid());

create policy "boards_delete_owner"
  on public.boards
  for delete
  to authenticated
  using (public.current_is_gm() or owner_id = auth.uid());
```

### 4.5 Padrão **OWNER-SELF**

Aplicável a artefatos individuais do usuário (`card_views_salvas`, `card_membros`, `card_membros_externos`, `card_comentarios` — variantes em §6).

```sql
create policy "<tabela>_select_self"
  on public.<tabela>
  for select
  to authenticated
  using (public.current_is_gm() or <owner_column> = auth.uid());

create policy "<tabela>_write_self"
  on public.<tabela>
  for all
  to authenticated
  using (public.current_is_gm() or <owner_column> = auth.uid())
  with check (public.current_is_gm() or <owner_column> = auth.uid());
```

## 5. Estrutura atômica da migração

Mesmo shape de `SEC-002.batch-B/C/D.spec-01`:

```sql
begin;
  -- por tabela:
  drop policy if exists "<policy_atual_1>" on public.<tabela>;
  drop policy if exists "<policy_atual_2>" on public.<tabela>;
  ...
  create policy "<tabela>_select_..." on public.<tabela> ...;
  create policy "<tabela>_write_..."  on public.<tabela> ...;

  alter table public.<tabela> enable row level security;
  revoke all on public.<tabela> from anon;
  grant select, insert, update, delete on public.<tabela> to authenticated;
  grant all on public.<tabela> to service_role;
commit;
```

**Transação única** para as 22 tabelas. Sem `commit` intermediário.

## 7. Exceções nominais

- **`boards`.** `INSERT` exige `owner_id = auth.uid()` (ou GM). Impede que um usuário crie board em nome de outro.
- **`board_membros`.** `INSERT/UPDATE` de linhas alheias só para GM ou owner do board (`exists (select 1 from public.boards b where b.id = board_membros.board_id and b.owner_id = auth.uid())`). `DELETE` permitido a GM, owner do board ou ao próprio membro (`user_id = auth.uid()`). Nenhum membro adiciona a si mesmo.
- **`card_membros`.** Simétrico a `board_membros`, mas o proprietário do card é `cards.responsavel_id`. `DELETE` permitido a GM, responsável ou ao próprio membro.
- **`card_membros_externos`.** Somente GM ou `cards.responsavel_id = auth.uid()` para `INSERT/UPDATE/DELETE`. `SELECT` segue CARD-SCOPE.
- **`card_comentarios`.** `INSERT` exige `autor_id = auth.uid()` e `user_in_card(auth.uid(), card_id)`. `UPDATE/DELETE` só GM ou `autor_id = auth.uid()`.
- **`card_atividades`.** Log operacional; `INSERT` por qualquer membro do card com `autor_id = auth.uid()`. `UPDATE/DELETE` só GM ou `autor_id = auth.uid()` — logs não devem ser silenciosamente sobrescritos.
- **`card_views_salvas`.** Não conceder `SELECT` compartilhado; view salva é privada.
- **QR/público.** Nenhuma tabela deste lote recebe acesso público. Fluxos QR/token, se surgirem, entram em `SEC-002.f` com policy de coluna/ação mínima e justificativa registrada.

## 8. Grants finais

Bloco reafirmado no final da migração para todas as 22 tabelas:

```sql

grant select, insert, update, delete on public.<tabela> to authenticated;
grant all on public.<tabela> to service_role;
```

Nenhuma tabela do lote recebe `grant` a `anon`.

Helpers reaproveitados (já grant-adados em `SEC-002.helpers-02.migration`):

```text
public.user_in_board(uuid, uuid)
public.user_in_card(uuid, uuid)
public.user_in_obra(uuid, uuid)
public.current_is_gm()

```

Este lote **não** cria helpers novos.

## 9. Cobertura de teste (gate)

- Lote E ⇒ **110 asserts** (22 tabelas × 5 casos: `gm`, `member`, `outsider`, `anon`, `ownership`).
- Confere o total global reconciliado em `SEC-002.batch-D.spec-01` §9: **331 asserts** = B39 + C92 + D75 + E110 + H15.

Casos obrigatórios específicos:

| Caso | Oráculo adicional |
|------|-------------------|
| `member` board | usuário em `board_membros` acessa `board_*`, `card_labels`, `card_secoes_visiveis`, `card_setores`, `card_board_posicao` do board |
| `member` card | usuário em `card_membros` acessa filhos de `cards` (`card_anexos`, `card_atividades`, etc.) e o próprio card |
| `outsider` | usuário autenticado sem vínculo recebe `SELECT=0` e escrita bloqueada em todas as 22 tabelas |
| `anon` | `SELECT/INSERT/UPDATE/DELETE` bloqueados em todas as 22 tabelas |
| `ownership` | não-owner tenta `UPDATE`/`DELETE` de `boards`, `card_views_salvas`, `card_comentarios` alheios: afeta 0 linhas ou falha por RLS |

## 10. Reversão

Companion `SEC-002.batch-E.rollback.sql` refaz as políticas do inventário-02 (`USING(true)`/`WITH CHECK(true)` para authenticated) para as 22 tabelas. Uso exclusivo para incidente de produção e aprovação de D-9.

Rollback **não** remove helpers `user_in_board`/`user_in_card` se já existirem, apenas deixa de usá-los nas policies revertidas.

## 11. Riscos

- **R1: cascata de leituras via `user_in_card`.** Cada `SELECT` em filho de card faz lookup em `card_membros`. Mitigação: gate deve validar índice em `card_membros(card_id, user_id)` e `board_membros(board_id, user_id)` antes do `SEC-002.batch-E.migration`.
- **R2: cards órfãos.** `cards` sem `card_board_posicao` e sem `card_membros` ficam invisíveis a não-GM. Mitigação: script pré-migração conta órfãos; se >0, decidir entre fallback via `obra_id` (já embutido em §4.3) ou backfill de responsável.
- **R3: `card_views_salvas` privada.** Se produto quiser compartilhamento de views, exige coluna de escopo (`board_id`/`obra_id`) — changeset próprio, fora do E.
- **R4: `card_atividades` como append-only.** Sem trigger, apenas RLS impede overwrite alheio; overwrite pelo próprio autor continua possível. Correção definitiva exige trigger `BEFORE UPDATE/DELETE` ou coluna `imutavel_apos timestamp`.
- **R5: divergência entre membros de board e membros de card.** Membro do board vê estrutura (`board_*`, labels, seções), mas não conteúdo do card se não estiver em `card_membros`. Comportamento intencional; documentar em `SEC-002.f`.

## 12. Impacto em produção

**Nenhum neste changeset.** Documento de especificação. A migração real (`SEC-002.batch-E.migration`) e a suíte (`SEC-002.tests-02.suite/batch-E`) são changesets seguintes, cada um sujeito ao próprio gate.
