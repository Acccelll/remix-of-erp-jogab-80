**Onda:** 0 · **Categoria:** Operação/Recuperação · **Prioridade:** P1 · **Criticidade:** C1

> **Status:** `.a` entregue. Os itens (d)–(f) da seção 5 pertencem agora a `OPS-006.b` (Onda 7) e **não bloqueiam** o Stage Gate da Onda 0.

## 1. Problema

- Backup do host MySQL não evidenciado — risco real de perda dos cadastros-núcleo.
- Rollback de schema não coordenado com o revert de frontend (reverter commit no Lovable não reverte migration).
- Sem procedimento escrito → qualquer tentativa de recuperação hoje é improvisada.

## 2. Entregues nesta sessão

| Artefato          | Caminho                | Papel                                                                                                             |
| ----------------- | ---------------------- | ----------------------------------------------------------------------------------------------------------------- |
| Script de backup  | `ops/mysql-backup.sh`  | `mysqldump` consistente (InnoDB, `--single-transaction`), compressão gzip, checksum SHA-256, rotação por retenção |
| Script de restore | `ops/mysql-restore.sh` | Validação de checksum, confirmação manual em bases `*prod*`, restore idempotente                                  |
| Runbook           | este documento         | Procedimento operacional, agendamento, teste de restore, rollback coordenado                                      |

Ambos os scripts leem credenciais **apenas via variáveis de ambiente**. Nenhuma senha em disco, nenhuma no repositório.

## 3. Runbook operacional (executar no host)

### 3.1. Pré-requisitos no host

- MySQL client 8.x (`mysqldump`, `mysql`).
- Usuário MySQL dedicado ao backup com privilégios mínimos:
  ```sql
  CREATE USER 'gestaobra_backup'@'localhost' IDENTIFIED BY '<gerar>';
  GRANT SELECT, LOCK TABLES, SHOW VIEW, EVENT, TRIGGER, PROCESS, RELOAD
    ON gestaobra.* TO 'gestaobra_backup'@'localhost';
  FLUSH PRIVILEGES;
  ```
- Diretório de backup em partição separada com espaço ≥ 10× o tamanho atual da base.
- Credenciais em `/etc/gestaobra/backup.env` com `chmod 600` (não versionar).

### 3.2. Agendamento diário (systemd timer recomendado)

`/etc/systemd/system/gestaobra-backup.service`

```ini
[Unit]
Description=Backup diario MySQL GestaObra
After=network-online.target

[Service]
Type=oneshot
EnvironmentFile=/etc/gestaobra/backup.env
ExecStart=/opt/gestaobra/ops/mysql-backup.sh
User=gestaobra
Nice=10
```

`/etc/systemd/system/gestaobra-backup.timer`

```ini
[Unit]
Description=Backup diario MySQL GestaObra (02:15 UTC)

[Timer]
OnCalendar=*-*-* 02:15:00 UTC
Persistent=true
RandomizedDelaySec=15m

[Install]
WantedBy=timers.target
```

Ativar: `systemctl enable --now gestaobra-backup.timer`.

Alternativa cron:

```cron
15 2 * * *  gestaobra  . /etc/gestaobra/backup.env && /opt/gestaobra/ops/mysql-backup.sh >> /var/log/gestaobra-backup.log 2>&1
```

### 3.3. Cópia off-host

O backup local **não é DR**. Espelhar `/var/backups/gestaobra` para armazenamento externo (S3/rclone/rsync) imediatamente após o dump. Exemplo:

```bash
ExecStartPost=/usr/bin/rclone copy /var/backups/gestaobra remote:gestaobra-backups --min-age 1m
```

### 3.4. Teste de restore (obrigatório, mensal)

1. Provisionar base descartável: `CREATE DATABASE gestaobra_restore_test;`
2. Restaurar o dump mais recente:
   ```bash
   MYSQL_DATABASE=gestaobra_restore_test ./ops/mysql-restore.sh /var/backups/gestaobra/gestaobra-<ts>.sql.gz
   ```
3. Validar contagens contra produção (mesmo dia):
   ```sql
   SELECT 'colaboradores', COUNT(*) FROM gestaobra_restore_test.colaboradores
   UNION ALL SELECT 'obras', COUNT(*) FROM gestaobra_restore_test.obras
   UNION ALL SELECT 'patrimonios', COUNT(*) FROM gestaobra_restore_test.patrimonios;
   ```
4. Registrar resultado em `docs/modernizacao/EXECUCAO/04_VALIDACAO/restore-log.md` (data, dump usado, contagens, OK/FALHA).
5. `DROP DATABASE gestaobra_restore_test;`

### 3.5. Rollback coordenado (frontend + schema)

Reverter um deploy no Lovable **não** desfaz migration executada no MySQL. Procedimento correto:

1. Identificar o último commit estável e a migration associada (cabeçalho da migration = ID do commit).
2. Se a migration é **aditiva** (nova coluna/tabela sem drop): reverter só o frontend; schema permanece compatível.
3. Se a migration é **destrutiva** (drop/rename/alter incompatível): **restaurar o dump imediatamente anterior** em base paralela `gestaobra_rollback`, promover troca:
   ```sql
   RENAME TABLE gestaobra.<tab> TO gestaobra.<tab>_broken,
                gestaobra_rollback.<tab> TO gestaobra.<tab>;
   ```
4. Reverter frontend no Lovable.
5. Publicar post-mortem em `docs/modernizacao/EXECUCAO/04_VALIDACAO/post-mortem-<data>.md`.

Toda migration destrutiva **deve** ser precedida de dump ad-hoc:

```bash
BACKUP_DIR=/var/backups/gestaobra/pre-migration ./ops/mysql-backup.sh
```

## 4. Credenciais e segurança

- Senha do usuário `gestaobra_backup` **nunca** aparece nos scripts, logs ou repositório.
- Rotação de credencial acompanha SEC-003 (mesma janela de troca).
- Arquivo `/etc/gestaobra/backup.env` com owner `root:gestaobra`, `chmod 640`.
- Backups em disco devem ficar em partição com criptografia at-rest quando disponível.
