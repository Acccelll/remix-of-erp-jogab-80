# OPS-006.b — Rollback coordenado front ↔ schema (Lovable Cloud / Supabase)

**Onda:** 3  
**Categoria:** Operação/Recuperação  
**Relacionado:** OPS-006.a (MySQL), DB-001 (fronteira), ARC-003 (repositories)  
**Status:** procedimento documentado (concluído). Execução real é feita sob incidente.

## 1. Problema

`OPS-006.a` cobre backup/rollback do MySQL legado. Faltava o análogo para o backend moderno (Lovable Cloud/Supabase): reverter um deploy no Lovable **não** desfaz migrations aplicadas no Postgres. Sem procedimento escrito, qualquer rollback de esquema atual é improvisado — o que viola o Contrato §1 e o critério de saída da Onda 3.

## 2. Classificação de migration

Toda migration é classificada **antes** de ser aplicada:

| Classe | Exemplos | Reversível sem restore? |
| --- | --- | --- |
| **Aditiva** | `CREATE TABLE`, `ADD COLUMN NULL`, `CREATE INDEX CONCURRENTLY`, `CREATE POLICY`, `GRANT` | Sim — basta reverter o frontend. Schema novo é ignorado pelo código antigo. |
| **Compatível** | `ADD COLUMN NOT NULL DEFAULT`, novo `CHECK NOT VALID`, novo trigger idempotente | Sim, com migration inversa (`DROP COLUMN`/`DROP CHECK`). |
| **Destrutiva** | `DROP COLUMN`, `DROP TABLE`, `ALTER COLUMN TYPE` incompatível, `RENAME`, `DROP POLICY` sem substituto | **Não** — requer restore do PITR. |

## 3. Procedimento por classe

### 3.1. Aditiva

1. Reverter o frontend via **History** no Lovable (commit imediatamente anterior).
2. Deixar o schema como está. Registrar no post-mortem que a coluna/tabela nova ficou órfã até o próximo deploy corretivo.

### 3.2. Compatível

1. Reverter o frontend.
2. Aplicar migration inversa via `supabase--migration` (o próprio agente Lovable pode gerar; deve ser aprovada pelo usuário).
3. Verificar `supabase--linter` limpo.

### 3.3. Destrutiva

1. **Congelar escritas**: comunicar via banner de manutenção (feature flag `manutencao_ativa`).
2. Abrir chamado de restore PITR para o timestamp `T-1min` da aplicação da migration ruim — Lovable Cloud → Backend → *Point-in-Time Recovery*. O PITR do Supabase gerenciado é o único caminho: não há `pg_dump` local sob nosso controle.
3. Reverter o frontend no Lovable para o commit anterior à migration.
4. Após restore concluído, executar checks:
   ```sql
   -- amostra: contagens críticas
   SELECT 'obras', COUNT(*) FROM public.obras
   UNION ALL SELECT 'colaboradores', COUNT(*) FROM public.colaboradores
   UNION ALL SELECT 'cards', COUNT(*) FROM public.cards;
   -- fronteira
   SELECT COALESCE(SUM(total_orfaos),0) FROM public.vw_db001_fronteira_orfaos;
   ```
5. Rodar `bun run verify:db001-orfaos` contra o banco restaurado (DATABASE_URL somente leitura).
6. Reabrir escritas.
7. Publicar post-mortem em `docs/modernizacao/EXECUCAO/04_VALIDACAO/post-mortem-<data>.md`.

## 4. Pré-condições obrigatórias antes de aplicar migration destrutiva

- [ ] Migration classificada e revisada no PR.
- [ ] Janela de manutenção anunciada.
- [ ] Feature flag `manutencao_ativa` funcional.
- [ ] Timestamp UTC do início da migration registrado (base para o PITR).
- [ ] Contagens de referência das tabelas afetadas capturadas.

Sem esses cinco itens, a migration **não é aplicada**.

## 5. Ordem de execução em incidente

```text
detectar impacto  →  congelar escritas  →  reverter frontend
                                              ↓
                                       classe da migration?
                                        │           │
                                    aditiva     destrutiva
                                        │           │
                                  fim (obs.)   PITR → checks → reabrir → post-mortem
```

## 6. Não-objetivos

- Não substitui OPS-006.a — MySQL legado continua com backup próprio.
- Não descreve rollback de edge functions (coberto por `supabase--deploy_edge_functions` reverter).
- Não descreve rollback do Storage (buckets versionados; recuperação por objeto).

## 7. Critérios de aceite

- (a) Classificação de migration documentada ✅
- (b) Procedimento por classe documentado ✅
- (c) Pré-condições explícitas para destrutivas ✅
- (d) Integração com gate `verify:db001-orfaos` ✅
- (e) Checks pós-restore especificados ✅
