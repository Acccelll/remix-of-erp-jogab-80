## Escopo entregue nesta sessão

O achado foi escrito com base no backend PHP legado (`api.php` + host MySQL) e no repositório monorepo original. Este projeto Lovable é o **destino da modernização**, não contém `api.php` nem o host MySQL — então os itens (a) e (b) do critério de aceite se aplicam ao repositório legado e são tratados no runbook abaixo, não em código deste app.

### 1. CORS sem fallback `*` (Critério d)

Antes: `sync-player-auth` e `seed-obra-demo` emitiam `Access-Control-Allow-Origin: *` incondicional.

Depois: novo módulo `supabase/functions/_shared/cors.ts` com allowlist estrita:

- hosts padrão: `localhost`, `127.0.0.1`, `lovable.app`, `lovableproject.com`, `lovable.dev`;
- hosts adicionais via env `EDGE_ALLOWED_ORIGINS` (CSV);
- se a origem não está autorizada, não emite `Allow-Origin` e o handler devolve **403**;
- inclui `Vary: Origin` para caches.

Funções migradas: `sync-player-auth`, `seed-obra-demo`. A função `provision-auth-user` já usava a mesma estratégia inline (`originPermitida`) e permanece; pode ser convergida para o módulo compartilhado em uma manutenção posterior fora do escopo desta Onda.

### 2. `.env` no `.gitignore` (Critério c)

Adição solicitada:

```
.env
.env.*
!.env.example
```

**Bloqueio operacional:** o arquivo `.gitignore` é somente-leitura na sandbox Lovable e não pôde ser editado nesta sessão. Ficam duas opções para o operador humano:

1. Editar `.gitignore` fora da sandbox (repositório espelho) aplicando o bloco acima.
2. Registrar como Discovery **D-01/SEC-003** e cumprir no espelho do repo, mantendo o restante de SEC-003 fechado.

O `.env` gerenciado pelo Lovable Cloud contém apenas chaves publishable/URL do backend (públicas por design), então o risco residual até a edição é **baixo**, mas o critério de aceite formal só fecha após a alteração.

## Runbook — Rotação de credenciais e retirada da senha do código PHP

**Aplicabilidade:** repositório legado com `api.php` e host MySQL.
**Executor:** operador com acesso ao host MySQL e ao repositório PHP.
**Pré-requisito:** janela de manutenção acordada; backup validado (ver runbook OPS-006.a).

### Passos

1. **Backup preventivo** (ver `RUNBOOK_OPS-006.md`).
2. **Rotacionar a senha do usuário MySQL** consumido pelo `api.php`:
   ```sql
   ALTER USER 'app_user'@'%' IDENTIFIED BY '<nova-senha-forte>';
   FLUSH PRIVILEGES;
   ```
3. **Publicar a nova senha como variável de ambiente do host**, nunca no repositório:
   - Docker/systemd: adicionar a `MYSQL_PASSWORD` em `EnvironmentFile` restrito (chmod 600).
   - Painel de hospedagem PHP: cadastrar como env var do processo.
4. **Editar `api.php` para ler `getenv('MYSQL_PASSWORD')`**, removendo o literal em texto do arquivo.
5. **Purgar histórico Git da senha antiga** (`git filter-repo --replace-text`) e forçar push coordenado — todos os desenvolvedores refazem clone.
6. **Reiniciar o processo PHP** e validar login de um usuário de teste + endpoint `/health`.
7. **Registrar rotação** em `system_events` com tipo `security.credential_rotation`.

### Rollback

- Reverter a env var para a senha anterior e reiniciar o processo PHP.
- A rotação MySQL não precisa ser desfeita se a env var estiver correta.

### Critérios de aceite verificáveis pelo operador

- `grep -RIn "password" api.php` retorna 0 literais de senha.
- Login de teste OK após rotação.
- `git log -p api.php | grep <senha-antiga>` (após filter-repo) retorna 0.
