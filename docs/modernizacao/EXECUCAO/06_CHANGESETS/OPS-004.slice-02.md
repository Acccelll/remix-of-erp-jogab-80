# OPS-004.slice-02 — Instrumentação dos fluxos críticos

**Onda:** 7 · **Achado:** OPS-004 · **Tipo:** NEW · **Escopo:** LOTE (Plataforma)

## Problema

O registry puro de saúde por fluxo existia, mas ainda não recebia sinais
dos call-sites reais. Assim, TOTVS, sync de obra e fila offline seguiam
sem telemetria contínua de sucesso/falha.

## Alterações

`src/lib/observability/critical-flows.ts` (novo, `@module-kind orchestration`):
- IDs estáveis: `totvs.import`, `obra.sync`, `offline.queue`.
- `registerCriticalFlows()` registra definições no singleton `flowHealth`.
- `noteCriticalFlowOk()` / `noteCriticalFlowFail()` injetam `Date.now()` e
  emitem `flow.health.ok` / `flow.health.fail` via logger estruturado.
- `observeCriticalFlow()` encapsula chamadas assíncronas preservando
  rethrow do erro original.

`src/lib/observability/bootstrap.ts`:
- Bootstrap passa a registrar os fluxos críticos junto dos sinks e do
  interceptor de `fetch`.

Call-sites reais instrumentados:
- `financeiroRepo.rpcImportarRelatorioTotvs()` → `totvs.import`.
- `syncObraToSupabase()` → `obra.sync`.
- `useSyncQueueStatus.flushNow()` → `offline.queue`, incluindo falha
  parcial quando `runSync()` retorna itens falhos/remanescentes.

`src/lib/observability/__tests__/critical-flows.test.ts` (novo):
- Registro dos três fluxos críticos.
- Sucesso marca `healthy` e emite `flow.health.ok`.
- Falha marca `degraded`, preserva `lastError`, emite `flow.health.fail`
  e relança a exceção original.

## Não escopo

- Exposição HTTP/JSON do health agregado — fica para `OPS-004.slice-03`.
- Alertas persistentes ou dashboard novo — este slice apenas alimenta o
  registry e breadcrumbs/logs estruturados.
- Instrumentar parse de arquivo inválido como falha sistêmica; falha de
  layout do usuário continua sendo validação funcional, não saúde do fluxo.

  incluindo `critical-flows` verde.
- `bunx tsgo --noEmit` esperado: sem erros de tipo.
