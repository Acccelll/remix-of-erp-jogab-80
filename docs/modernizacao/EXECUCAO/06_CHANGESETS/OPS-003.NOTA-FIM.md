# OPS-003 — NOTA-FIM (Logging estruturado + correlação)

**Onda:** 7 · **Achado:** OPS-003 · **Tipo:** STD/REF · **Escopo:** LOTE (Plataforma)
**Slices consolidados:** `slice-01`, `slice-02`, `slice-03`.

## Problema (origem)

`logger` era wrapper fino sobre `console.*` com strings livres: sem
severidade padronizada como dado, sem campos estruturados, sem
`correlationId` propagado. Numa arquitetura de fronteira dupla
(cliente → PHP → Supabase → edge) qualquer incidente ponta a ponta
era irrastreável — não havia como investigar após o fato.

Referência: `ETAPA_13_OBSERVABILIDADE_OPERACAO.md` (Etapas A/D).

## Entregas por slice

### `slice-01` — Regra pura (correlação + logger estruturado)
- `src/lib/observability/correlation.ts` (`@module-kind pure`):
  `newCorrelationId(prefix?)`, `withCorrelation(id, fn)`,
  `getCorrelationId()` — pilha LIFO síncrona (sem AsyncLocalStorage).
- `src/lib/observability/structured-logger.ts` (`@module-kind pure`):
  `emit(severity, event, { correlationId?, fields? })` e
  `structured.{debug,info,warn,error}`. Formato canônico
  `{ ts, severity, event, correlationId?, fields? }`. `addSink(fn)` +
  isolamento de sink defeituoso. Serialização segura de `Error` e
  valores complexos.
- Testes: 8/8 verdes.

### `slice-02` — Sinks + `apiFetch` instrumentado
- `src/lib/observability/bootstrap.ts` (`@module-kind io`,
  idempotente): sink de console em dev (linha JSON grep-friendly) e
  sink de Sentry breadcrumb em prod (severity→level, correlationId
  em `data`).
- `src/main.tsx`: chama `installObservabilitySinks()` após `initSentry()`.
- `src/lib/api.ts`: `doFetch` exige `correlationId` e envia
  **`X-Correlation-Id`**. `apiFetch` gera id por chamada e emite
  `planifik.api.ok` | `planifik.api.http_error` | `planifik.api.fail`
  com `route`, `method`, `status`, `durationMs`, `error?`, `replayed?`.

### `slice-03` — Interceptor de `fetch` (Supabase / Edge)
- `src/lib/observability/fetch-interceptor.ts` (`@module-kind io`,
  idempotente): monkey-patch de `globalThis.fetch`. Alvos padrão:
  host de `VITE_SUPABASE_URL` + qualquer path contendo `/functions/v1/`.
  Injeta `X-Correlation-Id` (contexto corrente ou id efêmero) sem
  sobrepor header explícito, e emite
  `sb.fetch.ok` | `sb.fetch.http_error` | `sb.fetch.fail`.
- Requisições fora do alvo passam pelo `originalFetch` intactas.
- Testes: 6/6 verdes.

## Critérios de aceite (todos atendidos)

- (a) Logs com campos estruturados — `structured.*` + `StructuredEvent`.
- (b) Id de correlação propagado cliente→backend→edge — header
  `X-Correlation-Id` no PHP (`apiFetch`) e nas rotas Supabase/edge
  (interceptor).
- (c) Eventos relevantes consultáveis — em prod via breadcrumbs Sentry;
  em dev via console. Pipeline de coletor externo fica em `OPS-004`.
- (d) Severidade padronizada — `debug | info | warn | error`.

## Não escopo (débitos conhecidos)

- Leitura/repasse do header no backend PHP e nos edges (depende do
  time de backend; o header já sai do cliente).
- Coletor externo agregando eventos além do Sentry breadcrumb
  (pré-requisito de `OPS-004`).
- Migração dos call-sites que ainda usam `logger.warn` / `logger.error`
  com strings livres — segue permitido; migração incremental sob demanda.

## Validação global
