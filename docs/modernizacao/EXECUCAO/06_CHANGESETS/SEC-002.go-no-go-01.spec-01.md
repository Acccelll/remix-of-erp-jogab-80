## 1. Objetivo

Formalizar, por lote (`helpers-02`, `tests-02-suite`, `batch-B`, `batch-C`, `batch-D`, `batch-E`), a **decisão explícita** que autoriza o merge do PR de apply em produção. Consolida em um único artefato versionado:

1. critérios objetivos que definem cada estado (`GO`, `HOLD`, `ROLLBACK`, `ERRATA`);
2. responsáveis (DRI técnico + aprovador de negócio);
3. evidências mínimas obrigatórias por critério;
4. janela de validade da decisão (24 h);
5. registro auditável do resultado (`decision`, `decided_at`, `decided_by`, `evidence_refs`).

Sem esta decisão registrada, o merge do PR de apply é **proibido** pelo CI `sec002-pr-checklist` (novo gate `go_no_go_present=true`).

## 2. Fora de escopo

- Alterar migrações, políticas RLS, código de produção, funções edge.
- Substituir os gates já definidos em `pr-checklist-01` — este spec **complementa**, não substitui.
- Definir critérios de negócio da Onda 2 fora de `SEC-002` (permanecem em D-1/D-2).

## 3. Estados canônicos

| Estado | Semântica | Efeito no merge | Reversibilidade |
|--------|-----------|-----------------|-----------------|
| `GO` | Todos os critérios do lote satisfeitos, evidências anexadas, janela válida. | Autoriza merge do PR de apply. | N/A (avança) |
| `HOLD` | ≥1 critério não satisfeito ou evidência ausente/expirada. | Bloqueia merge; PR permanece aberto. | Reavaliar após ação corretiva. |
| `ROLLBACK` | Apply anterior do mesmo lote executado e revertido; requer nova staging parity + nova suíte. | Bloqueia merge; força reabrir ciclo. | Só após novo `GO`. |
| `ERRATA` | Correção pontual em spec já mergeado sem novo apply de migração. | Autoriza merge de errata (docs-only). | N/A |

Qualquer estado diferente de `GO` **não** produz merge de migração.

## 5. Estrutura do artefato de decisão

Arquivo: `.github/sec002-go-no-go/<sec002_apply_id>.md`
Formato: markdown com frontmatter YAML determinístico.

```yaml
---
sec002_apply_id: <helpers-02|tests-02-suite|batch-B|batch-C|batch-D|batch-E>
decision: <GO|HOLD|ROLLBACK|ERRATA>
decided_at: <ISO8601 UTC>
decided_by:
  dri_technical: <github-login>
  dri_business: <github-login>
valid_until: <ISO8601 UTC = decided_at + 24h>
staging_snapshot_id: <hash>
observability_dashboard_url: <url>
evidence:
  G1: { status: pass|fail, ref: <url> }
  G2: { status: pass|fail, ref: <url> }
  G3: { status: pass|fail, ref: <url> }
  G4: { status: pass|fail, ref: <url> }
  G5: { status: pass|fail, ref: <url> }
  G6: { status: pass|fail, ref: <url> }
  G7: { status: pass|fail, ref: <url> }
  G8: { status: pass|fail, ref: <url> }
  # critérios específicos do lote (H*, T*, B*, C*, D*, E*)
notes: |
  <texto livre — obrigatório se decision != GO>
---
```

Regras:

1. `decision=GO` exige **todos** `evidence.*.status=pass` (globais + específicos do lote).
2. `valid_until` = `decided_at + 24 h`. Merge após esse instante → `HOLD` automático.
3. `staging_snapshot_id` deve bater com `.github/sec002-staging-parity.json`.
4. `notes` obrigatório para `HOLD`, `ROLLBACK`, `ERRATA`.
5. Arquivo é **append-only**: nova decisão = novo arquivo com sufixo `.v2`, `.v3`.

## 6. Responsáveis (DRI matrix)

| Papel | Responsabilidade | Aprovação |
|-------|------------------|-----------|
| DRI técnico SEC-002 | Executar checklist, coletar evidências, propor decisão | assina `decided_by.dri_technical` |
| DRI plataforma | Freeze, staging parity, rollback dry-run | evidências G2, G3, G7 |

| GM (Cappucceno) | Aprovação final de negócio | assina `decided_by.dri_business` |

Sem as duas assinaturas o CI rejeita o arquivo.

## 7. Validador `scripts/sec002/validate-go-no-go.mjs`

Assinatura: `node scripts/sec002/validate-go-no-go.mjs --apply-id <id> --file <path>`.

Verificações determinísticas:

1. arquivo existe em `.github/sec002-go-no-go/<apply-id>.md` (ou `.vN.md`);
2. frontmatter YAML válido com todos os campos obrigatórios;
3. `sec002_apply_id` = argumento `--apply-id`;
4. `decision ∈ {GO, HOLD, ROLLBACK, ERRATA}`;
5. `decided_at ≤ now`; `valid_until = decided_at + 24 h`;
6. `now ≤ valid_until` (senão `expired`);
7. `staging_snapshot_id` = valor em `.github/sec002-staging-parity.json`;
8. mapeamento `apply_id → critérios específicos` conforme §4.2;
9. se `decision=GO`, todos os `evidence.*.status=pass`;
10. se `decision≠GO`, `notes` não vazio;
11. `decided_by.dri_technical ≠ decided_by.dri_business` (dupla assinatura).

Exit codes: `0` válido; `1` inválido (mensagem determinística no stderr).

## 8. Integração com CI

`sec002-pr-checklist` ganha novo step após `validate-staging-parity`:

```yaml
- name: Validate go/no-go decision
  run: node scripts/sec002/validate-go-no-go.mjs --apply-id "${{ steps.parse.outputs.apply_id }}" --file ".github/sec002-go-no-go/${{ steps.parse.outputs.apply_id }}.md"
```

Ordem final dos gates no PR de apply:

1. `sec002-pr-checklist` (inclui `validate-go-no-go`)
2. `sec002-freeze-guard`
3. `sec002-staging-parity`
4. `sec-002-tests`

Falha em qualquer gate → merge bloqueado.

## 9. Ciclo de reavaliação

- `HOLD`: corrigir causa raiz, atualizar evidências, publicar nova versão `.vN.md`, re-rodar CI.
- `ROLLBACK`: registrar `notes` com causa, executar runbook `release-plan §rollback`, refresh staging (`sec002-staging-refresh`), nova suíte, novo `.vN.md`.
- `ERRATA`: PR docs-only marcado `[SEC-002][errata:<apply-id>]`; não passa por `validate-changed-files` para migrações.
