# SEC-002.batch-E.migration.spec-01 — Migração executável do Lote E

**Onda:** 2 (preparatória — bloqueada por fechamento de `SEC-001`, `SEC-002.helpers-02.migration`, `SEC-002.batch-B.migration`, `SEC-002.batch-C.migration` e `SEC-002.batch-D.migration`)  
**Data:** 2026-07-12  
**Escopo:** especifica o **arquivo SQL executável** `supabase/migrations/<ts>_sec_002_batch_e.sql` que materializa as políticas-alvo descritas em `SEC-002.batch-E.spec-01` para as **22 tabelas de boards & cards**. Este changeset é **apenas especificação do arquivo de migração** — nada é aplicado ao banco, nada em `src/` ou edge functions muda. É o quinto e último artefato executável de RLS de `SEC-002`, depois de `helpers-02`, `batch-B`, `batch-C` e `batch-D`.

## 3. Estrutura do arquivo

Uma transação. 22 tabelas em ordem alfabética, tudo no mesmo `begin/commit`. Este lote **não** cria helpers.

```text
begin;
  -- para cada tabela (§6 do batch-E.spec-01):
  --   1. drop policy if exists <policy_atual_n> on public.<tabela>;  (todas as atuais)
  --   2. create policy "<tabela>_select_..." on public.<tabela> ... ;
  --   3. create policy "<tabela>_write_..."  on public.<tabela> ... ;
  --      (variantes: 4 policies em boards/cards; policies split select+write especiais em board_membros,
  --       card_membros, card_membros_externos, card_comentarios, card_atividades — ver §6)
  --   4. alter table public.<tabela> enable row level security;
  --   5. revoke all on public.<tabela> from anon;
  --   6. grant select, insert, update, delete on public.<tabela> to authenticated;
  --   7. grant all on public.<tabela> to service_role;
  notify pgrst, 'reload schema';
commit;
```

Transação única. Sem `commit` intermediário — falha em qualquer tabela reverte o lote inteiro.

## 5. Enumeração das policies atuais para `drop policy if exists`

O PR obriga, **antes de escrever o SQL**, uma extração literal:

```sql
select tablename, policyname
from   pg_policies
where  schemaname = 'public'
  and  tablename in (<22 tabelas>)
```

## 6. Materialização por classe

Cada tabela deve terminar com o número exato de policies definido abaixo. Nomes seguem `SEC-002.batch-E.spec-01`.

### 6.1 BOARD-SCOPE — 2 policies

Aplicado a:

```text
board_campos, board_listas, card_board_posicao,
card_labels, card_secoes_visiveis, card_setores
```

Contrato (`SELECT` + `FOR ALL`):

```sql
using (public.current_is_gm() or public.user_in_board(auth.uid(), board_id))
with check (public.current_is_gm() or public.user_in_board(auth.uid(), board_id))
```

### 6.2 CARD-SCOPE — 2 policies

Aplicado a:

```text
card_anexos, card_campos_valores, card_checklist_itens,
card_custom_field_valores, card_grupos_negociacao,
card_label_links, card_local, card_recursos
```

Contrato (`SELECT` + `FOR ALL`):

```sql
using (public.current_is_gm() or public.user_in_card(auth.uid(), card_id))
with check (public.current_is_gm() or public.user_in_card(auth.uid(), card_id))
```

### 6.3 CARDS-ROOT — 4 policies (`cards`)

Nomes canônicos obrigatórios (§4.3 do spec):

- `cards_select_scoped`
- `cards_insert_member`
- `cards_update_member`
- `cards_delete_owner`

Expressões copiadas literalmente. `DELETE` é GM ou `responsavel_id = auth.uid()` — sem alargamento.

### 6.4 BOARDS-ROOT — 4 policies (`boards`)

Nomes canônicos obrigatórios (§4.4 do spec):

- `boards_select_scoped`
- `boards_insert_authenticated` (exige `owner_id = auth.uid()` ou GM)
- `boards_update_owner`
- `boards_delete_owner`

### 6.5 Split leitura BOARD/CARD-SCOPE + escrita nominal

Tabelas com policy de leitura larga e escrita restrita. Cada uma termina com **3 policies**: uma `SELECT`, uma `INSERT` (`WITH CHECK`) e uma `UPDATE/DELETE` combinada (`FOR ALL` com `USING` restrito e `WITH CHECK` idem) — divididas conforme abaixo para clareza semântica.

#### 6.5.1 `board_membros` — 4 policies

- `board_membros_select_board` — `SELECT` via `user_in_board(auth.uid(), board_id)` ou GM.
- `board_membros_insert_owner` — `INSERT` com `WITH CHECK`: GM ou owner do board.
  ```sql
  with check (
    public.current_is_gm()
    or exists (
      select 1 from public.boards b
      where b.id = board_membros.board_id
        and b.owner_id = auth.uid()
    )
  )
  ```
- `board_membros_update_owner` — `UPDATE`: mesmo predicado no `USING`/`WITH CHECK`.
- `board_membros_delete_self_or_owner` — `DELETE`:
  ```sql
  using (
    public.current_is_gm()
    or user_id = auth.uid()
    or exists (
      select 1 from public.boards b
      where b.id = board_membros.board_id
        and b.owner_id = auth.uid()
    )
  )
  ```

#### 6.5.2 `card_membros` — 4 policies

Simétrico a `board_membros`, mas o proprietário é `cards.responsavel_id`:

- `card_membros_select_card` — `SELECT` via `user_in_card(auth.uid(), card_id)` ou GM.
- `card_membros_insert_owner` — `WITH CHECK`: GM ou `exists (select 1 from public.cards c where c.id = card_membros.card_id and c.responsavel_id = auth.uid())`.
- `card_membros_update_owner` — mesmo predicado.
- `card_membros_delete_self_or_owner` — permite `user_id = auth.uid()`, responsável do card ou GM.

#### 6.5.3 `card_membros_externos` — 2 policies

- `card_membros_externos_select_card` — `SELECT` via CARD-SCOPE.
- `card_membros_externos_write_owner` — `FOR ALL`:
  ```sql
  using (
    public.current_is_gm()
    or exists (
      select 1 from public.cards c
      where c.id = card_membros_externos.card_id
        and c.responsavel_id = auth.uid()
    )
  )
  with check (<mesma expressão>)
  ```

#### 6.5.4 `card_comentarios` — 3 policies

- `card_comentarios_select_card` — CARD-SCOPE.
- `card_comentarios_insert_author` — `WITH CHECK`:
  ```sql
  with check (
    autor_id = auth.uid()
    and public.user_in_card(auth.uid(), card_id)
  )
  ```
  GM também autorizado (`public.current_is_gm() or (...)`).
- `card_comentarios_modify_author` — `FOR UPDATE, DELETE` (materializado como duas policies `card_comentarios_update_author` e `card_comentarios_delete_author` se `FOR UPDATE, DELETE` combinado não for aceito):
  ```sql
  using (public.current_is_gm() or autor_id = auth.uid())
  with check (public.current_is_gm() or autor_id = auth.uid())
  ```

Contagem final admite 3 ou 4 policies dependendo do split UPDATE/DELETE; o gate §8.2 aceita ambos, contanto que a matriz de asserts §9 permaneça verde.

#### 6.5.5 `card_atividades` — 3 policies

Log operacional:

- `card_atividades_select_card` — CARD-SCOPE.
- `card_atividades_insert_author` — `WITH CHECK`:
  ```sql
  with check (
    (autor_id is null or autor_id = auth.uid())
    and (public.current_is_gm() or public.user_in_card(auth.uid(), card_id))
  )
  ```
- `card_atividades_modify_author` — `USING` / `WITH CHECK`: GM ou `autor_id = auth.uid()`. Mesma nota do §6.5.4 sobre split UPDATE/DELETE.

### 6.6 OWNER-SELF — 2 policies

Aplicado a:

```text
card_views_salvas
```

Contrato:

```sql
using (public.current_is_gm() or owner_id = auth.uid())
with check (public.current_is_gm() or owner_id = auth.uid())
```

Não conceder `SELECT` amplo — view é privada.

## 7. Grants finais (repetição obrigatória por tabela)

Bloco padrão aplicado às **22** tabelas:

```sql
revoke all on public.<tabela> from anon;
grant select, insert, update, delete on public.<tabela> to authenticated;
grant all on public.<tabela> to service_role;
```

Nenhum `grant` a `anon` em qualquer tabela do lote. Nenhum helper novo — os de `helpers-02` são reutilizados.

## 9. Rollback

Companion `SEC-002.batch-E.rollback.sql`, executável em transação única:

```sql
begin;
  -- para cada tabela do lote (22):
  drop policy if exists "<tabela>_select_..." on public.<tabela>;
  drop policy if exists "<tabela>_write_..."  on public.<tabela>;
  -- boards/cards/board_membros/card_membros: dropar as 4 policies canônicas.
  -- card_comentarios/card_atividades: dropar as 3 ou 4 canônicas.

  -- recria a policy legada permissiva:
  create policy "<tabela>_authenticated_all"
    on public.<tabela>
    for all
    to authenticated
    using (true)
    with check (true);
commit;
```

Helpers de `helpers-02` **não** são removidos. Grants **não** são revertidos. Como é o último lote, rollback é seguro sem dependência de lotes posteriores.

## 11. Riscos

- **R1: cascata de leituras via `user_in_card`.** Cada `SELECT` em filho de card faz lookup em `card_membros`. Mitigação: índices exigidos em §2.9; helpers são `stable security definer`.
- **R2: cards órfãos.** Sem `card_board_posicao` e sem `card_membros`, cards ficam invisíveis a não-GM. Mitigação: contagem obrigatória §2.10; fallback via `obra_id` já embutido em §4.3 do spec.
- **R3: `card_atividades` como append-only imperfeito.** RLS impede overwrite alheio, mas o próprio autor ainda pode. Correção definitiva exige trigger — fora deste changeset.
- **R4: divergência board-member × card-member.** Membro do board não vê conteúdo do card se não for `card_membros`. Comportamento intencional; UI deve refletir.
- **R5: PostgREST cacheia policies antigas.** Mitigação: `notify pgrst, 'reload schema';` no final da migração.

## 12. Impacto em produção

**Nenhum neste changeset.** Documento de especificação do arquivo. A execução real (`SEC-002.batch-E.migration`) é changeset seguinte, com seu próprio gate. Após seu apply em produção e 24 h estáveis, `SEC-002` fecha e a Onda 2 avança para o pós-RLS (D-1/D-2 e cutover auth).
