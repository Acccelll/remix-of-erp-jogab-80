# SEC-002.batch-D.spec-01 — Políticas-alvo do Lote D (DP & financeiro)

**Onda:** 2 (preparatória — bloqueada por fechamento de `SEC-001`)

**Escopo:** especifica o **conjunto atômico de políticas** que substituirá as políticas atuais das **15 tabelas do Lote D** definidas em `SEC-002.inventory-02` §3. Correção formal: o inventário-02 registrou "D ≈ 14"; a contagem real no CSV é **15**. Nenhuma migração é aplicada; **este é o contrato SQL** que a migração `SEC-002.batch-D.migration` executará, sob gate, depois dos lotes B/C e dos helpers de escopo. Nenhum código de produção é alterado.

## 1. Escopo

## 2. Pré-requisitos duros

A migração `SEC-002.batch-D.migration` só entra depois de, em ordem:

1. `SEC-002.batch-B.migration` **em produção há ≥ 24 h sem regressão RLS**.
2. `SEC-002.batch-C.migration` **em produção há ≥ 24 h sem regressão RLS**.
3. `SEC-002.helpers-02.migration` **aplicada** — inclui `public.user_in_empresa` e `public.user_in_obra` (`SEC-002.helpers-01`).

Se qualquer passo falhar, a migração aborta.

## 3. Diagnóstico de schema do lote

Consulta desta janela contra `information_schema.columns` e `information_schema.table_constraints`:

| Achado | Tabelas | Impacto na policy |
|--------|---------|-------------------|

| `colaborador_id text` legado | `custo_colaborador_competencia`, `decimo_terceiro`, `dp_holerite`, `fopag_entries`, `historico_salarial`, `horas_extras`, `provisoes` | derivar empresa por `colaboradores.id::text → colaboradores.obra_atual_id → obras.empresa_id` quando houver obra atual |

## 4. Padrões de regra por classe

Cinco padrões apenas. Toda tabela do lote mapeia para exatamente um em §6.

### 4.1 Padrão **DP-ROLE**

Aplicável a folha, remuneração e dados pessoais de DP. Leitura/escrita só por GM ou papel DP.

```sql
create policy "<tabela>_select_dp"
  on public.<tabela>
  for select
  to authenticated
  using (public.current_is_gm() or public.has_role(auth.uid(), 'dp'));

create policy "<tabela>_write_dp"
  on public.<tabela>
  for all
  to authenticated
  using (public.current_is_gm() or public.has_role(auth.uid(), 'dp'))
  with check (public.current_is_gm() or public.has_role(auth.uid(), 'dp'));
```

Este padrão não concede leitura ao próprio colaborador nesta fase: o schema não possui `user_id` confiável no colaborador/holerite. Qualquer self-service de holerite será changeset próprio depois de identidade de colaborador canônica.

### 4.2 Padrão **FINANCE-ROLE**

Aplicável a dados financeiros sem escopo de obra confiável direto. Leitura por GM/financeiro/compras; escrita por GM/financeiro, com exceções de compras em §7.

```sql
create policy "<tabela>_select_finance"
  on public.<tabela>
  for select
  to authenticated
  using (
    public.current_is_gm()
    or public.has_role(auth.uid(), 'financeiro')
    or public.has_role(auth.uid(), 'compras')
  );

create policy "<tabela>_write_finance"
  on public.<tabela>
  for all
  to authenticated
  using (public.current_is_gm() or public.has_role(auth.uid(), 'financeiro'))
  with check (public.current_is_gm() or public.has_role(auth.uid(), 'financeiro'));
```

### 4.3 Padrão **FINANCE-OBRA**

Aplicável a lançamentos/documentos com `obra_id uuid`. Regra base: papel financeiro/compras é obrigatório; vínculo de obra restringe o subconjunto quando `obra_id` existe. GM bypass explícito.

```sql
create policy "<tabela>_select_finance_obra"
  on public.<tabela>
  for select
  to authenticated
  using (
    public.current_is_gm()
    or (
      (public.has_role(auth.uid(), 'financeiro') or public.has_role(auth.uid(), 'compras'))
      and (obra_id is null or public.user_in_obra(auth.uid(), obra_id))
    )
  );

create policy "<tabela>_write_finance_obra"
  on public.<tabela>
  for all
  to authenticated
  using (
    public.current_is_gm()
    or (
      public.has_role(auth.uid(), 'financeiro')
      and (obra_id is null or public.user_in_obra(auth.uid(), obra_id))
    )
  )
  with check (
    public.current_is_gm()
    or (
      public.has_role(auth.uid(), 'financeiro')
      and (obra_id is null or public.user_in_obra(auth.uid(), obra_id))
    )
  );
```

`obra_id IS NULL` continua visível/editável apenas a financeiro/GM — não a usuários operacionais — porque representa título sem obra conciliada.

### 4.4 Padrão **VIA-PARENT**

Aplicável a linhas filhas sem coluna de escopo própria.

```sql
create policy "<tabela>_select_via_parent"
  on public.<tabela>
  for select
  to authenticated
  using (
    public.current_is_gm()
    or (
      (public.has_role(auth.uid(), 'financeiro') or public.has_role(auth.uid(), 'compras'))
      and exists (
        select 1 from public.<parent_tbl> p
        where p.id = <tabela>.<parent_fk>
          and <parent_scope_predicate>
      )
    )
  );

create policy "<tabela>_write_via_parent"
  on public.<tabela>
  for all
  to authenticated
  using (
    public.current_is_gm()
    or (
      public.has_role(auth.uid(), 'financeiro')
      and exists (
        select 1 from public.<parent_tbl> p
        where p.id = <tabela>.<parent_fk>
          and <parent_scope_predicate>
      )
    )
  )
  with check (<mesma expressão do using>);
```

Derivações autorizadas neste lote:

| Tabela | Pai | Predicado de escopo |
|--------|-----|---------------------|
| `financeiro_rateios` | `financeiro_lancamentos(lancamento_id)` | `p.obra_id is null or user_in_obra(auth.uid(), p.obra_id)` |
| `solicitacao_comentarios` | `solicitacoes_financeiras(solicitacao_id)` | `SEC-002.can_access_solicitacao_financeira(p.id)` — helper local da migração D, ver §7 |
| `controle_despesas` | `solicitacoes_financeiras(solicitacao_id)` quando preenchido | se `solicitacao_id is null`, cai em FINANCE-ROLE; se preenchido, herda solicitação |

### 4.5 Padrão **SOLICITACAO-FINANCEIRA**

Aplicável exclusivamente a `solicitacoes_financeiras`.

Objetivo funcional:

1. GM vê/escreve tudo.
2. `financeiro` vê tudo e aprova/paga, exceto a própria solicitação.
3. `compras` cria e acompanha solicitações; não aprova a própria.
4. Solicitante vê sua própria solicitação.
5. Nenhum `anon` lê/escreve.

Como o schema atual usa autoria textual, a migração D deve criar **helper auxiliar** `public.current_profile_login()` (`stable security definer`) ou equivalente, lendo `profiles.login` do `auth.uid()`. A policy usa login textual apenas como ponte temporária, nunca localStorage.

```sql
create policy "solicitacoes_financeiras_select_scoped"
  on public.solicitacoes_financeiras
  for select
  to authenticated
  using (
    public.current_is_gm()
    or public.has_role(auth.uid(), 'financeiro')
    or public.has_role(auth.uid(), 'compras')
    or criado_por = public.current_profile_login()
    or solicitante = public.current_profile_login()
  );

create policy "solicitacoes_financeiras_insert_solicitante"
  on public.solicitacoes_financeiras
  for insert
  to authenticated
  with check (
    public.current_is_gm()
    or public.has_role(auth.uid(), 'compras')
    or public.has_role(auth.uid(), 'financeiro')
  );

create policy "solicitacoes_financeiras_update_segregated"
  on public.solicitacoes_financeiras
  for update
  to authenticated
  using (
    public.current_is_gm()
    or (
      public.has_role(auth.uid(), 'financeiro')
      and coalesce(criado_por, solicitante, '') <> public.current_profile_login()
    )
    or (
      public.has_role(auth.uid(), 'compras')
      and criado_por = public.current_profile_login()
      and aprovado_por is null
      and data_aprovacao is null
    )
  )
  with check (
    public.current_is_gm()
    or (
      public.has_role(auth.uid(), 'financeiro')
      and coalesce(criado_por, solicitante, '') <> public.current_profile_login()
    )
    or (
      public.has_role(auth.uid(), 'compras')
      and criado_por = public.current_profile_login()
      and aprovado_por is null
      and data_aprovacao is null
    )
  );

create policy "solicitacoes_financeiras_delete_gm_only"
  on public.solicitacoes_financeiras
  for delete
  to authenticated
  using (public.current_is_gm());
```

## 5. Estrutura atômica da migração

Mesmo shape de `SEC-002.batch-B.spec-01` §4 e `SEC-002.batch-C.spec-01` §5:

```sql
begin;
  -- helpers auxiliares do lote D, se ainda ausentes:
  create or replace function public.current_profile_login() ... security definer ...;
  create or replace function public.can_access_solicitacao_financeira(_solicitacao uuid) ... security definer ...;

  -- por tabela:
  drop policy if exists "<policy_atual_1>" on public.<tabela>;
  drop policy if exists "<policy_atual_2>" on public.<tabela>;
  ...
  create policy "<tabela>_select_..." on public.<tabela> ...;
  create policy "<tabela>_write_..."  on public.<tabela> ...;

  alter table public.<tabela> enable row level security;
  revoke all on public.<tabela> from anon;
  grant select, insert, update, delete on public.<tabela> to authenticated;
  grant all on public.<tabela> to service_role;
commit;
```

**Transação única** para as 15 tabelas. Sem `commit` intermediário.

## 7. Exceções nominais

- **`solicitacoes_financeiras`.** Segregação mínima obrigatória: usuário cujo `current_profile_login()` coincide com `criado_por` ou `solicitante` **não pode aprovar/pagar a própria solicitação**. Enquanto não houver `solicitante_id/aprovador_id uuid`, a segregação é textual e deve ser registrada como risco residual R1 (§11).
- **`solicitacao_comentarios`.** `INSERT` permitido para quem consegue ver a solicitação pai. `UPDATE/DELETE` só para GM ou autor (`autor = current_profile_login()`) enquanto não houver `autor_id uuid`.
- **`controle_despesas`.** Compras pode inserir despesas vinculadas a solicitação própria enquanto `pagamento_pendente = false`; financeiro controla baixa/pagamento. Se `solicitacao_id IS NULL`, escrita fica restrita a financeiro/GM.
- **`financeiro_snapshots`.** `owner_id` é metadado de importação, não autorização; não usar OWNER-SELF.
- **`horas_extras`.** Apesar de conter `obra_id text`, permanece DP-ROLE porque é dado de remuneração. Filtro por obra pode ser adicionado como defesa em profundidade somente se não quebrar importações legadas: `obra_id is null or exists (select 1 from obras o where o.id::text = horas_extras.obra_id and user_in_obra(auth.uid(), o.id))`.
- **`dp_holerite`.** Não criar policy de self-read sem vínculo `auth.uid() → colaborador_id` formal. Self-service exige changeset posterior.

## 8. Grants finais

Bloco reafirmado no final da migração para todas as 15 tabelas:

```sql
revoke all on public.<tabela> from anon;
grant select, insert, update, delete on public.<tabela> to authenticated;
grant all on public.<tabela> to service_role;
```

Nenhuma tabela do lote recebe `grant` a `anon`.

Helpers auxiliares do lote D:

```sql
grant execute on function public.current_profile_login() to authenticated, service_role;
grant execute on function public.can_access_solicitacao_financeira(uuid) to authenticated, service_role;
```

Casos obrigatórios específicos:

| Caso | Oráculo adicional |
|------|-------------------|
| `member` DP | usuário com `has_role('dp')` acessa tabelas DP |
| `member` financeiro | usuário com `has_role('financeiro')` acessa tabelas financeiras |
| `member` compras | usuário com `has_role('compras')` cria/acompanhada solicitação, mas não aprova pagamento |
| `outsider` | usuário autenticado sem papel DP/financeiro/compras recebe `SELECT=0` e escrita bloqueada |
| `segregation` | mesmo login em `criado_por`/`solicitante` tenta aprovar: `UPDATE` deve afetar 0 linhas ou falhar por RLS |

## 10. Reversão

Companion `SEC-002.batch-D.rollback.sql` refaz as políticas do inventário-02 (`USING(true)`/`WITH CHECK(true)` para authenticated). Uso exclusivo para incidente de produção e aprovação de D-9.

Rollback **não** remove helpers `current_profile_login()`/`can_access_solicitacao_financeira()` se já existirem, apenas deixa de usá-los nas policies revertidas.

## 11. Riscos

- **R1: segregação textual.** `solicitacoes_financeiras` não possui `solicitante_id/aprovador_id uuid`; usar `profiles.login` é mitigação temporária. Correção definitiva exige coluna UUID e backfill.
- **R2: tabelas DP sem vínculo de empresa confiável.** `colaborador_id` é texto legado; DP-ROLE protege por papel, não por empresa. Mitigação: DB-001/ARC devem normalizar FK antes de escopo fino.
- **R3: `financeiro_rateios` depende de join em `financeiro_lancamentos`.** Mitigação: helper/policy usa parent por PK; gate deve validar índice em `financeiro_rateios(lancamento_id)`.
- **R4: `compras` amplo demais em leitura financeira.** Mitigação: leitura de compras é aceita apenas para fluxo de solicitação/despesa; se telas financeiras sensíveis exigirem isolamento, separar `compras` de `financeiro_lancamentos` no `SEC-002.batch-D.migration`.
- **R5: importações por função backend.** Qualquer rotina administrativa deve usar `service_role`; grants preservam `service_role` livre.

## 12. Impacto em produção

**Nenhum neste changeset.** Documento de especificação. A migração real (`SEC-002.batch-D.migration`) e a suíte (`SEC-002.tests-02.suite/batch-D`) são changesets seguintes, cada um sujeito ao próprio gate.
