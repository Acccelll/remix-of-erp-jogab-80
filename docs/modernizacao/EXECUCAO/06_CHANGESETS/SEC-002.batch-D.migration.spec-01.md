**Onda:** 2 (preparatória — bloqueada por fechamento de `SEC-001`, `SEC-002.helpers-02.migration`, `SEC-002.batch-B.migration` e `SEC-002.batch-C.migration`)  
**Data:** 2026-07-12  
**Escopo:** especifica o **arquivo SQL executável** `supabase/migrations/<ts>_sec_002_batch_d.sql` que materializa as políticas-alvo descritas em `SEC-002.batch-D.spec-01` para as **15 tabelas de DP & financeiro**. ## 3. Estrutura do arquivo

Uma transação. Ordem estrita: helpers locais do lote D → 15 tabelas em ordem alfabética, tudo no mesmo `begin/commit`:

```text
begin;
  -- 3.1 helpers auxiliares do lote D (idempotentes):
  create or replace function public.current_profile_login() ... security definer ...;
  create or replace function public.can_access_solicitacao_financeira(_solicitacao uuid) ... security definer ...;
  grant execute on function public.current_profile_login() to authenticated, service_role;
  revoke execute on function public.current_profile_login() from anon;
  grant execute on function public.can_access_solicitacao_financeira(uuid) to authenticated, service_role;
  revoke execute on function public.can_access_solicitacao_financeira(uuid) from anon;

  -- 3.2 para cada tabela (§6 do batch-D.spec-01):
  --   1. drop policy if exists <policy_atual_n> on public.<tabela>;  (todas as atuais)
  --   2. create policy "<tabela>_select_..." on public.<tabela> ... ;
  --   3. create policy "<tabela>_write_..."  on public.<tabela> ... ;  (ou 4 policies em solicitacoes_financeiras — §6.5)
  --   4. alter table public.<tabela> enable row level security;
  --   5. revoke all on public.<tabela> from anon;
  --   6. grant select, insert, update, delete on public.<tabela> to authenticated;
  --   7. grant all on public.<tabela> to service_role;

  notify pgrst, 'reload schema';
commit;
```

Transação única. Sem `commit` intermediário — falha em qualquer tabela ou helper reverte o lote inteiro.

## 4. Fonte canônica do SQL de policies

Cópia literal dos padrões §4, exceções §7 e mapa §6 de `SEC-002.batch-D.spec-01`. Nenhuma flexibilização. A única consolidação é a definição executável dos helpers locais (§5) — cujos contratos já estão fixados em §4.5 e §7 do spec de política.

Ordem das tabelas dentro do `begin/commit` (alfabética, para diff estável):

```text
controle_despesas, custo_colaborador_competencia, decimo_terceiro,
dp_holerite, financeiro_lancamentos, financeiro_rateios,
financeiro_snapshots, fopag_entries, historico_salarial,
horas_extras, notas_fiscais, provisoes, recebimentos,
solicitacao_comentarios, solicitacoes_financeiras
```

`financeiro_rateios` fica **depois** de `financeiro_lancamentos` na ordem alfabética natural, o que preserva a dependência lógica (rateios referenciam lançamentos via `EXISTS`, mas RLS não impõe ordem de criação — apenas o teste de gate).

## 5. Helpers locais obrigatórios

### 5.1 `public.current_profile_login()`

```sql
create or replace function public.current_profile_login()
returns text
language sql
stable
security definer
set search_path = public
as $$
  select p.login
  from public.profiles p
  where p.id = auth.uid()
$$;
```

Retorna `NULL` para `anon` ou usuário sem `profiles` — o que faz as comparações `criado_por = current_profile_login()` avaliarem `NULL` (nunca `true`), preservando negação segura.

### 5.2 `public.can_access_solicitacao_financeira(_solicitacao uuid)`

```sql
create or replace function public.can_access_solicitacao_financeira(_solicitacao uuid)
returns boolean
language sql
stable
security definer
set search_path = public
as $$
  select exists (
    select 1
    from public.solicitacoes_financeiras s
    where s.id = _solicitacao
      and (
        public.current_is_gm()
        or public.has_role(auth.uid(), 'financeiro')
        or public.has_role(auth.uid(), 'compras')
        or s.criado_por  = public.current_profile_login()
        or s.solicitante = public.current_profile_login()
      )
  );
$$;
```

Espelha o `USING` de `solicitacoes_financeiras_select_scoped` (§6.5) para reuso em `solicitacao_comentarios`. Ambos os helpers **não têm** `grant execute` para `anon`.

## 6. Materialização por classe

Cada tabela deve terminar com exatamente **2 policies** (uma leitura + uma escrita `FOR ALL`), exceto `solicitacoes_financeiras`, que termina com **4 policies** (select, insert, update, delete) conforme §4.5 do spec. Nomes devem seguir `SEC-002.batch-D.spec-01`.

### 6.1 DP-ROLE

Aplicado a:

```text
custo_colaborador_competencia, decimo_terceiro, dp_holerite,
fopag_entries, historico_salarial, horas_extras, provisoes
```

Contrato:

```sql
using (public.current_is_gm() or public.has_role(auth.uid(), 'dp'))
with check (public.current_is_gm() or public.has_role(auth.uid(), 'dp'))
```

`horas_extras`: DP-ROLE puro nesta migração; filtro por `obra_id text` fica fora — sua adoção como defesa em profundidade exige errata explícita.

### 6.2 FINANCE-ROLE

Aplicado a:

```text
financeiro_snapshots
```

E, como **fallback**, a `controle_despesas` quando `solicitacao_id IS NULL` (implementado por `OR` na expressão da policy única — ver §6.4).

Leitura: GM/financeiro/compras. Escrita: GM/financeiro.

### 6.3 FINANCE-OBRA

Aplicado a:

```text
financeiro_lancamentos, notas_fiscais, recebimentos
```

Contrato conforme §4.3 do spec. Escrita: GM ou (financeiro **e** (`obra_id IS NULL` ou `user_in_obra`)). Leitura amplia para `compras`.

### 6.4 VIA-PARENT

| Tabela | Pai | FK | Predicado de escopo do pai |
|--------|-----|----|----------------------------|
| `financeiro_rateios` | `financeiro_lancamentos` | `lancamento_id` | `p.obra_id is null or public.user_in_obra(auth.uid(), p.obra_id)` |
| `solicitacao_comentarios` | `solicitacoes_financeiras` | `solicitacao_id` | `public.can_access_solicitacao_financeira(p.id)` |
| `controle_despesas` (via pai) | `solicitacoes_financeiras` | `solicitacao_id` | `public.can_access_solicitacao_financeira(p.id)` |

Para `controle_despesas`, a policy única combina VIA-PARENT quando `solicitacao_id` está preenchido com o fallback FINANCE-ROLE quando não:

```sql
using (
  public.current_is_gm()
  or (
    (public.has_role(auth.uid(), 'financeiro') or public.has_role(auth.uid(), 'compras'))
    and (
      (solicitacao_id is not null
        and public.can_access_solicitacao_financeira(solicitacao_id))
      or (solicitacao_id is null
        and public.has_role(auth.uid(), 'financeiro'))
    )
  )
)
```

Escrita: mesmo padrão, restringindo o papel operacional a `financeiro` (com exceção nominal de `compras` em §7).

### 6.5 SOLICITACAO-FINANCEIRA

Aplicado exclusivamente a `solicitacoes_financeiras`. Exatamente **4 policies**, nomes canônicos:

- `solicitacoes_financeiras_select_scoped`
- `solicitacoes_financeiras_insert_solicitante`
- `solicitacoes_financeiras_update_segregated`
- `solicitacoes_financeiras_delete_gm_only`

Expressões copiadas literalmente de §4.5 do `SEC-002.batch-D.spec-01`. A segregação textual (`criado_por/solicitante <> current_profile_login()`) é obrigatória no `USING` **e** no `WITH CHECK` do `UPDATE`.

### 6.6 Exceções nominais obrigatórias

- **`controle_despesas`.** `compras` pode `INSERT/UPDATE` linhas próprias enquanto `pagamento_pendente = false`. Cláusula adicional no `WITH CHECK` de escrita, aplicada como `OR`:
  ```sql
  or (
    public.has_role(auth.uid(), 'compras')
    and solicitacao_id is not null
    and public.can_access_solicitacao_financeira(solicitacao_id)
    and coalesce(pagamento_pendente, false) = false
  )
  ```
- **`solicitacao_comentarios`.** `INSERT` liberado a quem lê a solicitação. `UPDATE/DELETE` restritos a GM ou `autor = public.current_profile_login()`. Materializado dividindo a policy `write` em duas expressões dentro do mesmo `FOR ALL` via `USING` (para `UPDATE/DELETE`) e `WITH CHECK` (para `INSERT`):
  ```sql
  using (
    public.current_is_gm()
    or (coalesce(autor,'') = public.current_profile_login() and public.current_profile_login() is not null)
  )
  with check (
    public.current_is_gm()
    or (
      exists (select 1 from public.solicitacoes_financeiras s
              where s.id = solicitacao_comentarios.solicitacao_id
                and public.can_access_solicitacao_financeira(s.id))
    )
  )
  ```
- **`financeiro_snapshots`.** `owner_id` **não** entra em `USING`/`WITH CHECK`. Apenas FINANCE-ROLE.
- **`dp_holerite`.** Sem policy de self-read. Auto-atendimento é changeset posterior.

## 7. Grants finais (repetição obrigatória por tabela)

Bloco padrão aplicado às **15** tabelas:

```sql
revoke all on public.<tabela> from anon;
grant select, insert, update, delete on public.<tabela> to authenticated;
grant all on public.<tabela> to service_role;
```

Nenhum `grant` a `anon` em qualquer tabela do lote. Helpers de §5 seguem os grants declarados lá.

Após `commit`, executar em janela read-only:

```sql

from   information_schema.role_table_grants
where  table_schema='public'
  and  grantee='anon'
  and  table_name in (<15 tabelas>);
-- oráculo: 0 linhas

-- 8.4 authenticated tem os 4 privilégios nas 15

from   information_schema.role_table_grants
where  table_schema='public'
  and  grantee='authenticated'
  and  table_name in (<15 tabelas>)
group  by table_name;
-- oráculo: 'DELETE,INSERT,SELECT,UPDATE' em todas

-- 8.5 helpers locais existem, security definer, sem grant a anon
select p.proname, p.prosecdef,
       has_function_privilege('anon',           p.oid, 'execute') as anon_can,
       has_function_privilege('authenticated',  p.oid, 'execute') as auth_can,
       has_function_privilege('service_role',   p.oid, 'execute') as svc_can
from   pg_proc p
join   pg_namespace n on n.oid = p.pronamespace
where  n.nspname = 'public'
  and  p.proname in ('current_profile_login','can_access_solicitacao_financeira');
-- oráculo: prosecdef=true, anon_can=false, auth_can=true, svc_can=true

-- 8.6 policies dependem dos helpers/papéis esperados

from   pg_policies
where  schemaname='public'
  and  tablename in (<15 tabelas>)
order  by tablename, policyname;
-- oráculo: sem USING(true), sem auth.uid() is not null permissivo,
--          referências a current_is_gm/has_role/user_in_obra/current_profile_login/can_access_solicitacao_financeira conforme §6
```

## 9. Rollback

Companion `SEC-002.batch-D.rollback.sql`, executável em transação única:

```sql
begin;
  -- para cada tabela do lote:
  drop policy if exists "<tabela>_select_..." on public.<tabela>;
  drop policy if exists "<tabela>_write_..."  on public.<tabela>;
  -- solicitacoes_financeiras: dropar as 4 policies canônicas.

  -- recria a policy legada permissiva conforme baseline do inventário-02:
  create policy "<tabela>_authenticated_all"
    on public.<tabela>
    for all
    to authenticated
    using (true)
    with check (true);
commit;
```

Helpers de §5 **não** são removidos — permanecem inertes. Grants **não** são revertidos — permanecem coerentes com o esquema atual. Rollback só é seguro se `batch-E` ainda não tiver sido aplicado.

## 11. Riscos

- **R1: segregação textual em `solicitacoes_financeiras`.** `current_profile_login()` é ponte enquanto não houver `solicitante_id/aprovador_id uuid`. Mitigação: `db-*` posterior para colunas UUID + backfill; segregação atual bloqueia apenas login coincidente.
- **R2: joins em VIA-PARENT.** `financeiro_rateios`, `solicitacao_comentarios` e `controle_despesas` fazem `EXISTS` no pai. Mitigação: gate deve confirmar índices em `financeiro_rateios(lancamento_id)`, `solicitacao_comentarios(solicitacao_id)`, `controle_despesas(solicitacao_id)`.
- **R3: `compras` amplo em leitura financeira.** Mitigação: leitura ampla é aceita para fluxo de solicitação/despesa; caso telas sensíveis precisem restringir, splittar `compras` em `SEC-002.batch-D.migration.errata-01`.
- **R4: PostgREST cacheia policies antigas.** Mitigação: `notify pgrst, 'reload schema';` no final da migração.
- **R5: importações backend.** Rotinas administrativas devem usar `service_role`; grants preservam `service_role` livre.
