# SEC-002.apply-template-01.spec-01 — Materialização operacional do checklist de apply

**Onda:** 2 (preparatória — bloqueada por fechamento de `SEC-001`)  
**Data:** 2026-07-12  
**Escopo:** especifica o PR de operação que materializa o contrato de `SEC-002.pr-checklist-01.spec-01`: criação do template `.github/pull_request_template/sec-002-apply.md`, workflow CI `sec002-pr-checklist` e scripts auxiliares de validação. Não aplica migrations, não altera policies, não altera `src/` e não muda edge functions.

## 1. Objetivos

1. Transformar o checklist documental em gate operacional bloqueante antes de qualquer apply de `SEC-002`.
2. Garantir que PRs `helpers-02`, `tests-02-suite`, `batch-B`, `batch-C`, `batch-D`, `batch-E` sejam validados por máquina.
3. Evitar parsing frágil de linguagem livre usando campos determinísticos (`sec002_apply_id`, `staging_snapshot_id`, checks marcados, arquivos alterados).
4. Manter a Onda 2 segura: este PR prepara a esteira, mas não executa nenhuma mudança de banco.

## 5. Workflow CI

`.github/workflows/sec002-pr-checklist.yml`:

```yaml
name: sec002-pr-checklist

on:
  pull_request:
    types: [opened, edited, synchronize, reopened, ready_for_review]

permissions:
  contents: read
  pull-requests: read

jobs:
  validate:
    if: contains(github.event.pull_request.title, '[SEC-002][apply:')
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - uses: actions/setup-node@v4
        with:
          node-version: 20

      - name: Collect changed files
        run: |
          git diff --name-only origin/${{ github.base_ref }}...HEAD > /tmp/sec002_changed_files.txt

      - name: Validate checklist body
        run: node scripts/sec002/validate-pr-checklist.mjs
        env:
          PR_TITLE: ${{ github.event.pull_request.title }}
          PR_BODY: ${{ github.event.pull_request.body }}

      - name: Validate changed files
        run: node scripts/sec002/validate-changed-files.mjs /tmp/sec002_changed_files.txt
        env:
          PR_TITLE: ${{ github.event.pull_request.title }}
          PR_BODY: ${{ github.event.pull_request.body }}

      - name: Validate staging parity metadata
        run: node scripts/sec002/validate-staging-parity.mjs
        env:
          PR_BODY: ${{ github.event.pull_request.body }}
```

O workflow roda apenas para PRs com título `[SEC-002][apply:<id>]`, evitando bloquear documentação comum.

## 6. Validador do corpo do PR

`validate-pr-checklist.mjs` deve:

1. Extrair `sec002_apply_id` do título e do corpo; ambos devem coincidir.
2. Validar que o id pertence ao mapa §4.
3. Verificar presença das seções obrigatórias: Identificação, Escopo, Pré-condições globais, Paridade staging, Testes RLS, Observabilidade, Freeze, Rollback, Aprovações, Pós-apply obrigatório.
4. Reprovar se houver checkbox `- [ ]` em seção obrigatória.
5. Reprovar se houver placeholder `<...>` remanescente.
6. Reprovar se `expected_asserts` do mapa não aparecer na linha `Assert count esperado confirmado`.
7. Reprovar se links/evidências obrigatórios estiverem vazios.

Saída em falha deve ser objetiva:

```text
SEC002_PR_CHECKLIST_FAILED
- missing_section: Observabilidade
- unchecked_item: Rollback testado em staging
- stale_placeholder: <CI_RUN_URL>
```

## 7. Validador de arquivos alterados

`validate-changed-files.mjs` deve:

1. Ler `/tmp/sec002_changed_files.txt`.
2. Resolver `allowed_paths` do `sec002_apply_id`.
3. Permitir sempre alterações no próprio corpo documental do lote correspondente.
4. Bloquear:
   - alterações em `src/**`;
   - alterações em lote anterior ou posterior;
   - alterações simultâneas em `helpers-02` e `batch-*`;
   - alterações em schemas proibidos por path de migration contendo `auth.`, `storage.`, `realtime.`, `supabase_functions.`, `vault.`;
   - alteração em `.github/sec002-staging-parity.json` no mesmo PR de apply.

Exceção: `tests-02-suite` pode alterar `.github/workflows/*sec*002*`, mas não pode conter migration.

## 8. Validador de paridade staging

`validate-staging-parity.mjs` deve ler `.github/sec002-staging-parity.json` e reprovar quando:

1. Arquivo ausente.
2. `fixtures_ok !== true`.
3. `helpers_suite_pass !== true`.
4. `last_refresh_at` tiver mais de 24 h.
5. `staging_snapshot_id` do PR divergir de `snapshot_id` do JSON.
6. `current_batch` divergir de `staging_batch` do mapa §4.

Para `helpers-02` e `tests-02-suite`, `current_batch` deve ser `none`; para lotes B–E, deve ser a letra do lote.

## 9. Integração com freeze guard

Este workflow não substitui `sec002-freeze-guard`; ele falha cedo em PR de apply. Ordem recomendada no CI:

```text
1. sec002-pr-checklist
2. sec002-freeze-guard
3. sec002-staging-parity
4. sec-002-tests
5. build/lint padrão
```

Se `sec002-pr-checklist` falhar, os demais jobs podem ser cancelados para reduzir ruído.
