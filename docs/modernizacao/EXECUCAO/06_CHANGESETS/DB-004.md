# DB-004 — Trilho MySQL rastreável

**Onda:** 3 · **Categoria:** Dados · **Prioridade:** P2 · **Criticidade:** C2
**Relacionado:** OPS-006 (backup/restore), DB-003 (baseline Postgres), D-3 (canonicidade)

## Problema

Scripts SQL do MySQL do host legado eram aplicados **manualmente e sem registro do que foi aplicado**. Drift entre repositório e banco era questão de tempo (Etapa 8, ficha DB-004).

## Ação

1. **Runner idempotente** [`ops/mysql-migrate.sh`](../../../../ops/mysql-migrate.sh):
   - Cria `schema_migrations_mysql` (filename PK + sha256 + timestamp + user) no bootstrap.
   - Aplica arquivos `migrations-mysql/*.sql` em ordem lexicográfica.
   - Detecta drift (checksum diverge do registrado) e falha com exit 3.
   - Suporta `--dry-run`.
2. **Documentação de trilho** [`docs/db/MYSQL_STATE.md`](../../../db/MYSQL_STATE.md): regras de escrita, uso, exit codes, convivência com Postgres.
3. **Diretório `migrations-mysql/`**: convenção definida; a criação física fica no repo espelho (a sandbox Lovable não hospeda o legado PHP/MySQL).

## Critérios de aceite

- (a) Tabela de controle registrando toda aplicação ✅ (via bootstrap do runner)
- (b) Runner idempotente com detecção de drift ✅
- (c) Documentação de uso e regras de escrita ✅
- (d) Conferência repo × schema executável em CI/cron — ⏳ **fora da sandbox**: exige acesso ao host MySQL legado, provisionado via secrets no runner de infra.

## Discoveries

- **D-21:** o runner assume MySQL 8+ para `ALTER … IF NOT EXISTS`. Hosts 5.7 exigirão wrapper com `INFORMATION_SCHEMA` — documentar no arquivo de migração se necessário.
