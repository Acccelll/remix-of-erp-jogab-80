**Onda:** 2 (bloqueada — PC1/PC2/PC3/PC4 OK; PC5–PC7 pendentes)  
**Rodada:** R117 (E3 — spec de escopo)  
**Standard:** E5  
**Precedente autorizante:** `SEC-002.wave-2-formal-open-01.pc4-scope-01.verifier-patch-01.materialize-01.md` (R116) — PC4 satisfeito em dry-run.  
**Escopo:** especificar o **escopo auditável** de `E_WAVE2_PC5`, sem materializar o artefato `.github/sec002-guards-status.json`, sem promover verificador a gate, sem bumpar apply-map, sem alterar `INDEX.md` e sem tocar produção.

---

## 1. Objetivo

Contratar as próximas rodadas responsáveis por satisfazer `E_WAVE2_PC5`, fixando:

1. O contrato exato exigido por `verifyPC5()` de `scripts/sec002/verify-wave-2-preconditions.mjs`.
2. O estado atual auditado: arquivo `.github/sec002-guards-status.json` ausente.
3. O formato mínimo do artefato futuro de status verde dos guards.
4. As invariantes que impedem simulação opaca, promoção prematura de workflow ou abertura formal da Onda 2 antes de PC6–PC7.

Este spec **não cria** `.github/sec002-guards-status.json`, **não altera** o verificador, o `INDEX.md`, o apply-map ou workflows. Apenas fixa contrato, critérios de aceite e rejeição para as rodadas seguintes.

---

## 2. Fonte normativa do escopo (R97/R116)

`scripts/sec002/verify-wave-2-preconditions.mjs :: verifyPC5()` exige literalmente:

1. **Arquivo presente:** `.github/sec002-guards-status.json` deve existir e ser JSON válido.
2. **Identificação do verde:** o JSON deve conter `last_green_sha` com valor truthy.
3. **Rastreabilidade do verde:** o JSON deve conter `last_green_run_url` com valor truthy.
4. **Data válida:** deve existir uma data em `last_green_at`, ou `generated_at`, ou `evaluated_at`.
5. **Janela temporal:** a data escolhida deve ser parseável por `Date.parse`, não pode estar no futuro e não pode ter idade superior a 7 dias no momento da verificação.

Nenhuma outra propriedade é exigida por R97/R116 nesta pré-condição; propriedades adicionais são permitidas desde que não violem (1)–(5).

## 4. Contrato do artefato previsto

O artefato futuro deve ser criado em:

```text
.github/sec002-guards-status.json
```

Formato mínimo canônico:

```json
{
  "schema_version": "v2026-07-12.4",
  "apply_id": "wave-2-formal-open-01",
  "last_green_sha": "<sha auditável do último ciclo verde>",
  "last_green_run_url": "<URL auditável do último ciclo verde>",
  "last_green_at": "<ISO-8601 UTC dentro da janela de 7 dias>",
  "source": "manual-attestation",
  "notes": [
    "Artefato documental para E_WAVE2_PC5.",
    "Não promove workflow e não abre Onda 2."
  ]
}
```

`generated_at` e `evaluated_at` são aceitos pelo verificador como alternativas técnicas, mas o campo preferencial para R118/R119 é `last_green_at`, por refletir explicitamente a semântica do último ciclo verde.

## 7. Critérios de rejeição para R118/R119

R118 ou R119 devem ser recusados se:

1. Alterarem `verifyPC5()` para contornar a ausência do artefato.
2. Criarem o JSON fora de `.github/sec002-guards-status.json`.
3. Omitirem `last_green_sha` ou `last_green_run_url`.
4. Usarem data inválida, futura ou mais antiga que 7 dias no momento da validação.
5. Declararem PC6, PC7 ou Onda 2 como satisfeitos por consequência de PC5.
6. Tocarem código de produção, schema, funções, migrações, frontend, workflows, apply-map ou `INDEX.md` sem rodada própria.
7. Omitirem manifest próprio da materialização.
8. Falharem em `node scripts/sec002/verify-wave-2-preconditions.mjs --dry-run --only=PC5`.
