# SEC-002.tests-02.assert-01.spec-01 — Helpers de assert RLS para pgTAP

**Onda:** 2 (OPEN)  
**Ref:** R186 · **Round:** compact-01  
**Data:** 2026-07-12  
**Escopo:** especifica os helpers `pg_temp.assert_rls_{select,insert,update,delete}` que serão acrescentados em `supabase/tests/sec-002/_lib/assert.sql` no apply seguinte. **Nenhum `.sql` é alterado neste changeset**; apenas contrato, assinatura, semântica de erro e mapeamento para os 315 `test_id` de `SEC-002.tests-01`/`SEC-002.tests-02.spec-01`.

## 1. Motivação

`SEC-002.tests-02.spec-01` decompõe 315 `test_id` em arquivos pgTAP por caso, mas cada arquivo precisa de um oráculo uniforme para os quatro comandos. Sem helpers comuns, o gerador duplicaria blocos `throws_ok`/`lives_ok`/`is_empty` em 315 arquivos, aumentando divergência e dificultando diagnóstico.

Este changeset fixa uma camada única de assert para:

1. normalizar `{allow, deny, empty}`;
2. separar erro de permissão de resultado vazio;
3. preservar o `test_id` no nome de cada assert;
4. permitir geração determinística por `gen-tests-02.mjs`.

## 3. Assinaturas canônicas

Os helpers serão `pg_temp` para não poluir `public` e para manter isolamento por sessão de teste:

```sql
create or replace function pg_temp.assert_rls_select(
  _test_id text,
  _sql text,
  _expect text
) returns void language plpgsql as $$ ... $$;

create or replace function pg_temp.assert_rls_insert(
  _test_id text,
  _sql text,
  _expect text
) returns void language plpgsql as $$ ... $$;

create or replace function pg_temp.assert_rls_update(
  _test_id text,
  _sql text,
  _expect text
) returns void language plpgsql as $$ ... $$;

create or replace function pg_temp.assert_rls_delete(
  _test_id text,
  _sql text,
  _expect text
) returns void language plpgsql as $$ ... $$;
```

`_sql` é sempre gerado pelo repositório (`gen-tests-02.mjs`), nunca interpolado de entrada externa.

## 4. Semântica de `_expect`

| Expect | SELECT | INSERT/UPDATE/DELETE |
|--------|--------|----------------------|
| `allow` | consulta executa e retorna `count(*) > 0` | comando executa sem exceção e afeta `row_count > 0` quando aplicável |
| `empty` | consulta executa e retorna `count(*) = 0` | inválido para escrita; helper falha com `E_ASSERT_EXPECT_INVALID` |
| `deny` | consulta levanta erro RLS/permissão **ou** retorna 0 quando o caso é anon/outsider | comando levanta erro RLS/permissão **ou** afeta 0 linhas em `UPDATE/DELETE` filtrados por RLS |

Erros aceitos como negação: `42501` (`insufficient_privilege`), `P0001` com mensagem RLS, e mensagens contendo `violates row-level security policy` ou `permission denied`.

## 5. Pseudocódigo obrigatório

### 5.1 SELECT

```sql
begin
  execute format('select count(*) from (%s) q', _sql) into v_count;

  if _expect = 'allow' and v_count > 0 then
    perform pass(_test_id || ' select allow');
  elsif _expect = 'empty' and v_count = 0 then
    perform pass(_test_id || ' select empty');
  elsif _expect = 'deny' and v_count = 0 then
    perform pass(_test_id || ' select deny-empty');
  else
    perform fail(_test_id || ' select expected ' || _expect || ' got count=' || v_count);
  end if;
exception when insufficient_privilege then
  if _expect = 'deny' then perform pass(_test_id || ' select deny-error');
  else perform fail(_test_id || ' select unexpected permission error'); end if;
end;
```

### 5.2 Escritas

```sql
begin
  execute _sql;
  get diagnostics v_rows = row_count;

  if _expect = 'allow' and v_rows > 0 then
    perform pass(_test_id || ' <cmd> allow');
  elsif _expect = 'deny' and v_rows = 0 then
    perform pass(_test_id || ' <cmd> deny-filtered');
  else
    perform fail(_test_id || ' <cmd> expected ' || _expect || ' got rows=' || v_rows);
  end if;
exception when insufficient_privilege or check_violation then
  if _expect = 'deny' then perform pass(_test_id || ' <cmd> deny-error');
  else perform fail(_test_id || ' <cmd> unexpected denial'); end if;
end;
```

`<cmd>` deve ser substituído internamente por `insert`, `update` ou `delete` conforme helper chamado.

## 6. Integração com pgTAP

Cada arquivo gerado mantém `select plan(4)` e invoca exatamente quatro asserts:

```sql
select pg_temp.assert_rls_select(:'test_id', :'select_sql', :'select_expect');
select pg_temp.assert_rls_insert(:'test_id', :'insert_sql', :'insert_expect');
select pg_temp.assert_rls_update(:'test_id', :'update_sql', :'update_expect');
select pg_temp.assert_rls_delete(:'test_id', :'delete_sql', :'delete_expect');
```

Os helpers usam `pass()`/`fail()` do pgTAP; não usam `raise notice` como oráculo final. O runner continua abortando em falha via `ON_ERROR_STOP=1`.

## 7. Regras de segurança

1. Nenhum helper roda como `security definer`.
2. Nenhum helper altera `role`, `request.jwt.claims` ou `search_path`.
3. Nenhum helper toca schemas `auth`, `storage`, `realtime`, `vault` ou `supabase_functions`.
4. Nenhum helper faz DDL, `grant`, `revoke`, `alter table` ou `drop policy`.
5. `_sql` só pode vir do gerador versionado; o gerador deve bloquear `;` múltiplo e comandos fora de `select/insert/update/delete`.
