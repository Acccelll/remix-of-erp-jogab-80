**Materializa:** `.github/sec002-acceptance/<apply-id>.md` + `scripts/sec002/validate-acceptance-gates.mjs`

## 1. Objetivo

Definir critérios determinísticos de aceitação após cada apply `SEC-002` (`helpers-02`, `tests-02-suite`, `batch-B/C/D/E`) para decidir se o lote pode ser encerrado, se permanece em observação ou se exige rollback/hotfix. Este spec consolida:

1. gates técnicos pós-apply;
2. gates funcionais por lote;
3. gates de segurança e regressão RLS;
4. gates de observabilidade T+1h/T+24h;
5. evidências mínimas e responsáveis;
6. artefato auditável `.github/sec002-acceptance/<apply-id>.md`.

Sem aceitação válida em T+24h, o próximo lote `SEC-002` **não** pode entrar em `GO`.

## 2. Fora de escopo

- Autorizar merge inicial do apply — isso pertence a `go-no-go-01`.
- Executar rollback/hotfix — isso pertence a `incident-runbook-01`.
- Criar dashboards novos — este spec consome `observability-01`.
- Alterar migrações, policies, código de produção ou funções edge.

## 3. Estados de aceitação

| Estado | Semântica | Efeito |
|--------|-----------|--------|
| `ACCEPTED` | Todos os gates obrigatórios verdes em T+24h. | Encerra lote e libera preparação do próximo. |
| `OBSERVE` | Sem falha crítica, mas há métrica instável ou evidência parcial. | Mantém freeze e observação por mais 24 h. |
| `REJECTED` | ≥1 gate crítico falhou ou evidência ausente. | Bloqueia próximo lote e aciona incidente. |
| `WAIVED` | Exceção formal aprovada por GM para gate não crítico. | Libera com risco aceito e ação corretiva registrada. |

Regras duras:

1. RLS falso-permissivo, vazamento de PII ou divergência `has_role` → `REJECTED`, sem waiver.
2. Falha de suíte RLS em produção → `REJECTED`, salvo falha comprovada de infraestrutura com rerun verde.
3. `OBSERVE` não pode durar mais de 48 h sem virar `ACCEPTED` ou `REJECTED`.

## 6. Artefato de aceitação

Arquivo: `.github/sec002-acceptance/<apply-id>.md`.

Formato obrigatório:

```yaml

acceptance_state: <ACCEPTED|OBSERVE|REJECTED|WAIVED>
evaluated_at: <ISO8601 UTC>
evaluated_by:
  dri_technical: <github-login>
  dri_tests: <github-login>
  dri_observability: <github-login>
  gm: <github-login|null>
source_refs:
  pr: <url>
  go_no_go: .github/sec002-go-no-go/<apply-id>.md
  comms: .github/sec002-comms/<apply-id>.md

  incident_refs: []
gates:
  A1: { status: pass|fail|waived, ref: <url>, notes: <texto|null> }
  A2: { status: pass|fail|waived, ref: <url>, notes: <texto|null> }
  A3: { status: pass|fail|waived, ref: <url>, notes: <texto|null> }
  A4: { status: pass|fail|waived, ref: <url>, notes: <texto|null> }
  A5: { status: pass|fail|waived, ref: <url>, notes: <texto|null> }
  A6: { status: pass|fail|waived, ref: <url>, notes: <texto|null> }
  A7: { status: pass|fail|waived, ref: <url>, notes: <texto|null> }

```

## 7. Regras de decisão

1. `ACCEPTED` exige todos os gates obrigatórios e específicos com `status=pass`.
2. `OBSERVE` permite até 2 gates não críticos com evidência parcial, desde que `A2`, `A3`, `A7` estejam `pass`.
3. `REJECTED` exige `next_action=open_incident` e ao menos um `incident_refs[]` em até 15 min.
4. `WAIVED` exige `waivers[]` com aprovação GM e plano corretivo.
5. `A2`, `A3`, `A7` não aceitam `waived`.
6. Todo `ref` deve ser não vazio e não pode conter placeholder `<...>`.

## 8. Waiver controlado

Formato de `waivers[]`:

```yaml
waivers:
  - gate_id: <A1|A4|A5|A6|A8|AH*|AT*|AB*|AC*|AD*|AE*>
    reason: <texto>
    risk: <low|medium|high>
    approved_by: <github-login GM>
    corrective_action: <texto>
    due_at: <ISO8601 UTC>
```

Waiver proibido para:

- qualquer gate ligado a RLS falso-permissivo;
- `A2`, `A3`, `A7`;
- ausência total de comunicação T+24h;
- incidente SEV1/SEV2 aberto.

## 9. Validador `scripts/sec002/validate-acceptance-gates.mjs` (materialização futura)

Assinatura:

```bash
node scripts/sec002/validate-acceptance-gates.mjs --apply-id <id> --file .github/sec002-acceptance/<id>.md
```

Verificações determinísticas:

1. arquivo existe e frontmatter YAML é válido;
2. `sec002_apply_id` = argumento `--apply-id`;
3. `acceptance_state ∈ {ACCEPTED,OBSERVE,REJECTED,WAIVED}`;
4. `go_no_go`, `comms` e `staging_parity` existem;
5. gates globais `A1–A8` presentes;
6. gates específicos esperados para o apply presentes;
7. `ACCEPTED` exige todos `status=pass`;
8. `OBSERVE` exige `A2/A3/A7=pass`;
9. `REJECTED` exige `next_action=open_incident`;
10. `WAIVED` exige `waivers[]` válido e GM preenchido;
11. `A2/A3/A7` não podem ser `waived`;
12. nenhum campo contém placeholder `<...>`.

Exit codes: `0` válido; `1` inválido com mensagem determinística no stderr.

## 10. Integração com release train

O acceptance gate roda após a janela T+24h de cada apply e antes de qualquer novo `go-no-go`:

```text
apply concluído
→ observabilidade T+1h
→ comunicação T+1h
→ observabilidade T+24h
→ comunicação T+24h
→ validate-acceptance-gates
→ próximo lote pode iniciar go/no-go
```

Ordem entre lotes:

1. `helpers-02` só libera `tests-02-suite` se `ACCEPTED`.
2. `tests-02-suite` só libera `batch-B` se `ACCEPTED`.
3. `batch-B` só libera `batch-C` se `ACCEPTED`.
4. `batch-C` só libera `batch-D` se `ACCEPTED`.
5. `batch-D` só libera `batch-E` se `ACCEPTED`.
6. `batch-E` só libera handoff pós-RLS se `ACCEPTED`.
