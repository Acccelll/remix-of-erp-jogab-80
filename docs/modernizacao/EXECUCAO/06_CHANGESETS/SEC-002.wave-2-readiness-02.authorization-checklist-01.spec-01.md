# R218' — SEC-002 · Wave 2 Readiness · Authorization Checklist (spec)

**Tipo:** especificação · governança pura  
**Alvo:** checklist canônico de validação sintática/semântica de intakes GM (R213') e D-3 (R214'), consumindo o contrato R216' e os templates R217'.  
**Baseline:** R208', R209', R210', R211', R212', R213', R214', R215', R216', R217'.  
**Data:** 2026-07-12.

## 1. Objetivo

Definir o checklist único que qualquer intake externo precisa satisfazer, item por item, para ser reconhecido como autorização válida de abertura de round documental (R213' ou R214'). Este spec **não** assina, **não** cria `GO-SEC-002-helpers-02-deploy-01.md`, **não** preenche §5 de `D-3-SEC-002.md`, **não** faz deploy de `helpers-02` e **não** aplica `helpers-03`.

## 2. Checklist GM (para intake conforme R213' + template R217')

Um intake GM é **válido** se e somente se todos os itens abaixo forem verdadeiros:

- [ ] alvo textual é exatamente `helpers-02.deploy-01`;
- [ ] decisão única `GO` **xor** `NO-GO` (nunca ambas, nunca ausente);
- [ ] assinante é `Cappucceno` ou GM formal identificado por papel;
- [ ] data em ISO-8601 (`YYYY-MM-DDTHH:MM:SSZ`);
- [ ] refs preservam R208', R211', R213' byte-a-byte;
- [ ] hash SHA-256 de R208' registrado como baseline;
- [ ] se `GO`: janela de deploy, DRI operacional e rollback owner declarados;
- [ ] se `NO-GO`: motivo textual e condição de reabertura declarados;
- [ ] evidência textual de `verify-wave-2-preconditions.mjs --json` mais recente com PC1..PC7 verdes;
- [ ] nenhum segredo/chave/senha embutido no intake.

Falha em qualquer item ⇒ intake **inválido** ⇒ nenhum efeito, R213' permanece aguardando.

## 3. Checklist D-3 (para intake conforme R214' + template R217')

Um intake D-3 é **válido** se e somente se todos os itens abaixo forem verdadeiros:

- [ ] alvo textual é exatamente `helpers-03.apply-01`;
- [ ] opção única `D-3a` **xor** `D-3b` **xor** `D-3c` (nunca múltipla, nunca ausente);
- [ ] assinante é DRI Produto **e** DRI Segurança identificados por papel;
- [ ] data em ISO-8601 (`YYYY-MM-DDTHH:MM:SSZ`);
- [ ] refs preservam R209', R210', R212', R214' byte-a-byte;
- [ ] hash SHA-256 de R210' registrado como baseline;
- [ ] reconhecimento textual explícito de que `D-3a` só destrava abertura futura de `helpers-03.apply-01.materialize-01` **após** deploy de helpers-02;
- [ ] reconhecimento de que `D-3b`/`D-3c` mantêm bloqueio até novo spec de bump;
- [ ] evidência textual de `verify-wave-2-preconditions.mjs --json` mais recente com PC1..PC7 verdes;
- [ ] nenhum segredo/chave/senha embutido no intake.

Falha em qualquer item ⇒ intake **inválido** ⇒ nenhum efeito, R214' permanece aguardando.

## 4. Roteamento pós-validação

- GM válido ⇒ abre R213' materialize (criação de `GO-SEC-002-helpers-02-deploy-01.md` em round autorizado).
- D-3 válida ⇒ abre R214' materialize (preenchimento de §5 de `D-3-SEC-002.md` em round autorizado).
- Ambos válidos no mesmo ciclo ⇒ processar GM primeiro (helpers-03 depende de helpers-02 deployado).
- Ambos inválidos ⇒ manter governança e aguardar novo intake.
