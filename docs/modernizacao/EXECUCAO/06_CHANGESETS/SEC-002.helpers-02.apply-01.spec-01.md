**Onda:** 2 (OPEN — gate operacional PC1..PC7 reativado por R130)
**Data:** 2026-07-12
**Escopo:** especifica o **primeiro apply autorizado** do write set da Onda 2 —
materializar o arquivo físico `supabase/migrations/<yyyymmddhhmmss>_sec_002_helpers_02.sql`
conforme o contrato imutável de `SEC-002.helpers-02.spec-01` (§§1–11). Este changeset
**não** aplica SQL ao banco, **não** altera policies, **não** consome os lotes B/C/D/E.
Ele apenas fixa o contrato do apply e as invariantes AP1–AP12 que a materialização
subsequente (`materialize-01`) precisará satisfazer.

## 1. Pré-condições duras

O apply só pode ser materializado se **todas** verdadeiras:

1. Onda 2 `OPEN` — `.github/sec002-readiness/wave-2.md` com bloco canônico de R95 §3
   (garantido por R127 e reverificado por R130).
2. `node scripts/sec002/verify-wave-2-preconditions.mjs --json` → `PC1..PC7 = OK`
   contra `main` no SHA imediatamente anterior ao apply (gate operacional restaurado
   por R130; `EXPECTED_INDEX_ROWS = 30`).
3. `SEC-002.helpers-01` (contrato lógico das 4 funções) e `SEC-002.helpers-02.spec-01`
   (contrato do arquivo SQL) presentes e imutáveis no repositório.
4. `SEC-001` release train R1–R10 concluído (dependência declarada em
   `SEC-002.helpers-02.spec-01` §2.1).
5. Nenhuma policy dos lotes B/C/D/E aplicada em produção (§2.4 idem).

Se qualquer item falhar, o apply é abortado sem escrever bytes.

## 3. Invariantes AP1–AP12

- **AP1** — Um único arquivo `.sql` criado sob `supabase/migrations/`.
- **AP2** — Nome bate `^\d{14}_sec_002_helpers_02\.sql$`.
- **AP3** — Um único `begin;` … `commit;`; nenhum `savepoint`, nenhum DDL fora do bloco.
- **AP4** — Quatro `create or replace function` na ordem topológica
  `user_in_empresa → user_in_obra → user_in_board → user_in_card`.
- **AP5** — Assinaturas, `search_path = public`, `security definer`, `stable`,
  `language sql` idênticas a `SEC-002.helpers-01` §4 (diff textual = 0).
- **AP6** — Quatro pares `revoke all … from public, anon;` seguidos de
  `grant execute … to authenticated, service_role;`. Nenhum `grant … to anon`
  ou `to public`.
- **AP7** — Cinco `create index if not exists` exatamente como spec §6; nenhum
  `unique`, nenhum `concurrently`.
- **AP8** — Quatro `comment on function` apontando `SEC-002.helpers-01§4.x`.
- **AP9** — Zero `drop function`, zero `alter function`, zero `create policy`,
  zero mutação em tabelas.
- **AP10** — Diff físico do arquivo ≤ 200 linhas (spec §10).
- **AP11** — Manifest `helpers-02-apply-01/manifest.json` com `schema_version:
  v2026-07-12.4`, `apply_id: helpers-02-apply-01`, `verifier_gate: on`,
  `refs` incluindo `R131`.
- **AP12** — `node scripts/sec002/verify-wave-2-preconditions.mjs --json` continua
  `PC1..PC7 = OK` após o apply (o arquivo SQL novo não invalida o INDEX nem o
  readiness — a linha 31 do `INDEX.md` só entra em `self-register-01`).

## 4. Efeito no banco

**Nenhum neste changeset e nenhum no `materialize-01`.** A migração é apenas
gravada como arquivo versionado. A execução real contra staging/produção fica
condicionada a:

1. Suíte `SEC-002.tests-02.suite/helpers` verde (changeset separado).
2. Janela de deploy declarada por DRI GM `Cappucceno`.
3. Verificação pós-migração §7 do spec-01 retornando os 4 oráculos esperados.

## 5. Rollback do apply (não do SQL)

Se `materialize-01` for revertido antes do deploy, basta remover os 2 arquivos
do write set (§2) e o `INDEX.md` volta ao estado de R130 sem efeito colateral.
O rollback do SQL propriamente dito segue §9 do `SEC-002.helpers-02.spec-01` e
só se aplica após deploy real.
